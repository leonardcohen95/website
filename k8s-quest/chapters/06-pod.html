    Pod 详解

    Pod 是 Kubernetes 中最小的部署单元，但它绝不仅仅是"装容器的盒子"。本章我们深入 Pod 的内部：它的生命周期、Init 容器、Sidecar 模式、资源限制、健康探针以及优雅终止机制。理解这些细节，才能让你的应用在 K8s 中稳定、高效地运行。

    学习目标

    • 理解 Pod 的定义以及共享网络与存储的特性
    • 掌握 Pod 的生命周期与各阶段状态
    • 了解 Init 容器和 Sidecar 模式的使用场景
    • 学会配置 requests 和 limits 资源限制
    • 掌握 liveness、readiness、startup 三种探针
    • 理解优雅终止与 terminationGracePeriodSeconds

    1. Pod 是什么

    🫛 Pod

    Pod 是 Kubernetes 中最小的部署单元。一个 Pod 包含一个或多个紧密协作的容器， 这些容器共享网络命名空间（同一个 IP 地址和端口空间）和 共享存储卷。容器之间可以通过 localhost 直接通信，并共享挂载的 Volume。

    K8s 不直接管理容器，而是管理 Pod。调度器以 Pod 为单位分配到节点上， 同一个 Pod 内的容器始终被调度到同一个节点。

    🌰 为什么需要 Pod

    Docker 是单容器模型，容器之间相互隔离。但现实中，有些应用需要紧密协作—— 比如主应用和日志收集器需要共享网络和数据。Pod 就是为了解决"多个容器需要共享上下文"的问题而设计的。

    2. Pod 生命周期

    Pod 从创建到销毁会经历一系列状态变化，这些状态反映在 Pod 的 status.phase 字段中：

    ⏳ Pending

    Pod 已被 API Server 接收，但还没有被调度到节点上，或者镜像还在拉取中。 这是 Pod 创建后的初始状态。

    🏃 Running

    Pod 已经调度到某个节点上，且至少有一个容器在运行。 容器可能正在启动、正在运行，或者正在重启。

    ✅ Succeeded

    Pod 中的所有容器都已成功退出（退出码为 0），且不会再重启。 常见于 Job 类型的一次性任务。

    ❌ Failed

    Pod 中的所有容器都已终止，且至少有一个容器以非零状态码退出， 或者被系统杀死。

    ⚠️ Unknown（补充）

    当节点失联或无法获取 Pod 状态时，Pod 会进入 Unknown 状态。 通常是节点故障或网络问题导致的。

    3. Init 容器

    Init 容器是在主容器启动之前运行的初始化容器。 它可以执行一些准备工作，比如拉取配置、等待依赖服务就绪、初始化数据库等。

    ⚙️ Init Container 的特点

    • Init 容器按顺序运行，前一个成功完成后才会启动下一个
    • 所有 Init 容器都成功完成后，主容器才会启动
    • 如果某个 Init 容器失败，Pod 会不断重试（直到成功或达到 restartPolicy 限制）
    • Init 容器不支持就绪探针（readinessProbe），因为它们必须运行完成 

    apiVersion: v1
kind: Pod
metadata:
  name: myapp-pod
spec:
  initContainers:
  - name: wait-for-db
    image: busybox
    command: ['sh', '-c', 'until nslookup mydb; do sleep 2; done']
  containers:
  - name: myapp
    image: myapp:latest
    💡 典型场景

    等待数据库服务就绪、初始化配置文件、从远程拉取数据、执行数据库迁移脚本等。 把这些逻辑放在 Init 容器里，可以让主容器保持纯净。

    4. Sidecar 模式

    Sidecar（边车）模式是指在一个 Pod 中，除了主应用容器外， 再运行一个或多个辅助容器，用于增强主容器的能力。

    🚗 Sidecar 模式的常见用途

    • 日志收集：fluentd / filebeat 采集主容器的日志并转发到日志中心
    • 服务代理：istio/envoy sidecar 拦截流量实现服务治理
    • 配置同步：辅助容器定期拉取并刷新配置文件
    • 数据同步：定时备份主容器产生的数据

    Sidecar 容器和主容器共享网络和存储，因此它可以直接读取主容器写入 Volume 的日志文件， 或通过 localhost 与主容器通信。

    🔄 Sidecar vs Init Container

    Init 容器是"一次性"的，运行完就退出；Sidecar 容器是"常驻"的，和主容器一起运行。 前者用于启动前准备，后者用于运行时增强。

    5. 资源限制：requests 与 limits

    在 K8s 中，每个容器都可以声明资源需求。这不仅能保证容器获得足够的资源， 还能防止某个容器吃光节点资源影响其他应用。

    📥 requests（资源请求）

    容器启动时保证能分配到的资源量。 调度器根据 requests 来决定把 Pod 调度到哪个节点——只有剩余资源满足 requests 的节点才会被选中。

    📤 limits（资源上限）

    容器最多能使用的资源量。 超过 limits 的内存使用会导致容器被 OOMKilled，超过 limits 的 CPU 使用会被限流（throttled）。 

    resources:
  requests:
    cpu: 100m        # 0.1 核 CPU
    memory: 128Mi    # 128 MB 内存
  limits:
    cpu: 500m        # 0.5 核 CPU
    memory: 512Mi    # 512 MB 内存
    ⚠️ requests 与 limits 的关系

    如果只设置 limits 不设置 requests，K8s 会默认让 requests 等于 limits（保证服务质量 QoS = Guaranteed）。 生产环境建议两者都显式设置，避免资源浪费或被驱逐。

    6. 健康探针

    健康探针（Probe）是 K8s 判断容器是否健康的重要机制。通过探针，K8s 能知道容器是否活着、是否准备好接收流量。

    ❤️ livenessProbe（存活探针）

    检测容器是否还活着。如果探针失败，kubelet 会杀掉容器并根据 restartPolicy 决定是否重启。 用于检测死锁、应用挂起等内部故障。

    ✅ readinessProbe（就绪探针）

    检测容器是否准备好接收流量。如果探针失败，K8s 会把该 Pod 从 Service 的端点列表中移除， 但不会杀掉容器。用于应用启动慢、依赖未就绪等场景。

    🚀 startupProbe（启动探针）

    专门用于检测容器的启动过程。在 startupProbe 成功之前，liveness 和 readiness 探针都会被暂时禁用。 非常适合启动慢的应用，避免在启动期间被 livenessProbe 误杀。

    探针支持三种检测方式：httpGet（HTTP 接口）、tcpSocket（TCP 端口）、exec（执行命令）。

    livenessProbe:
  httpGet:
    path: /healthz
    port: 8080
  initialDelaySeconds: 10
  periodSeconds: 5
readinessProbe:
  httpGet:
    path: /ready
    port: 8080
  periodSeconds: 3
    💡 探针使用建议

    生产环境建议同时配置 livenessProbe 和 readinessProbe。 对于启动时间较长的应用，务必配置 startupProbe，否则可能在启动期间被 livenessProbe 反复重启。

    7. 优雅终止

    当一个 Pod 被删除时，K8s 不会立即强杀容器，而是给容器一个优雅关闭的机会。 整个过程涉及 terminationGracePeriodSeconds 参数（默认 30 秒）。

    🛑 优雅终止流程

    1. K8s 将 Pod 标记为 Terminating，并从 Service 端点中移除
    2. 同时给容器发送 SIGTERM 信号
    3. 容器在 terminationGracePeriodSeconds 时间内完成清理并退出
    4. 如果超时未退出，K8s 发送 SIGKILL 强制杀死容器
    5. kubelet 删除 Pod 

    spec:
  terminationGracePeriodSeconds: 60
  containers:
  - name: myapp
    image: myapp:latest
    lifecycle:
      preStop:
        exec:
          command: ['sh', '-c', 'nginx -s quit']
    ⚠️ preStop 钩子

    preStop 钩子会在收到 SIGTERM 之前执行，常用于执行优雅关闭命令（如 nginx -s quit）或通知负载均衡器摘除流量。 注意：preStop 的执行时间也计入 terminationGracePeriodSeconds。

    本章小结

    • Pod 是 K8s 最小部署单元，容器共享网络和存储
    • Pod 生命周期：Pending → Running → Succeeded / Failed
    • Init 容器在主容器前运行，用于初始化准备工作
    • Sidecar 模式：主容器 + 常驻辅助容器（日志、代理等）
    • requests 是资源请求（调度依据），limits 是资源上限（防止超用）
    • liveness 探针决定是否重启容器，readiness 探针决定是否接收流量，startup 探针保护慢启动应用
    • terminationGracePeriodSeconds 控制优雅终止的超时时间，默认 30 秒
