    Service 服务发现

    Pod 的 IP 是临时的——Pod 重启、迁移、伸缩后 IP 都会变化。直接访问 Pod IP 显然不靠谱。Service 就是为了解决这个问题而生的：它为一组 Pod 提供一个稳定的网络入口，并负责负载均衡。本章我们学习 Service 的四种类型、Headless Service 的用途，以及 kube-proxy 的工作模式。

    学习目标

    • 理解 Service 的作用：稳定网络入口 + 负载均衡
    • 掌握 ClusterIP、NodePort、LoadBalancer 三种 Service 类型
    • 理解 Headless Service 的用途（与 StatefulSet 配合）
    • 了解 kube-proxy 的 iptables 和 ipvs 两种模式
    • 学会创建和使用 Service

    1. Service 是什么

    🌐 Service

    Service 为一组 Pod 提供一个稳定的访问入口（虚拟 IP / DNS 名称）， 并对后端 Pod 进行负载均衡。Service 通过 Label Selector 选择后端 Pod， 客户端只需访问 Service，无需关心后端 Pod 的变化。

    Service 的核心价值在于解耦：Service 和 Pod 之间没有硬编码的关联， 全靠标签匹配。Pod 增减、重启、迁移都不影响 Service 的访问地址。 

    apiVersion: v1
kind: Service
metadata:
  name: nginx-svc
spec:
  selector:
    app: nginx          # 选择所有标签为 app=nginx 的 Pod
  ports:
  - protocol: TCP
    port: 80            # Service 端口
    targetPort: 80      # 后端 Pod 端口
  type: ClusterIP
    💡 Service 的三种端口

    • port：Service 暴露的端口（集群内部访问用）
    • targetPort：后端 Pod 上的端口
    • nodePort：节点上开放的端口（仅 NodePort 类型，30000-32767 范围）

    2. ClusterIP —— 集群内部访问

    🔵 ClusterIP（默认）

    为 Service 分配一个集群内部的虚拟 IP，只能在集群内部访问。 这是 Service 的默认类型，适合服务间内部通信。

    集群内的 Pod 可以通过 Service 的 ClusterIP 或 DNS 名称（如 nginx-svc.default.svc.cluster.local）访问服务。 同命名空间下可以直接用 Service 名称访问。 

    # 查看 Service，CLUSTER-IP 列就是虚拟 IP
kubectl get svc

# 集群内 Pod 可通过 DNS 访问：
# http://nginx-svc:80   （同命名空间）
# http://nginx-svc.default.svc.cluster.local:80  （完整域名）

    3. NodePort —— 通过节点端口暴露

    🟢 NodePort

    在每个节点上开放一个固定端口（默认范围 30000-32767）， 外部可以通过 任意节点IP:NodePort 访问服务。 NodePort 内部会创建一个 ClusterIP，外部流量经节点端口转发到 ClusterIP，再负载均衡到后端 Pod。 

    apiVersion: v1
kind: Service
metadata:
  name: nginx-nodeport
spec:
  type: NodePort
  selector:
    app: nginx
  ports:
  - port: 80
    targetPort: 80
    nodePort: 30080     # 可选，不指定则自动分配（30000-32767）
    ⚠️ NodePort 的局限

    NodePort 端口范围有限（30000-32767），且需要外部用户知道节点 IP。 生产环境通常不直接用 NodePort 对外服务，而是配合 LoadBalancer 或 Ingress 使用。

    4. LoadBalancer —— 云厂商负载均衡

    🟣 LoadBalancer

    调用云厂商的负载均衡器，为 Service 分配一个外部 IP。 外部流量先到云负载均衡器，再转发到节点的 NodePort，最终到达后端 Pod。 此类型需要在支持 LoadBalancer 的环境（如 AWS、GCP、Azure、阿里云）中使用。 

    apiVersion: v1
kind: Service
metadata:
  name: nginx-lb
spec:
  type: LoadBalancer
  selector:
    app: nginx
  ports:
  - port: 80
    targetPort: 80
    💡 LoadBalancer = NodePort + 外部 LB

    LoadBalancer 类型本质上是在 NodePort 的基础上，由云厂商自动创建一个外部负载均衡器。 因此它同时具备 NodePort 和 ClusterIP 的能力。

    5. Headless Service

    ⚫ Headless Service

    将 clusterIP 设为 None，Service 就不再分配虚拟 IP， DNS 查询会直接返回后端 Pod 的 IP 列表，客户端可以直接连接到具体的 Pod。 常用于需要直连特定 Pod 的场景，尤其是与 StatefulSet 配合。 

    apiVersion: v1
kind: Service
metadata:
  name: mysql-headless
spec:
  clusterIP: None        # 关键：设为 None 即为 Headless Service
  selector:
    app: mysql
  ports:
  - port: 3306
    targetPort: 3306
    🔑 Headless Service 的用途

    • StatefulSet 配套：为每个 Pod 提供稳定的 DNS 名称（如 mysql-0.mysql-headless）
    • 客户端负载均衡：让客户端自己决定连哪个 Pod（如数据库主从）
    • 服务发现：获取所有 Pod 的 IP 列表

    6. kube-proxy 与负载均衡模式

    kube-proxy 是运行在每个节点上的网络代理，负责实现 Service 的负载均衡和转发规则。 它支持两种工作模式：

    📜 iptables 模式（默认）

    kube-proxy 通过配置 iptables 规则来实现流量转发。 当 Service 有多个后端 Pod 时，iptables 会用随机（轮询）方式选择一个后端。 优点是稳定可靠，缺点是规则数量随 Service 增多而膨胀，性能下降。

    ⚡ ipvs 模式（高性能）

    基于内核的 IPVS（IP Virtual Server）实现负载均衡， 支持多种调度算法（轮询、最小连接、源地址哈希等），性能远高于 iptables， 适合大规模集群。需要内核加载 ip_vs 模块。 

    # 查看当前 kube-proxy 模式
kubectl get configmap kube-proxy -n kube-system -o yaml | grep mode

# 常见模式值："iptables" 或 "ipvs"
    💡 模式选择建议

    小规模集群 iptables 完全够用；大规模集群（Service 数量上千）建议切换到 ipvs 模式以获得更好的性能。 切换方式是修改 kube-proxy 的 ConfigMap 或启动参数 --proxy-mode=ipvs。

    本章小结

    • Service 为一组 Pod 提供稳定的网络入口，通过 Label Selector 匹配后端 Pod
    • ClusterIP 是默认类型，仅集群内部可访问
    • NodePort 在每个节点开放端口（30000-32767），可通过节点 IP 访问
    • LoadBalancer 调用云厂商负载均衡器，分配外部 IP，适合公有云
    • Headless Service（clusterIP: None）不分配虚拟 IP，直接返回 Pod IP，常用于 StatefulSet
    • kube-proxy 支持 iptables（默认）和 ipvs（高性能）两种模式
