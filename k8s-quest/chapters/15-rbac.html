    RBAC 权限

    在生产环境的 Kubernetes 集群中，不可能让所有人都拥有集群管理员权限。如何精确控制"谁能对哪些资源执行什么操作"？这就是 RBAC（Role-Based Access Control，基于角色的访问控制）要解决的问题。RBAC 是 Kubernetes 安全体系的核心，本章我们将深入学习它的概念与实践。

    学习目标

    • 理解 RBAC 的核心概念：User、Group、ServiceAccount
    • 区分 Role 与 ClusterRole、RoleBinding 与 ClusterRoleBinding
    • 理解资源（Resources）与动词（Verbs）的含义
    • 掌握 ServiceAccount 的作用与使用方式
    • 理解最小权限原则并学会用 kubectl auth can-i 检查权限

    1. RBAC 概述

    RBAC（Role-Based Access Control）即基于角色的访问控制。它的核心思想是：不直接给用户分配权限，而是把权限赋予"角色"，再把角色绑定到"主体"上。这样主体就能通过角色获得对应的权限。

    RBAC 中涉及三类主体（Subject）：

    • User（用户）：人类用户，Kubernetes 本身不存储用户，通常由外部身份系统（如 LDAP、OIDC）管理。
    • Group（用户组）：一组用户的集合，方便批量授权。
    • ServiceAccount：Pod 内运行的应用程序使用的身份，由 Kubernetes 管理。

    2. Role 与 ClusterRole

    角色定义了"可以对哪些资源执行哪些操作"。根据作用范围不同，分为两种：

    👤 Role（命名空间级）

    角色定义在某个命名空间内，只能授权该命名空间内的资源操作。 例如：允许用户在 default 命名空间内读取 Pod。

    🌐 ClusterRole（集群级）

    角色定义在集群级别，可以授权集群范围的资源操作（如节点、命名空间）， 也可以授权所有命名空间内的资源。 

    # Role 示例：允许在 default 命名空间读取 Pod
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: default
  name: pod-reader
rules:
- apiGroups: [""]              # 核心 API 组（空字符串表示 core）
  resources: ["pods"]          # 资源类型
  verbs: ["get", "list", "watch"]  # 允许的操作

    3. RoleBinding 与 ClusterRoleBinding

    角色定义好了权限，但还需要把角色绑定到主体上才能生效。绑定同样分两种：

    🔗 RoleBinding

    将 Role 或 ClusterRole 绑定到某个命名空间内的主体。 如果绑定的是 ClusterRole，则权限仅限于 RoleBinding 所在的命名空间。

    🔗 ClusterRoleBinding

    将 ClusterRole 绑定到主体，权限在整个集群范围内生效。 

    # RoleBinding 示例：将 pod-reader 角色绑定到用户 alice
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-pods
  namespace: default
subjects:
- kind: User
  name: alice
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
    💡 用 ClusterRole + RoleBinding 复用权限

    一个常见的模式是：定义一个 ClusterRole（如 "view"）， 然后在每个命名空间用 RoleBinding 绑定它。这样同一个权限模板可以在多个命名空间复用， 而权限范围只限于各自的命名空间。

    4. 资源与动词

    RBAC 的规则由 资源（resources） 和 动词（verbs） 组成：

    常用资源

    • 核心资源（apiGroups: [""]）：pods、services、configmaps、secrets、persistentvolumeclaims 等
    • apps 组资源：deployments、statefulsets、replicasets、daemonsets 等
    • 集群级资源：nodes、namespaces、persistentvolumes、clusterroles 等

    常用动词

    • get：读取单个资源（如 kubectl get pod mypod）
    • list：列出资源（如 kubectl get pods）
    • watch：监听资源变更
    • create：创建资源
    • update：更新资源
    • patch：部分更新资源
    • delete：删除资源
    • *：所有动词

    5. ServiceAccount

    ServiceAccount 是 Pod 内运行的应用程序访问 Kubernetes API 的身份。与人类用户不同，ServiceAccount 由 Kubernetes 管理，存储为 Secret。

    # 创建 ServiceAccount
kubectl create serviceaccount my-app

# 将 ClusterRole "view" 绑定到该 ServiceAccount
kubectl create rolebinding my-app-view \
  --clusterrole=view \
  --serviceaccount=default:my-app \
  --namespace=default

    在 Pod 中使用 ServiceAccount：

    apiVersion: v1
kind: Pod
metadata:
  name: pod-with-sa
spec:
  serviceAccountName: my-app   # 指定使用的 ServiceAccount
  containers:
  - name: app
    image: nginx
    💡 默认 ServiceAccount

    每个命名空间都有一个名为 default 的 ServiceAccount。 如果 Pod 没有指定 serviceAccountName，会自动使用 default。 默认情况下 default ServiceAccount 没有任何额外权限。

    6. 最小权限原则与权限检查

    最小权限原则是安全的黄金法则：只授予主体完成工作所需的最少权限，不要多给。例如，一个只需要读取 Pod 的应用，就不应该赋予它删除 Pod 的权限。

    Kubernetes 提供了 kubectl auth can-i 命令来检查当前用户是否有权执行某个操作：

    # 检查当前用户是否能在 default 命名空间读取 Pod
kubectl auth can-i get pods --namespace=default

# 检查是否能创建 Deployment
kubectl auth can-i create deployments

# 以其他用户身份检查（需要模拟权限）
kubectl auth can-i delete pods --as=alice

# 检查 ServiceAccount 的权限
kubectl auth can-i list secrets \
  --as=system:serviceaccount:default:my-app
    💡 self-access-review

    kubectl auth can-i 底层调用的是 SelfSubjectAccessReview API， 可以在不实际执行操作的情况下判断是否有权限，非常适合调试权限问题。

    本章小结

    • RBAC 通过"角色（权限）+ 绑定（主体）"模型实现访问控制
    • 主体包括 User、Group、ServiceAccount 三类
    • Role/RoleBinding 是命名空间级，ClusterRole/ClusterRoleBinding 是集群级
    • 权限规则由 resources（资源）和 verbs（动词，如 get/list/create/delete）组成
    • ServiceAccount 是 Pod 内应用的身份，通过 serviceAccountName 关联
    • 遵循最小权限原则，用 kubectl auth can-i 检查权限
