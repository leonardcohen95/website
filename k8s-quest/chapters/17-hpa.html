    自动扩缩容

    业务流量有高峰有低谷，手动调整副本数既不及时也容易出错。Kubernetes 提供了强大的自动扩缩容能力：HPA 自动调整 Pod 副本数，VPA 自动调整 Pod 的资源请求，Cluster Autoscaler 自动增减节点。本章我们将系统学习这三种扩缩容机制，重点掌握 HPA 的配置与使用。

    学习目标

    • 理解 HPA、VPA、Cluster Autoscaler 三者的区别
    • 掌握 HPA 基于 CPU/内存指标的配置方法
    • 了解 HPA 基于自定义指标的扩缩容
    • 理解 minReplicas 与 maxReplicas 的作用
    • 了解 metrics-server 的作用与部署
    • 理解扩缩容冷却期的设计意义

    1. 三种扩缩容机制

    Kubernetes 的自动扩缩容分为三个维度：

    📈 HPA（Horizontal Pod Autoscaler）

    水平扩缩容：根据指标自动增加或减少 Pod 的副本数量。 适用于无状态应用，应对流量波动。

    📊 VPA（Vertical Pod Autoscaler）

    垂直扩缩容：自动调整单个 Pod 的资源请求（CPU/内存）。 适用于有状态应用或难以水平扩展的场景，需要重启 Pod 生效。

    🖥️ Cluster Autoscaler

    集群级扩缩容：当 Pod 因资源不足而无法调度（Pending）时，自动增加节点； 当节点资源空闲时，自动删除节点。

    💡 三者配合

    实际生产中，三者通常配合使用：HPA 调整副本数 → 如果节点资源不够 → Cluster Autoscaler 加节点； VPA 则单独优化单 Pod 的资源配置。

    2. HPA 核心概念

    HPA 是最常用的扩缩容机制。它周期性地检查目标指标（如 CPU 使用率），并与目标值比较，从而计算出期望的副本数。

    HPA 的关键配置项：

    • minReplicas：最小副本数，缩容下限
    • maxReplicas：最大副本数，扩容上限
    • targetCPUUtilizationPercentage：目标 CPU 使用率阈值

    HPA 基于的指标类型：

    • 资源指标：CPU、内存（需 metrics-server）
    • 自定义指标：QPS、队列长度等（需 Prometheus Adapter）
    • 外部指标：来自集群外部的指标

    3. metrics-server：指标数据来源

    HPA 默认依赖 metrics-server 来获取 Pod 的 CPU 和内存使用率。metrics-server 从 kubelet 收集指标并聚合，通过 Metrics API 暴露给 HPA 和 kubectl top 命令。

    # 部署 metrics-server
kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml

# 验证 metrics-server 正常工作
kubectl top nodes
kubectl top pods
    ⚠️ 没有 metrics-server 的后果

    如果集群中没有部署 metrics-server，kubectl top 和基于 CPU/内存的 HPA 都无法工作， HPA 会显示 "unknown" 指标。

    4. 配置 HPA

    以下是一个基于 CPU 使用率的 HPA 示例，目标是让 Deployment 的平均 CPU 使用率保持在 50% 左右，副本数在 2~10 之间自动调整：

    apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: nginx-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: nginx
  minReplicas: 2
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 50
    # 一行命令快速创建 HPA
kubectl autoscale deployment nginx --cpu-percent=50 --min=2 --max=10

# 查看 HPA 状态
kubectl get hpa
kubectl describe hpa nginx-hpa

    5. 冷却期（Cooldown Period）

    如果流量频繁波动，HPA 可能会频繁扩缩容（抖动），影响应用稳定性。为此，Kubernetes 引入了冷却期机制：

    • 扩容冷却：扩容后需要等待一段时间才能再次扩容
    • 缩容冷却：缩容后需要等待一段时间才能再次缩容（默认较长，防止过早缩容）
    ✅ 为什么需要冷却期？

    扩容的新 Pod 启动需要时间，指标可能有延迟。冷却期可以避免在指标尚未稳定时做出错误的扩缩容决策， 保证系统稳定。缩容冷却期通常比扩容更长，因为过早缩容可能导致服务能力不足。

    6. VPA 简介

    VPA 会根据 Pod 的历史资源使用情况，自动推荐或调整 Pod 的 resources.requests 和 limits。VPA 有三种模式：

    • Off：只给出推荐值，不自动应用
    • Initial：只在 Pod 创建时应用推荐值
    • Auto：自动调整，必要时重启 Pod
    ⚠️ HPA 与 VPA 不要同时使用

    HPA 和 VPA 不能同时针对同一个资源指标（如 CPU）进行扩缩，否则会互相冲突。 HPA 调整副本数，VPA 调整资源请求，二者作用于不同维度，应合理分工。

    本章小结

    • HPA 水平调整 Pod 副本数，VPA 垂直调整 Pod 资源请求，Cluster Autoscaler 调整节点数
    • HPA 可基于 CPU/内存或自定义指标进行扩缩容
    • minReplicas 和 maxReplicas 分别设定扩缩容的下限和上限
    • metrics-server 提供 HPA 所需的资源指标数据
    • 冷却期机制防止频繁扩缩容导致的系统抖动
    • HPA 与 VPA 不能同时针对同一资源指标工作
