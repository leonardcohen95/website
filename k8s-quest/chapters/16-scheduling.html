    调度与亲和性

    Pod 创建出来之后，到底该跑在哪个节点上？这就是 kube-scheduler 要解决的问题。本章我们会深入调度的核心流程，学习如何用 nodeSelector、亲和性、污点与容忍等机制，精细地控制 Pod 的节点分布，从而满足生产环境中各种"谁和谁在一起、谁不能和谁在一起"的部署需求。

    学习目标

    • 理解 kube-scheduler 的职责与调度三步流程
    • 掌握 nodeSelector 的基本用法
    • 掌握 nodeAffinity、podAffinity、podAntiAffinity 三种亲和性
    • 理解污点（Taint）与容忍（Toleration）的作用
    • 学会使用 cordon / drain 进行节点维护
    • 了解资源请求如何影响调度决策

    1. kube-scheduler 与调度流程

    kube-scheduler 是 Kubernetes 控制平面的核心组件之一，它的唯一职责就是：为新创建的、还没有绑定节点的 Pod 选择一个最合适的 Node。

    调度过程可以概括为三步：

    1. 过滤（Filtering）：遍历所有节点，剔除不满足 Pod 要求的节点（如资源不足、端口冲突、污点不匹配等）。
    2. 打分（Scoring）：对剩余的候选节点进行打分，选出得分最高的节点。
    3. 选择（Selecting）：将 Pod 绑定到得分最高的节点上。
    🎯 过滤 + 打分

    过滤阶段解决"能不能跑"的问题，打分阶段解决"跑在哪更好"的问题。 常见的打分策略包括：节点资源分配均衡、Pod 尽量分散到不同节点等。

    2. nodeSelector：最简单的节点选择

    nodeSelector 是最简单的节点定向调度方式。它通过匹配节点的标签（label）来决定 Pod 可以调度到哪些节点上。

    # 给节点打上标签
kubectl label nodes node-1 disktype=ssd

# Pod 中指定 nodeSelector
apiVersion: v1
kind: Pod
metadata:
  name: nginx
spec:
  nodeSelector:
    disktype: ssd
  containers:
  - name: nginx
    image: nginx
    💡 nodeSelector 的局限

    nodeSelector 只能做"精确匹配"，无法表达"或"、"不等于"等复杂条件。 要实现更灵活的调度规则，需要使用下面的亲和性机制。

    3. 亲和性（Affinity）

    亲和性是比 nodeSelector 更强大的调度机制，分为三类：

    🖥️ nodeAffinity（节点亲和性）

    控制 Pod 调度到具有特定标签的节点上。支持 required（硬要求，必须满足）和 preferred（软要求，尽量满足）两种模式。操作符包括 In、NotIn、Exists、DoesNotExist 等。

    🤝 podAffinity（Pod 亲和性）

    控制 Pod 与已运行的某些 Pod 调度到同一拓扑域（如同一个节点、同一个可用区）。 适用于需要通信频繁、希望降低网络延迟的场景。

    🚫 podAntiAffinity（Pod 反亲和性）

    控制 Pod 与已运行的某些 Pod 调度到不同拓扑域。 适用于高可用部署，避免多个副本集中在同一个节点上。 

    apiVersion: v1
kind: Pod
metadata:
  name: with-node-affinity
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - key: disktype
            operator: In
            values:
            - ssd
            - nvme
  containers:
  - name: app
    image: nginx

    4. 污点与容忍（Taint & Toleration）

    亲和性是从 Pod 的角度"主动选择"节点；而污点（Taint）则是从节点的角度"排斥"Pod。

    给节点打上污点后，没有对应容忍的 Pod 不会被调度到该节点上。Pod 通过声明容忍（Toleration）来允许自己在有污点的节点上运行。

    # 给节点添加污点（effect 为 NoSchedule）
kubectl taint nodes node-1 key=value:NoSchedule

# Pod 中声明容忍
apiVersion: v1
kind: Pod
metadata:
  name: nginx
spec:
  tolerations:
  - key: "key"
    operator: "Equal"
    value: "value"
    effect: "NoSchedule"
  containers:
  - name: nginx
    image: nginx

    污点的 effect 有三种：

    • NoSchedule：不调度新 Pod，但不驱逐已运行的 Pod
    • PreferNoSchedule：尽量不调度，但不强制
    • NoExecute：不调度新 Pod，并驱逐不匹配的已运行 Pod
    ⚠️ 控制平面节点的污点

    K8s 控制平面节点默认带有 node-role.kubernetes.io/control-plane:NoSchedule 污点， 普通 Pod 默认不会调度到控制平面节点上，这是出于安全与稳定性的考虑。

    5. cordon 与 drain：节点维护

    当需要对节点进行维护（如升级内核、更换硬件）时，可以使用以下命令：

    # 标记节点为不可调度（cordon），新 Pod 不会再调度过来
kubectl cordon node-1

# 排空节点（drain），驱逐该节点上的所有 Pod
kubectl drain node-1 --ignore-daemonsets --delete-emptydir-data

# 维护完成后，恢复节点可调度
kubectl uncordon node-1
    ✅ cordon vs drain

    cordon 只是让节点停止接收新 Pod，已有 Pod 继续运行；
    drain 则会先 cordon，再驱逐已有 Pod，让它们重新调度到其他节点。

    6. 资源请求对调度的影响

    Pod 的 resources.requests 是调度器的重要依据。调度器在过滤阶段会检查节点剩余可分配资源是否满足 Pod 的 requests。如果 Pod 请求的 CPU/内存超出了任何节点的剩余容量，Pod 就会一直处于 Pending 状态。

    apiVersion: v1
kind: Pod
metadata:
  name: resource-demo
spec:
  containers:
  - name: app
    image: nginx
    resources:
      requests:
        cpu: "500m"
        memory: "256Mi"
      limits:
        cpu: "1000m"
        memory: "512Mi"

    合理设置 requests 不仅影响调度，还影响节点的资源利用率。设置过大浪费资源，设置过小可能导致节点过载。

    本章小结

    • kube-scheduler 负责为 Pod 选择节点，流程为 过滤 → 打分 → 选择
    • nodeSelector 通过标签精确匹配节点，简单但不够灵活
    • 亲和性分 nodeAffinity、podAffinity、podAntiAffinity，支持硬/软要求
    • 污点（Taint）让节点排斥 Pod，容忍（Toleration）让 Pod 允许在带污点节点运行
    • cordon 标记节点不可调度，drain 排空节点用于维护
    • Pod 的 resources.requests 直接影响调度能否成功
