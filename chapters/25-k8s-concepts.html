    第 25 章 K8s 专题 约 40 分钟

    K8s 概念与架构

    本章是 K8s 深度专题的开篇。我们将从「为什么需要 K8s」讲起，把运维演进路径 理清楚；再系统拆解 K8s 的核心概念（Pod、Deployment、Service 等）和 Master/Node 架构；最后带你用 kubectl 部署第一个应用，理解 K8s 的灵魂—— 声明式模型。学完你能用大白话讲清楚 K8s 是什么、怎么工作，从容应对 「说说 K8s 架构」「K8s 和 Docker 啥关系」这类高频面试题。

    学习目标

    • 能说清运维从手工到编排的演进路径，以及 K8s 解决了什么痛点
    • 掌握 Pod、Deployment、Service、Namespace、ConfigMap 等核心概念
    • 理解 Master 控制平面与 Node 节点各组件的职责
    • 能用 kubectl 完成部署、查看、扩缩容、删除等基本操作
    • 深刻理解声明式模型与 reconciliation loop 的工作原理
    • 能回答「K8s 架构」「K8s 与 Docker 关系」「声明式模型」等面试题

    1. 为什么需要 K8s

    理解一个工具最好的方式是看它解决了什么问题。运维管理应用的方式经历了几次 演进，每次演进都是被上一阶段的痛点逼出来的。

    1.1 演进路径

    • 手工部署：SSH 登录服务器，下载包、改配置、起进程。一台台搞，慢、易错、不可复现。
    • 脚本自动化：写 Shell/Ansible 脚本批量执行。解决了「一台台」的问题，但机器坏了要手动换，进程挂了要手动拉起。
    • Docker 容器化：把应用和依赖打成镜像，docker run 一键起。解决了环境一致性问题，但单机管理几十个容器就手忙脚乱。
    • 容器编排：多机管理、自动调度、故障自愈、滚动升级、服务发现——这就是 K8s 干的事。
    Docker 解决了什么，又留下了什么

    Docker 让「我的机器上能跑」变成了「镜像在哪都能跑」，这是巨大进步。 但生产环境里你会面临：一台机器挂了上面 20 个容器怎么办？灰度发布怎么做？ 流量怎么自动转发到新容器？这些问题 Docker 自身不解决，需要编排系统。

    1.2 编排系统的痛点

    一个合格的容器编排系统要解决这些问题：

    • 调度：容器放哪台机器？资源够不够？要不要分散避免单点？
    • 自愈：容器挂了自动重启，机器挂了把容器迁到别的机器。
    • 扩缩容：流量来了自动加副本，流量下去自动减。
    • 服务发现：容器 IP 一直在变，调用方怎么找到它？
    • 滚动升级与回滚：不中断业务的情况下更新版本，出问题一键回滚。
    • 配置与密钥管理：不同环境不同配置，密码不能写死在镜像里。

    2. K8s 是什么

    Kubernetes（简称 K8s，因为 K 和 s 之间有 8 个字母）是 Google 基于 Borg 系统 的经验开源的容器编排平台，现由 CNCF 维护，是容器编排的事实标准。

    一句话定义：K8s 是一个用于自动部署、扩缩容和管理容器化应用的开源平台。

    与同类工具的一句话对比

    Docker Swarm：Docker 原生，简单轻量，但功能少、生态弱，适合小规模。 Mesos + Marathon：偏资源调度底层，支持多种负载，但复杂度高、社区萎缩。 K8s：功能最全、生态最丰富、社区最活跃，学习曲线陡但回报高，是行业标准。

    3. 核心概念速览

    先建立概念地图，后面章节会逐个深入。这里每个概念配一个最简 YAML，让你有 直观印象，不用死记。

    Pod —— K8s 最小调度单元

    Pod 是 K8s 调度的最小单位，一个 Pod 里可以跑多个容器（共享网络和存储）。 通常一个 Pod 一个容器，多容器场景如 Sidecar。Pod 是临时的，IP 会变， 所以不要直接用 Pod IP 访问，要用 Service。 

    # 最简 Pod
apiVersion: v1
kind: Pod
metadata:
  name: nginx-pod
  labels:
    app: nginx           # 标签，Service 靠它选中 Pod
spec:
  containers:
    - name: nginx
      image: nginx:1.25  # 用哪个镜像
      ports:
        - containerPort: 80
    Deployment —— 管理 Pod 副本

    生产环境不会直接创建 Pod，而是用 Deployment 描述「我要 3 个 nginx 副本」。 Deployment 帮你保证副本数、做滚动升级和回滚。它是「Pod 的管理者」。 

    apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-deploy
spec:
  replicas: 3                    # 期望 3 个副本
  selector:
    matchLabels:
      app: web                   # 选中 app=web 的 Pod
  template:                      # Pod 模板
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: web
          image: nginx:1.25
    Service —— 稳定的访问入口

    Pod IP 会变，Service 给一组 Pod 提供一个稳定的虚拟 IP（ClusterIP）和 DNS 名， 并做负载均衡。ClusterIP 集群内访问，NodePort 暴露到节点端口，LoadBalancer 走云厂商 ELB。 

    apiVersion: v1
kind: Service
metadata:
  name: web-svc
spec:
  type: ClusterIP                # 集群内访问
  selector:
    app: web                     # 选中所有 app=web 的 Pod
  ports:
    - port: 80                   # Service 端口
      targetPort: 80             # 转发到 Pod 的 80 端口
    Namespace —— 逻辑隔离

    Namespace 是集群内的逻辑分区，用于多团队/多环境隔离。不同 Namespace 的 资源名可以重复，可以做资源配额（ResourceQuota）限制。默认有 default、 kube-system（系统组件）等。 

    # 创建 Namespace
apiVersion: v1
kind: Namespace
metadata:
  name: dev

# 使用时指定 namespace
kubectl get pods -n dev
    ConfigMap —— 配置管理

    ConfigMap 存非敏感配置，解耦镜像和配置（同一镜像跑不同环境靠它）。 敏感信息用 Secret（注意 Secret 默认只是 base64 编码，不是加密）。 

    apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  app.env: "production"          # 配置项
  log.level: "info"
  nginx.conf: |                  # 也可以存整个配置文件
    server {
      listen 80;
    }
    概念关系一图懂

    Deployment（管理者）→ 创建多个 Pod（实际跑应用）→ Service（访问入口）通过 selector 选中这些 Pod → 配置从 ConfigMap 注入 → 全部跑在某个 Namespace 里。

    4. 架构详解

    K8s 是典型的主从架构：Master 负责「大脑」（决策），Node 负责「手脚」 （干活）。理解架构是回答面试题「说说 K8s 架构」的基础。

    4.1 Master 控制平面

    Master 也叫控制平面（Control Plane），是集群的大脑，做全局决策和响应事件。

    kube-apiserver

    所有操作的唯一入口，提供 REST API。kubectl、kubelet、 scheduler 都通过它读写集群状态。它做认证、授权、准入控制，再写入 etcd。 可以多副本部署做高可用。

    etcd

    分布式 KV 数据库，是集群状态的唯一持久化存储。所有资源对象 （Pod、Service、Secret…）都存在这里。它是 K8s 的「大脑记忆」，一旦数据丢失 集群就完了，所以必须做备份。生产通常 3 或 5 节点组成集群保证高可用。

    kube-scheduler

    调度器：当有新 Pod 待调度时，根据资源请求、节点选择器、亲和性、 污点容忍等规则，挑一个合适的 Node。只负责「决定放哪」，不负责「实际创建」。

    kube-controller-manager

    控制器的大脑，运行一堆控制器，每个负责一种资源的协调： 副本控制器保证 Deployment 副本数、节点控制器监控节点健康、端点控制器 维护 Service 的 endpoints 等。本质都是 reconciliation loop。

    4.2 Node 节点

    Node 是干活的机器（物理机或虚拟机），跑实际业务的 Pod。

    kubelet

    每个节点上的代理人，与 apiserver 通信。它看着本节点的 Pod 列表， 负责让 Pod 真正起来：调用容器运行时拉镜像、起容器，并上报节点状态和 Pod 状态。 Pod 不健康时按重启策略重启容器。

    kube-proxy

    每个节点上的网络代理，负责维护 Service 的网络规则（默认 iptables， 也可配 IPVS）。它让访问 Service IP 的流量能被负载均衡到后端某个 Pod。

    container runtime

    容器运行时：真正跑容器的软件。K8s 通过 CRI（容器运行时接口） 解耦，支持 containerd、CRI-O、Docker（新版已废弃 dockershim，推荐 containerd）。

    apiserver 是唯一入口

    注意所有组件都不直接读写 etcd，只有 apiserver 直接操作 etcd。 其他组件（scheduler、controller-manager、kubelet）都通过 apiserver 通信。 这是 K8s 架构的关键设计——保证状态一致性和访问控制。

    4.3 声明式 vs 命令式

    这是 K8s 区别于传统运维的根本范式，也是面试高频点。

    • 命令式：「帮我起 3 个 nginx 容器」。你告诉系统做什么。系统照做，但不关心后续状态。容器挂了你得再喊一次。
    • 声明式：「我要 3 个 nginx 副本一直存在」。你告诉系统要什么状态。系统持续监控，发现副本变少就补上，变多就删掉。
    声明式 vs 命令式 对比

    命令式（如 docker run、Ansible 任务）：关注动作，执行完就结束， 一次性的，状态漂移要人工修复。
    声明式（如 kubectl apply YAML）：关注期望状态，系统持续收敛到 期望状态，自愈、幂等、可重入。改了就 apply 新 YAML，不用关心怎么从旧到新。

    5. kubectl 初体验

    kubectl 是操作 K8s 的命令行工具，所有运维操作都从它开始。下面走一遍完整流程。 （假设你已有集群，下一章教你怎么搭。）

    5.1 安装 kubectl

    # Linux（x86_64）
curl -LO "https://dl.k8s.io/release/$(curl -L -s https://dl.k8s.io/release/stable.txt)/bin/linux/amd64/kubectl"
sudo install -o root -g root -m 0755 kubectl /usr/local/bin/kubectl
kubectl version --client    # 验证安装

# macOS（用 brew）
brew install kubectl

# 配置自动补全（bash）
echo 'source <(kubectl completion bash)' >> ~/.bashrc

    5.2 验证连接

    # 查看集群节点
kubectl get nodes
# NAME         STATUS   ROLES           AGE   VERSION
# minikube     Ready    control-plane   10d   v1.29.0

# 集群信息
kubectl cluster-info
# 看控制平面跑在哪、kube-dns 跑在哪

# 查看 kubectl 配置（连接信息在 ~/.kube/config）
kubectl config view

    5.3 部署第一个应用

    # 命令式快速创建一个 Deployment（学习用，生产写 YAML）
kubectl create deployment nginx --image=nginx:1.25
# deployment.apps/nginx created

# 查看 Pod（应用正在拉镜像、起容器）
kubectl get pods
# NAME                     READY   STATUS    RESTARTS   AGE
# nginx-xxxx-yyyy          1/1     Running   0          30s

# 查看 Deployment
kubectl get deploy
# NAME    READY   UP-TO-DATE   AVAILABLE   AGE
# nginx   1/1     1            1           35s

    5.4 暴露服务

    # 用 NodePort 把 nginx 暴露到节点端口
kubectl expose deployment nginx --port=80 --type=NodePort
# service/nginx exposed

# 查看 Service（自动分配了一个 30000+ 的端口）
kubectl get svc
# NAME         TYPE        CLUSTER-IP      EXTERNAL-IP   PORT(S)        AGE
# nginx        NodePort    10.96.123.45    <none>       80:31234/TCP   5s

# 访问测试（节点IP:NodePort）
curl http://节点IP:31234

    5.5 扩缩容

    # 扩容到 5 个副本
kubectl scale deployment nginx --replicas=5
# deployment.apps/nginx scaled

kubectl get pods    # 会看到 5 个 Pod
# 持续观察
kubectl get pods -w    # -w 是 watch，实时刷新

# 缩容到 2 个
kubectl scale deployment nginx --replicas=2

    5.6 删除应用

    # 删除 Service
kubectl delete svc nginx

# 删除 Deployment（会连带删除它管理的 Pod）
kubectl delete deployment nginx

# 一键查看所有资源是否清理干净
kubectl get all
    kubectl 三种操作模式

    ①命令式（imperative）：kubectl create/scale/delete，快但不可复现，适合临时操作； ②声明式（declarative）：kubectl apply -f xxx.yaml，可版本化、可复现，生产推荐； ③查看类：kubectl get/describe/logs/exec，只读不影响状态。

    6. 声明式模型深入

    声明式模型是 K8s 的灵魂。深刻理解它，后面学所有资源都事半功倍。

    6.1 期望状态 vs 实际状态

    K8s 里每个资源都描述一个期望状态（spec，你写在 YAML 里的）， 系统持续观测实际状态（status，集群里真实发生的），并不断让 实际状态收敛到期望状态。这个过程叫 reconciliation（协调）， 执行它的循环叫 reconciliation loop（协调循环）。

    生活类比：恒温空调

    把 K8s 想象成恒温空调：你在遥控器上设 26℃（期望状态）， 空调里的温度传感器读室温（实际状态），控制器不停比较两者—— 实际高于 26℃ 就制冷，低于就停机。你只管「我要 26℃」，不用管空调怎么开。 K8s 同理：你写「我要 3 个 nginx 副本」，它自己保证副本数永远是 3。

    6.2 reconciliation loop 怎么工作

    以 Deployment 为例，整个协调流程：

    1. 你 kubectl apply 一个 replicas=3 的 Deployment，写入 etcd。
    2. Deployment 控制器发现期望 3 个副本，创建 ReplicaSet。
    3. ReplicaSet 控制器发现期望 3 个 Pod，实际 0 个，创建 3 个 Pod。
    4. scheduler 给每个 Pod 选一个 Node，写到 Pod 的 spec.nodeName。
    5. 对应 Node 的 kubelet 看到有分配给自己的 Pod，调容器运行时起容器。
    6. Pod 挂了一个，实际副本变 2，ReplicaSet 控制器发现差异，再创建 1 个。

    每一层都是独立的 reconciliation loop，互不直接调用，只通过 etcd 间接通信。 这种设计让系统解耦、自愈、最终一致。

    apply 的幂等性

    声明式的好处是幂等：同一个 YAML 你 apply 100 次结果都一样 （只关心最终状态）。而命令式 docker run 跑 100 次会起 100 个容器。 这也是为什么生产都用 kubectl apply -f 而不是 kubectl create。

    7. 面试角度

    下面三个是 K8s 入门面试必考题，给出参考答案要点。

    7.1 「说说 K8s 的架构」

    参考答案要点

    K8s 是主从架构，分控制平面（Master）和工作节点（Node）。 控制平面四大组件：① kube-apiserver 是所有操作唯一入口，做认证授权； ② etcd 是分布式 KV 存储，存集群所有状态；③ scheduler 负责把 Pod 调度到合适节点；④ controller-manager 运行各种控制器， 通过 reconciliation loop 维持期望状态。Node 上三组件：kubelet 管本节点 Pod、 kube-proxy 维护 Service 网络规则、container runtime 跑容器。所有组件只通过 apiserver 读写 etcd，不直接访问。

    7.2 「K8s 和 Docker 的关系」

    参考答案要点

    两者不是替代关系，而是不同层级。Docker 是容器运行时，解决 「应用打包和环境一致性」；K8s 是容器编排平台，解决「多机管理、调度、自愈、 服务发现」。K8s 本身不跑容器，它调用容器运行时（containerd/CRI-O）来跑。 早期 K8s 内置 dockershim 支持 Docker，1.24 起移除，现在推荐直接用 containerd。 一句话：Docker 是「造容器」，K8s 是「管容器」。

    7.3 「什么是声明式模型」

    参考答案要点

    声明式是描述「要什么状态」而非「做什么动作」。你写 YAML 描述期望 （如 replicas: 3），K8s 通过 reconciliation loop 持续让实际状态收敛到期望状态： 副本少了补、多了删、容器挂了重启、节点挂了迁移。好处是：① 自愈， 状态漂移自动修复；② 幂等，apply 多次结果一致；③ 可版本化， YAML 入 Git 可回溯。对比命令式（如 docker run、Ansible）是一次性动作，状态变化 要人工干预。K8s 几乎所有资源（Deployment、Service…）都是声明式的。

    本章小结

    • 运维演进：手工 → 脚本 → Docker → 编排。K8s 解决多机调度、自愈、扩缩容、服务发现等编排痛点。
    • 核心概念：Pod 是最小调度单元，Deployment 管副本，Service 提供稳定入口，Namespace 做逻辑隔离，ConfigMap 管配置。
    • Master 控制平面四组件：apiserver（唯一入口）、etcd（状态存储）、scheduler（调度）、controller-manager（控制器大脑）。
    • Node 三组件：kubelet（管 Pod）、kube-proxy（管网络）、container runtime（跑容器）。所有组件只通过 apiserver 访问 etcd。
    • 声明式模型：描述期望状态，reconciliation loop 持续收敛实际状态，带来自愈、幂等、可版本化。
    • kubectl 三类操作：命令式（create/scale）快但不可复现、声明式（apply）生产推荐、查看类（get/describe/logs）只读。
    • K8s 与 Docker 是不同层级：Docker 造容器，K8s 管容器，1.24 起推荐 containerd 替代 Docker 作为运行时。
    • 面试高频：架构（主从+四组件+三组件）、声明式模型、K8s 与 Docker 关系，要能用大白话讲清。
