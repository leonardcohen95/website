    Kubernetes 容器编排

    K8s 是容器编排的事实标准。本章从架构讲起，覆盖核心资源（Pod、Service、Deployment）、 集群搭建、故障排查和性能调优。学完你能独立部署应用到 K8s， 并能回答面试中「Pod 起不来怎么办」「Service 不通怎么排查」等高频问题。

    学习目标

    • 理解 K8s 整体架构和核心组件职责
    • 掌握 Pod、Service、Deployment、ConfigMap 等核心资源
    • 能编写 YAML 部署一个带服务暴露的应用
    • 掌握 Pod 启动失败、Service 不通等常见故障排查
    • 了解 K8s 性能调优手段

    Master 组件

    apiserver：所有请求的入口，REST API，操作 etcd。 etcd：分布式 KV 存储，保存集群所有状态。 scheduler：把 Pod 调度到合适的 Node。 controller-manager：维护集群期望状态（副本数、端点等）。

    Node 组件

    kubelet：管理本节点的 Pod，和容器运行时（containerd）交互。 kube-proxy：维护 Service 的网络规则（iptables/IPVS）。 container runtime：真正跑容器的，如 containerd、CRI-O。

    2. 核心资源

    2.1 Pod —— 最小调度单元

    Pod 是 K8s 中最小的调度单位，一个 Pod 可以包含多个容器，它们共享网络和存储。

    apiVersion: v1
kind: Pod
metadata:
  name: nginx-pod
  labels:
    app: nginx
spec:
  containers:
    - name: nginx
      image: nginx:1.25
      ports:
        - containerPort: 80
      resources:
        requests:          # 最小资源保障
          cpu: 100m
          memory: 128Mi
        limits:            # 最大资源限制
          cpu: 500m
          memory: 256Mi
      readinessProbe:      # 就绪探针，通过才接流量
        httpGet:
          path: /
          port: 80
        initialDelaySeconds: 5
      livenessProbe:       # 存活探针，失败就重启容器
        httpGet:
          path: /
          port: 80
        periodSeconds: 10
    探针很重要

    livenessProbe：容器是否活着，失败就重启（解决死锁、hang 住）。 readinessProbe：容器是否就绪，失败就从 Service 摘流量（解决启动慢、过载）。 没有探针，K8s 不知道应用真实状态，流量可能打到还没启动完的 Pod。

    2.2 Deployment —— 管理 Pod 副本

    实际生产不会直接创建 Pod，而是用 Deployment 管理副本、滚动升级、回滚。

    apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-deploy
spec:
  replicas: 3                    # 期望 3 个副本
  selector:
    matchLabels:
      app: web
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1                # 升级时最多多 1 个
      maxUnavailable: 0          # 升级时最多少 0 个（保证不中断）
  template:                      # Pod 模板
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: web
          image: nginx:1.25
          ports:
            - containerPort: 80

    2.3 Service —— 服务发现与负载均衡

    Pod 是会漂移的，IP 会变。Service 给一组 Pod 提供稳定的访问入口。

    apiVersion: v1
kind: Service
metadata:
  name: web-svc
spec:
  type: ClusterIP          # 默认，集群内访问；NodePort 暴露到节点端口；LoadBalancer 云厂商负载均衡
  selector:
    app: web               # 选中所有 app=web 的 Pod
  ports:
    - port: 80             # Service 端口
      targetPort: 80       # Pod 端口

    2.4 ConfigMap & Secret —— 配置管理

    # ConfigMap：非敏感配置
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  app.env: "production"
  log.level: "info"

# Secret：敏感信息（base64 编码，不是加密！）
apiVersion: v1
kind: Secret
metadata:
  name: db-secret
type: Opaque
data:
  password: c2VjcmV0cGFzcw==   # echo -n 'secretpass' | base64

# 在 Pod 中使用
spec:
  containers:
    - name: app
      image: myapp
      env:
        - name: APP_ENV
          valueFrom:
            configMapKeyRef:
              name: app-config
              key: app.env
        - name: DB_PASSWORD
          valueFrom:
            secretKeyRef:
              name: db-secret
              key: password
    Secret 不是加密

    K8s 的 Secret 默认只是 base64 编码，不是加密。生产环境应开启 etcd 静态加密，或使用外部密钥管理服务（如 Vault、云厂商 KMS）。

    5. 故障排查

    5.1 Pod 起不来

    # 第一步：看 Pod 状态
kubectl get pods
# Pending  → 调度失败，看 describe 的 Events
# ContainerCreating → 镜像拉取或挂载失败
# CrashLoopBackOff → 容器启动后崩溃

# 第二步：看 Events
kubectl describe pod 名字
# 关注底部 Events 部分，常见原因：
#   FailedScheduling → 资源不足/污点/节点选择器不匹配
#   ErrImagePull     → 镜像地址错或没权限
#   ImagePullBackOff → 同上
#   CrashLoopBackOff → 应用启动失败，看 logs

# 第三步：看日志
kubectl logs 名字
kubectl logs --previous 名字   # 容器重启过，看上一次的日志
    Pod 状态速查
    • Pending：还没调度，资源不足或镜像拉取中
    • ContainerCreating：正在创建容器
    • Running：正常运行
    • CrashLoopBackOff：容器反复崩溃重启
    • ImagePullBackOff：镜像拉取失败
    • Error：启动出错

    5.2 Service 不通

    # 1. 确认 Service 选中了 Pod
kubectl get endpoints web-svc
# 如果是空的，说明 selector 没匹配到 Pod 的 label

# 2. 确认 Pod 本身能访问
kubectl exec -it 另一个pod -- curl http://podIP:80

# 3. 确认 Service 的 ClusterIP 能通
kubectl exec -it 另一个pod -- curl http://web-svc:80

# 4. 确认 kube-proxy 正常
kubectl get pods -n kube-system | grep kube-proxy
# 看 iptables 规则
iptables -t nat -L -n | grep web-svc

# 5. NodePort 不通，检查节点安全组/防火墙是否放行端口

    5.3 节点 NotReady

    # 看节点状态和原因
kubectl describe node 节点名
# 关注 Conditions：MemoryPressure/DiskPressure/PIDPressure

# 登录节点排查
systemctl status kubelet
journalctl -u kubelet -f        # 看 kubelet 日志
crictl ps                       # 看运行的容器
df -h /var/lib/kubelet          # 磁盘空间
free -h                         # 内存

    6. 性能调优

    • 资源 requests/limits：每个 Pod 设好，避免资源争抢和 OOM。
    • kube-proxy 用 IPVS：Service 多时比 iptables 性能好。
    • etcd 用 SSD：etcd 延迟直接影响整个集群响应。
    • 限制每节点 Pod 数：--max-pods 避免单节点过载。
    • HPA 自动扩缩容：根据 CPU/内存/自定义指标自动调整副本数。
    • 污点与亲和：把高 IO 应用调度到高性能节点。

    本章小结

    • K8s 分 Master（apiserver/etcd/scheduler/controller）和 Node（kubelet/kube-proxy/runtime）。
    • Pod 是最小调度单元，Deployment 管副本和滚动升级，Service 提供稳定入口。
    • 探针（liveness/readiness）让 K8s 感知应用真实状态，必须配置。
    • Pod 起不来：看状态 → describe 看 Events → logs 看日志。
    • Service 不通：先看 endpoints 是否为空，再逐层排查。
    • Secret 只是 base64，生产要开 etcd 加密或用外部 KMS。
