    1. 监控体系搭建

    K8s 监控的事实标准是 Prometheus + Grafana。 Prometheus 负责采集和存储时序指标，Grafana 负责可视化看板，Alertmanager 负责告警分发。

    监控架构一图流
       ┌──────────────────────────────────────────────────────────┐
   │                      K8s 集群                              │
   │                                                            │
   │  ┌────────────┐  ┌────────────┐  ┌────────────┐           │
   │  │ kubelet    │  │ API Server │  │ etcd       │           │
   │  │ /metrics   │  │ /metrics   │  │ /metrics   │           │
   │  └─────┬──────┘  └─────┬──────┘  └─────┬──────┘           │
   │        │               │               │                    │
   │  ┌─────┴───────────────┴───────────────┴──────┐           │
   │  │  Exporter / ServiceMonitor（指标暴露）       │           │
   │  └────────────────────┬────────────────────────┘           │
   └───────────────────────┼────────────────────────────────────┘
                           │ 抓取（pull）
                           ▼
              ┌────────────────────────┐
              │      Prometheus        │  ← 时序数据库
              │  (采集 + 存储 + 查询)   │

                 │                  │
        ┌────────┴───────┐   ┌──────┴─────────┐

    1.1 一键安装 kube-prometheus-stack

    社区维护的 kube-prometheus-stack 把 Prometheus、Grafana、Alertmanager、 NodeExporter、kube-state-metrics 全打包，一条命令装好整套监控。

    helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm repo update

helm install monitoring prometheus-community/kube-prometheus-stack \
  -n monitoring --create-namespace \
  --set grafana.adminPassword='Grafana@2024' \
  --set prometheus.service.type=NodePort \
  --set grafana.service.type=NodePort

# 查看
kubectl get pods -n monitoring
#  grafana-xxx                       2/2 Running
#  prometheus-monitoring-prometheus  2/2 Running
#  alertmanager-xxx                  2/2 Running
#  monitoring-prometheus-node-exporter-xxx  (DaemonSet，每节点一个)

# 访问 Grafana（拿到 NodePort 端口）
kubectl get svc -n monitoring grafana -o jsonpath='{.spec.ports[0].nodePort}'
# 浏览器访问 http://节点IP:上述端口，账号 admin / 上面设的密码

    1.2 关键监控指标

    • 节点资源：CPU/内存使用率、磁盘剩余、inode、网络收发。 node:node_memory_MemAvailable_bytes、node:node_cpu_utilisation。
    • Pod 状态：kube-state-metrics 暴露 Pod 的 Phase、 重启次数、OOM 计数。关注 kube_pod_container_status_restarts_total。
    • API Server 延迟：apiserver_request_duration_seconds， P99 延迟 > 1s 就要查控制面负载。
    • etcd 性能：etcd_disk_wal_fsync_duration_seconds、 etcd_server_proposals_failed_total，etcd 慢会拖垮整个集群。
    • 容器资源：container_cpu_usage_seconds_total、 container_memory_working_set_bytes（注意是 working_set，接近 OOM 判定值）。
    metrics-server 和 Prometheus 不是一回事

    metrics-server：轻量，只采集实时 CPU/内存用于 kubectl top 和 HPA 弹性伸缩，不存历史。 Prometheus：完整时序数据库，存历史、做查询、做告警看板。 生产两者都要：metrics-server 喂 HPA，Prometheus 喂监控告警。

    1.3 告警规则配置示例

    # PrometheusRule（kube-prometheus-stack 自动识别）
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: my-alerts
  namespace: monitoring
spec:
  groups:
    - name: k8s-alerts
      rules:
        - alert: NodeHighCpuUsage
          expr: node:node_cpu_utilisation:ratio_avg > 0.85
          for: 5m                  # 持续 5 分钟才告警，避免抖动
          labels:
            severity: warning
          annotations:
            summary: "节点 {{ $labels.node }} CPU 使用率过高"
            description: "当前 {{ $value | humanizePercentage }}，超过 85%"

        - alert: PodCrashLooping
          expr: rate(kube_pod_container_status_restarts_total[15m]) > 0
          for: 5m
          labels:
            severity: critical
          annotations:
            summary: "Pod {{ $labels.pod }} 反复重启"

        - alert: EtcdHighFsyncDuration
          expr: histogram_quantile(0.99, rate(etcd_disk_wal_fsync_duration_seconds_bucket[5m])) > 0.01
          for: 5m
          labels:
            severity: critical
          annotations:
            summary: "etcd 写盘延迟过高，可能影响整个集群"

    2. 日志收集

    K8s 容器日志默认写到 stdout/stderr，由容器运行时落到 /var/log/containers/。三种主流收集方案：

    • 方案一：EFK（Elasticsearch + Fluentd/Fluent Bit + Kibana）。 功能最全，支持全文检索、复杂查询，适合日志量大、需深度检索的场景。 缺点是 Elasticsearch 重，资源消耗高。
    • 方案二：Loki + Promtail。Prometheus 团队出品，标签化索引而非全文索引， 轻量、和 Grafana 原生集成，适合中小规模、日志查询以标签筛选为主。
    • 方案三：直接 kubectl logs。开发调试用， 不适合生产长期留存和检索。
    # 开发调试：看实时日志
kubectl logs -f myapp-pod -c myapp
kubectl logs --previous myapp-pod     # 看上次崩溃前的日志
kubectl logs -l app=web --tail=100    # 按 label 看多个 Pod

# Loki 安装（Helm，和 Grafana 同生态）
helm repo add grafana https://grafana.github.io/helm-charts
helm install loki grafana/loki-stack -n logging --create-namespace
#  Grafana 里直接添加 Loki 数据源，用 LogQL 查询
    日志方案选型建议

    中小规模、追求轻量 → Loki + Promtail，资源省、和 Grafana 一体化。 日志量大、需复杂全文检索和审计 → EFK，功能全但要养一套 ES 集群。 无论哪种，应用日志必须输出到 stdout/stderr，别写本地文件（Pod 漂移后日志就没了）。

    3. 故障排查手册（核心实战）

    这是生产运维最值钱的能力。下面按五大场景给出排查流程、命令和输出分析。

    3.1 Pod 排障流程

    # 第一步：看 Pod 状态（看 STATUS 列）
kubectl get pods -n myapp
#  NAME      READY  STATUS              RESTARTS
#  web-0     1/1   Running              0
#  web-1     0/1   CrashLoopBackOff     6
#  api-0     0/1   Pending              0
#  api-1     0/1   ImagePullBackOff     0

# 第二步：不同状态走不同分支
#  Pending        → 调度失败，看 describe 的 Events
#  ContainerCreating → 镜像拉取/挂载失败，看 Events
#  ImagePullBackOff → 镜像地址错或仓库没权限
#  CrashLoopBackOff → 容器启动后崩溃，看 logs
#  ErrImagePull    → 镜像名拼写错或不存在

# 第三步：describe 看 Events（重点看底部 Events 部分）
kubectl describe pod web-1 -n myapp
#  Events:
#    Warning  FailedScheduling  3m  default-scheduler
#      0/3 nodes are available: 3 Insufficient memory.
#      ↑ 资源不足，调小 requests 或加节点
#    Normal   Pulling  2m  kubelet  Pulling "nginx:v1"
#    Warning  Failed   2m  kubelet  Failed to pull image "nginx:v1":
#      manifest unknown   ↑ 镜像 tag 不存在

# 第四步：看日志（容器已启动但崩溃）
kubectl logs web-1 -n myapp
kubectl logs --previous web-1 -n myapp    # 看上一次（崩溃前）的日志

# 第五步：进容器内部排查（容器还活着时）
kubectl exec -it web-1 -n myapp -- /bin/sh
#  进去看：env、cat 配置文件、telnet/nc 测下游依赖是否通
    Pod 排障命令清单
    • kubectl get pods → 看 STATUS 决定下一步
    • kubectl describe pod 名字 → 看 Events（调度、拉镜像、挂载错误都在这）
    • kubectl logs 名字 → 看当前日志
    • kubectl logs --previous 名字 → 看上次崩溃前日志（CrashLoopBackOff 必看）
    • kubectl exec -it 名字 -- /bin/sh → 进容器内部排查依赖、配置
    • crictl logs <containerID> → kubelet 都连不上时在节点上直接看容器日志

    3.2 Service 排障流程

    # 1. 看 Service 是否选中了 Pod（最常见：endpoints 空）
kubectl get svc web-svc -n myapp
kubectl get endpoints web-svc -n myapp
#  NAME      ENDPOINTS
#  web-svc   <none>          ← 空！selector 没匹配到 Pod

# 2. 对照 selector 和 Pod labels（最常踩的坑）
kubectl get svc web-svc -o jsonpath='{.spec.selector}'   # Service 选什么
kubectl get pods -n myapp --show-labels                  # Pod 实际有什么 label
#  常见：label 拼写不一致、namespace 不对、Pod 没 Ready（readinessProbe 没过）

# 3. 在 Pod 内访问 ClusterIP
kubectl exec -it debug -- sh -c "curl -v http://web-svc:80"
#  通 → kube-proxy 规则正常
#  不通 → 往下查 kube-proxy / iptables

# 4. 看 kube-proxy 是否正常
kubectl get pods -n kube-system | grep kube-proxy
kubectl logs -n kube-system kube-proxy-xxx --tail=50

# 5. 在节点上看 iptables 规则（IPVS 模式看 ipvsadm -L）
iptables -t nat -L -n | grep web-svc
#  应能看到 DNAT 把 Service IP 改写成 Pod IP
ipvsadm -Ln | grep <ClusterIP>       # IPVS 模式

    3.3 节点排障流程

    # 1. 看节点状态
kubectl get nodes
#  NAME      STATUS     ROLES    VERSION
#  node-1    Ready      <none>   v1.28.0
#  node-2    NotReady   <none>   v1.28.0     ← 异常

# 2. describe 看 Conditions
kubectl describe node node-2
#  Conditions:
#    Ready            False  ... KubeletNotReady  container runtime not ready
#    MemoryPressure   True   ← 内存压力
#    DiskPressure     True   ← 磁盘压力
#    PIDPressure      False

# 3. 登录节点，看 kubelet 和运行时
systemctl status kubelet
journalctl -u kubelet --since "30 min ago" | tail -50
systemctl status containerd
crictl ps                        # 看运行中的容器

# 4. 看资源
free -h                           # 内存
df -h /var/lib/containerd /var   # 磁盘（容器磁盘满会让节点 NotReady）
df -i /var                        # inode（小文件太多会耗尽 inode）

# 5. NotReady 常见原因
#  - kubelet 崩溃/被 OOM → 看 journalctl
#  - 磁盘满（容器镜像、日志）→ 清理 docker/containerd 存储
#  - 容器运行时挂了 → systemctl restart containerd
#  - 网络插件问题 → CNI Pod 状态
    节点 NotReady 排查命令清单
    • kubectl describe node 名字 → 看 Conditions（Memory/Disk/PID Pressure）
    • systemctl status kubelet → kubelet 是否在跑
    • journalctl -u kubelet -f → kubelet 实时日志
    • systemctl status containerd + crictl ps → 运行时和容器
    • df -h /var + df -i /var → 磁盘空间和 inode
    • free -h → 内存

    3.4 网络排障流程

    # 1. DNS 解析
kubectl exec -it debug -- nslookup web-svc
#  能解析出 ClusterIP → DNS（kube-dns/CoreDNS）正常
#  解析失败 → 看 kube-system 里 coredns Pod、看 /etc/resolv.conf

# 2. Pod 间直接通信（用 Pod IP）
kubectl exec -it debug -- ping <另一个PodIP>
#  同节点不通 → CNI 问题（calico/flannel）
#  跨节点不通 → 节点间隧道/IPIP/BGP 问题

# 3. Service 访问（见 3.2）

# 4. 跨节点通信排查
#  - 看 CNI 插件 Pod 是否正常：kubectl get pods -n kube-system | grep -E "calico|flannel"
#  - 看节点路由表：ip route
#  - 看网络策略是否误伤：kubectl get networkpolicy -A

# 5. 外部访问不通
#  - Ingress：kubectl get ingress、kubectl describe ingress、看 ingress-controller 日志
#  - NodePort：节点防火墙/安全组是否放行
#  - LoadBalancer：云厂商 LB 后端是否注册了节点

    3.5 存储排障流程

    # 1. PVC 一直 Pending（最常见）
kubectl get pvc
#  NAME        STATUS    VOLUME   CAPACITY
#  data-pvc    Pending                       ← 没绑上 PV

kubectl describe pvc data-pvc
#  Events:
#    Warning  ProvisioningFailed  storageclass
#      storageclass "fast-ssd" not found   ← StorageClass 名字错
#    或: no persistent volumes available   ← 静态 PV 没有匹配的
#    或: volume binding is waiting         ← 等待调度（WaitForFirstConsumer）

# 2. PV 绑定问题
kubectl get pv
#  看是否有 ACCESS MODES、容量匹配 PVC 的可用 PV

# 3. StorageClass 是否存在、是否默认
kubectl get storageclass
#  fast-ssd (default)   kubernetes.io/no-provisioner
#  如果需要动态供给但 SC 是 no-provisioner，就不会自动建 PV

# 4. 挂载错误（Pod 卡在 ContainerCreating）
kubectl describe pod 名字
#  Events:
#    Warning  FailedMount  ...  Unable to attach or mount volume
#      volume "data" not found   ← PV 被删了或不存在
#    Warning  FailedMount  ...  mount /dev/xxx on /data failed
#      no such file or directory  ← 节点上挂载路径/权限问题

# 5. 节点上看挂载情况
mount | grep data
ls -l /var/lib/kubelet/pods/<podUID>/volumes
    排障铁律：从上往下，别跳步

    排障永远遵循「表象 → 资源状态 → 事件 → 日志 → 进容器」的顺序。 get 看 STATUS → describe 看 Events → logs 看应用日志 → exec 进容器验证。 跳过 describe 直接猜原因，是大多数排障时间被浪费的根源。

    4. etcd 备份与恢复

    etcd 是集群的大脑——所有 Pod、Service、Secret、ConfigMap、RBAC 都存在 etcd 里。 etcd 丢了，整个集群就没了。生产必须定期备份。

    # === 备份 ===
# 在任一 master 节点执行（需 etcdctl，装 etcd 时自带）
ETCDCTL_API=3 etcdctl snapshot save /backup/etcd-$(date +%Y%m%d).db \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key

# 验证备份完整性
ETCDCTL_API=3 etcdctl snapshot status /backup/etcd-20240901.db -w table
#  +----------+------------+-----------+-----------+
#  |  HASH    | REVISION   | TOTAL KEYS| TOTAL SIZE|
#  +----------+------------+-----------+-----------+
#  | ...      | 123456     | 8900      | 12 MB     |
    # === 恢复（在灾难恢复场景）===
# 1. 停掉所有 master 的 etcd 和控制面
systemctl stop kube-apiserver
systemctl stop etcd

# 2. 清空旧的 etcd 数据目录（非常重要，否则恢复会失败）
mv /var/lib/etcd /var/lib/etcd.bak

# 3. 从备份恢复
ETCDCTL_API=3 etcdctl snapshot restore /backup/etcd-20240901.db \
  --data-dir=/var/lib/etcd

# 4. 启动 etcd 和 apiserver
systemctl start etcd
systemctl start kube-apiserver

# 5. 多 master 集群：恢复一个后，其它 master 用 etcdctl member add 重新加入
    生产必须定期备份 etcd！

    建议每天至少备份一次，备份文件异机/异地存放（别和 etcd 放同一台机器， 机器挂了备份也跟着没）。恢复前必须停 etcd 并清空旧数据目录， 否则恢复会因目录非空而失败。重大操作（升级、迁移）前务必先做一次手动备份。

    5. 集群升级

    K8s 版本升级有严格原则，乱升会出大问题。

    • 升级顺序：先升 kubeadm（工具）→ 再升控制面组件（apiserver/scheduler/controller/etcd）→ 最后升 kubelet。 apiserver 版本不能比 kubelet 低超过 2 个小版本。
    • 一次只升一个小版本：如 1.27 → 1.28，不能跨 1.27 → 1.30。
    • 先升 master，再升 worker，worker 滚动升级避免业务全停。
    # 升级前：备份 etcd（见第 4 节）
# 升级前：排空一个 worker 节点测试
kubectl cordon node-2
kubectl drain node-2 --ignore-daemonsets --delete-emptydir-data

# 1. 升级 kubeadm
yum install -y kubeadm-1.28.x-0 --disableexcludes=kubernetes

# 2. 升级控制面（master 节点）
kubeadm upgrade apply v1.28.x

# 3. 升级 kubelet 和 kubectl
yum install -y kubelet-1.28.x-0 kubectl-1.28.x-0 --disableexcludes=kubernetes
systemctl daemon-reload
systemctl restart kubelet

# 4. 升级 worker 节点
kubeadm upgrade node       # 在 worker 上执行
yum install -y kubelet-1.28.x-0 --disableexcludes=kubernetes
systemctl restart kubelet
kubectl uncordon node-2    # 恢复调度
    升级前必须备份 etcd

    集群升级失败最严重的后果是 etcd 数据损坏、整个集群不可用。 升级前做一次 etcd 快照备份是硬性要求，且要先在测试集群演练全流程。 生产窗口选业务低峰期，准备好回滚预案（恢复 etcd 备份 + 回退 kubelet/kubeadm 版本）。

    6. CI/CD 与 GitOps

    应用从代码到 K8s 集群，有两代主流模式。

    6.1 传统 CI/CD

    代码 push → Jenkins/GitLab CI 构建镜像 → 流水线执行 kubectl apply -f deploy.yaml 或 helm upgrade。 简单直接，但集群状态不在 Git 里，手动改了集群配置后 Git 不会感知，漂移难发现。

    6.2 GitOps

    把整个集群的期望状态（YAML/Helm values）放在 Git 仓库， 由 ArgoCD / Flux 持续把 Git 的状态同步到集群。Git 是唯一真源（Single Source of Truth）。

    GitOps 流程一图流
      开发 push 代码
       │
       ▼
  ┌──────────┐   构建镜像   ┌──────────┐
  │  GitLab  │ ──────────→ │ Registry │
  │  CI/CD   │             │ (镜像仓库)│
  └────┬─────┘             └──────────┘
       │ 更新 K8s 清单仓库（改镜像 tag）
       ▼
  ┌──────────────────────────┐
  │   Git 配置仓库（YAML /   │  ← 唯一真源
  │   Helm values / Kustomize│
  └──────────┬───────────────┘
             │ 监听变更
             ▼
  ┌──────────────────────────┐
  │   ArgoCD / Flux          │  ← 持续同步
  │  (Compare & Apply)        │
  └──────────┬───────────────┘
             │ apply
             ▼
  ┌──────────────────────────┐
  │      K8s 集群             │
  └──────────────────────────┘
    GitOps 的好处
    • 可审计：每次集群变更都有 Git commit，谁改的、改了啥、何时改的一清二楚。
    • 可回滚：出问题就 git revert，ArgoCD 自动把集群回退到上一个版本。
    • 防漂移：有人手动 kubectl 改了集群，ArgoCD 检测到与 Git 不一致会告警甚至自动纠正。
    • 多环境一致：dev/test/prod 只是不同的 Git 目录或分支，部署方式完全一致。

    7. K8s 面试高频题汇总

    下面按模块汇总 30+ 道高频题，每题给精要参考答案要点。

    7.1 架构类

    说说 K8s 架构和各组件职责

    分 Master 控制面和 Node。Master：apiserver（请求入口，操作 etcd）、 etcd（状态存储）、scheduler（调度 Pod 到 Node）、controller-manager（维护期望状态如副本数）。 Node：kubelet（管理本节点 Pod，与容器运行时交互）、kube-proxy（维护 Service 网络规则）、 容器运行时（containerd/CRI-O 真正跑容器）。

    K8s 和 Docker 的关系

    Docker 是容器引擎，解决单机容器构建运行。K8s 是容器编排系统，解决多机多容器的调度、 服务发现、扩缩容、滚动更新。K8s 早期用 Docker 作为运行时，1.24 起弃用 dockershim， 改用 containerd/CRI-O（符合 CRI 标准）。K8s 不强绑 Docker，但二者常配合使用：Docker 构建，K8s 编排。

    什么是声明式模型

    用户向 K8s 提交「期望状态」（YAML，如 replicas: 3）， controller 持续对比期望状态和实际状态，发现偏差就自动调整使其一致。 和命令式（执行命令改状态）不同，声明式可重入、可自愈、易审计。 典型：kubectl apply 同一个 YAML 多次结果一致；Pod 挂了 controller 自动拉起新的。

    etcd 的作用是什么

    etcd 是强一致分布式 KV 存储，保存 K8s 集群所有状态数据（Pod/Service/Secret/ConfigMap/RBAC 等）。 是整个集群的「大脑」和唯一持久化真源。apiserver 是唯一直接读写 etcd 的组件。 etcd 挂了等于集群大脑死亡，生产用 3/5 节点 Raft 集群保证高可用，必须用 SSD 并定期备份。

    7.2 Pod 类

    Pod 有哪些状态

    Pending（等待调度/拉镜像）、ContainerCreating（创建中）、Running（运行中，但容器未必就绪）、 Succeeded（正常退出，Job 专用）、Failed（容器退出且非 0）、 CrashLoopBackOff（反复崩溃重启）、ImagePullBackOff（镜像拉取失败）、 Unknown（apiserver 联系不上 kubelet）。

    三类探针的区别

    livenessProbe（存活）：失败就重启容器，解决死锁/hang 住。 readinessProbe（就绪）：失败就从 Service 摘流量但不重启，解决启动慢/过载。 startupProbe（启动）：启动期独占，通过后另两个才生效，适合慢启动应用避免被 liveness 误杀。

    QoS 等级是什么

    按资源 requests/limits 配置自动分三档： Guaranteed（requests=limits，最高优先级，最后被驱逐）、 Burstable（至少一个有 requests，中等）、 BestEffort（无 requests/limits，最先被驱逐）。 节点资源紧张时按 QoS 从低到高驱逐 Pod。

    Init Container 和 Sidecar 的区别

    Init Container：在主容器前顺序执行完退出，用于初始化（等依赖、改配置、迁移数据）， 必须成功主容器才会启动。 Sidecar：和主容器并行长期运行，辅助主容器（如日志 agent、service mesh proxy）。 K8s 1.28+ 原生支持 Sidecar 容器（initContainers 设 restartPolicy: Always）。

    Pod 怎么优雅终止

    删除 Pod 时：1) 把 Pod 从 Service endpoints 摘除；2) 发送 SIGTERM 给主容器 （可设 preStop hook 做清理如反注册）；3) 等 terminationGracePeriodSeconds（默认 30s）； 4) 还没退出就 SIGKILL 强杀。要点：preStop + readinessProbe 配合，避免流量打到正在退出的 Pod。

    7.3 Workload 类

    Deployment 和 StatefulSet 的区别

    Deployment：无状态，Pod 名随机（web-xxx），可任意扩缩，适合 Web/API。 StatefulSet：有状态，Pod 名稳定有序（db-0/db-1），每个 Pod 有独立 PVC 和稳定网络标识 （db-0.headless-svc），适合数据库、消息队列、需主从拓扑的应用。扩缩要按序，不能乱序删。

    滚动更新的原理

    Deployment 用 maxSurge（最多多几个新 Pod）和 maxUnavailable（最多少几个旧 Pod）控制节奏。 新建新 Pod → 新 Pod Ready → 删一个旧 Pod → 重复，整个过程渐进替换。 可设 maxUnavailable: 0 保证不中断服务。回滚用 kubectl rollout undo， 切回上一个 ReplicaSet。

    什么场景用 DaemonSet

    每个 Node 上跑一个 Pod 的场景：日志采集（Fluentd）、监控 agent（node-exporter）、 网络插件（calico-node）、存储 agent、Ingress Controller（hostNetwork 模式）。 新节点加入自动起 Pod，节点删除自动清理。配合 toleration 可在 master 上也跑。

    Job 和 CronJob 的区别

    Job：跑一次就结束的任务（数据迁移、批处理），完成次数/并行度可控。 CronJob：按 cron 表达式定时触发 Job（每日备份、每时报表）。 注意 .spec.concurrencyPolicy 控制任务重叠时的行为（Allow/Forbid/Replace）。

    7.4 网络类

    Service 有几种类型

    ClusterIP（默认，集群内访问）、NodePort（暴露到节点端口 30000+）、 LoadBalancer（云厂商提供 LB，外部访问）、 ExternalName（DNS CNAME 到外部域名，不发 IP）。 另有 Headless（clusterIP: None，DNS 直接返回所有 Pod IP，StatefulSet 用）。

    Ingress 和 Service 的区别

    Service 是 L4（TCP/UDP）负载均衡，给一组 Pod 稳定入口，但不支持按域名/路径路由。 Ingress 是 L7（HTTP/HTTPS），按域名和路径把流量路由到不同 Service，还支持 TLS 终结、虚拟主机。 Ingress 需 Ingress Controller（如 ingress-nginx）真正转发流量，Ingress 资源只是路由规则。

    kube-proxy iptables 和 IPVS 的区别

    iptables 模式：规则线性匹配，Service 多时性能下降明显，但兼容性好。 IPVS 模式：基于哈希表，O(1) 查找，Service 量大（千级以上）时性能更好， 还支持更多负载算法（rr/lc/sh 等）。生产 Service 量大建议 IPVS。

    Service 不通怎么排查

    1) 看 endpoints 是否为空（selector 没匹配到 Pod）；2) Pod 是否 Ready（readinessProbe 没过会摘除）； 3) Pod 内 curl Pod IP；4) curl ClusterIP；5) 看 kube-proxy 和 iptables/ipvs 规则； 6) NodePort 看节点防火墙。从 selector → Pod 状态 → kube-proxy 逐层查。

    Headless Service 是什么

    clusterIP 设为 None 的 Service，不分配 ClusterIP，DNS 查询直接返回所有 Pod 的 IP。 用于客户端需要直连每个 Pod 的场景（StatefulSet 主从、gRPC 客户端负载均衡、 服务发现返回实例列表）。配合 StatefulSet，每个 Pod 有稳定的「Pod名.服务名」DNS 记录。

    7.5 存储类

    PV 和 PVC 的关系

    PV 是集群的存储资源（管理员创建或动态供给），PVC 是用户对存储的申请（容量、访问模式）。 PVC 绑定匹配的 PV 后，Pod 通过 PVC 使用存储。解耦了「谁提供存储」和「谁用存储」， 用户不用关心后端是 NFS 还是云盘。

    什么是 StorageClass

    StorageClass 是动态供给 PV 的模板，定义 provisioner（如云盘 CSI）、参数、绑定策略。 用户只声明 PVC，StorageClass 自动创建对应 PV 并绑定，省去管理员手动建 PV。 生产标配：按 SC 名（fast-ssd / hdd）区分存储性能档位。

    ConfigMap 热更新生效吗

    部分生效。环境变量方式不更新（Pod 重启才生效）； Volume 挂载方式会自动更新（kubelet 周期同步，约 1 分钟内）， 但应用是否重读取决于应用自身是否 watch 文件变化。 不重读就需要滚动重启 Pod。subPath 挂载的不会热更新。

    Secret 安全吗

    默认不安全，只是 base64 编码，能被 kubectl get secret -o yaml 直接解码。 生产加固：开启 etcd 静态加密（EncryptionConfiguration）、用 RBAC 限制 Secret 访问权限、 敏感凭据走外部 KMS（Vault、云厂商 KMS）或 Sealed Secrets 加密后再入 Git。

    7.6 安全类

    说说 RBAC 模型

    Role-Based Access Control。三要素：Subject（用户/组/ServiceAccount）、 Role（权限规则）、RoleBinding（把 Role 绑给 Subject）。 权限＝动词（get/list/create/...）＋资源（pods/deployments/...）。 最小权限原则：按需授权，CI/CD 用独立 ServiceAccount 而非共享 admin。

    Role 和 ClusterRole 的区别

    Role 是命名空间级权限，只在该 namespace 生效； ClusterRole 是集群级权限，可授权集群范围资源（nodes/pv/namespace）或跨 namespace 共享。 对应 RoleBinding（绑 Role，namespace 内）和 ClusterRoleBinding（绑 ClusterRole，集群级）。 常见做法：定义 ClusterRole，用 RoleBinding 绑到具体 namespace，实现权限复用 + 作用域限制。

    怎么保证 Pod 安全运行

    1) SecurityContext 限制：禁止特权（privileged: false）、只读根文件系统、设 runAsNonRoot； 2) Pod Security Standards（PSS）策略（privileged/baseline/restricted 三档）； 3) NetworkPolicy 限制 Pod 间网络访问； 4) RBAC 限制 ServiceAccount 权限； 5) 镜像漏洞扫描 + 只信可信镜像仓库； 6) 资源 requests/limits 防 OOM 和资源耗尽。

    7.7 调度类

    调度器怎么工作

    两阶段：1) 预选（Filter）：用一系列 Predicate 过滤不满足的节点（资源不足、污点不匹配、nodeSelector 不符）； 2) 优选（Score）：对剩余节点打分排序（资源均衡、亲和性、反亲和）。选最高分节点绑定 Pod。 新版调度器用 Scheduling Framework，支持插件化扩展自定义调度逻辑。

    Taint 和 Toleration

    Taint（污点）打在节点上，标记「不让 Pod 来」（如 master 节点 NoSchedule）。 Toleration（容忍）写在Pod上，声明「我能容忍某污点」。 用于：把专用节点（GPU/高内存）留给特定 Pod、把 master 排除掉业务 Pod、 节点维护时先打 NoSchedule 再 drain。effect 有 NoSchedule/PreferNoSchedule/NoExecute。

    HPA 怎么工作

    Horizontal Pod Autoscaler 根据 CPU/内存/自定义指标自动扩缩 Deployment/StatefulSet 副本数。 控制循环（默认 15s）从 metrics-server/Prometheus Adapter 取指标，对比目标值算期望副本数， 调 scale 子资源改 replicas。要点：必须设 resources.requests（HPA 算 CPU 利用率要分母）、 扩容快缩容慢（避免抖动）、有 min/max replicas 上下限。

    7.8 运维类

    怎么备份 K8s 集群

    核心是备份 etcd：用 ETCDCTL_API=3 etcdctl snapshot save 定期快照，异机存放。 集群配置（kube-apiserver/etcd 的证书和静态 Pod YAML）单独备份 /etc/kubernetes。 应用层用 Velero 备份 PVC 和命名空间资源，方便跨集群迁移。备份要做恢复演练，没演练过的备份等于没有。

    怎么排查 Pod 起不来

    看 STATUS 分流：Pending 看 describe 的 FailedScheduling（资源不足/污点）； ContainerCreating 看 Events 的镜像拉取/挂载错误； CrashLoopBackOff 看 logs --previous 上一次崩溃前日志（应用启动失败、配置错、依赖不通）。 流程：get → describe → logs → exec。

    怎么做滚动更新和回滚

    更新：kubectl set image deploy/web web=nginx:1.26 或 kubectl apply -f 改镜像， 看 kubectl rollout status。回滚：kubectl rollout undo deploy/web 回上一版，rollout undo --to-revision=N 回指定版本。Helm 用 helm rollback。 要点：设 maxUnavailable: 0 + readinessProbe 保证不中断。

    怎么限制 namespace 资源

    用 ResourceQuota 限制 namespace 总量（CPU/内存/PVC/对象数上限）， 用 LimitRange 设默认 requests/limits 和单个 Pod 上下限。 组合使用：ResourceQuota 卡总量上限，LimitRange 卡单个最小/默认值， 防止某团队一个 Pod 吃光整个集群资源。

    Helm 是什么

    K8s 的包管理器（类似 yum/apt）。把一组 YAML 打包成 Chart，支持参数化、版本管理、一键回滚。 三大概念：Chart（模板包）、Release（运行实例）、Repository（Chart 仓库）。 生产用 helm upgrade --install --atomic 实现幂等安装 + 失败自动回滚， 配置走 values 文件纳入 Git。

    本章小结

    • K8s 生产监控标准是 Prometheus + Grafana + Alertmanager，kube-prometheus-stack 一键装好，metrics-server 喂 HPA，Prometheus 喂监控告警。
    • 日志方案选型：轻量选 Loki + Promtail，需深度检索选 EFK，应用日志一律输出 stdout/stderr。
    • Pod 排障五步：get 看状态 → describe 看 Events → logs 看日志 → logs --previous 看崩溃前 → exec 进容器验证，别跳步。
    • Service 不通先查 endpoints 是否为空（selector 匹配 + Pod Ready），再逐层查 kube-proxy / iptables。
    • 节点 NotReady 看 describe Conditions（Memory/Disk/PID Pressure）+ journalctl kubelet + df/free。
    • etcd 是集群大脑，必须每天备份并异机存放，恢复前停 etcd 清空数据目录，灾难恢复靠它。
    • 集群升级一次只升一个小版本，顺序 kubeadm → 控制面 → kubelet，升级前必备份 etcd。
    • GitOps 让 Git 成为集群状态唯一真源，ArgoCD/Flux 自动同步，可审计可回滚防漂移。
    • 面试高频题按架构/Pod/Workload/网络/存储/安全/调度/运维八模块准备，重点是讲清原理和取舍。
    • 综合实战项目（前端+后端+MySQL+Redis）串联了整个 K8s 专题知识点，改成 Helm Chart 后就是生产标准形态。
