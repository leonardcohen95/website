    Workload 资源管理

    前一章我们讲了 Pod，但生产里几乎不会直接创建裸 Pod——挂了没人管、不能滚动更新、 副本数没法扩缩。本章覆盖 K8s 的五大 Workload 资源：ReplicaSet、Deployment、 StatefulSet、DaemonSet、Job/CronJob，重点拆 Deployment 滚动更新原理和 StatefulSet 为什么是有状态应用的唯一选择。学完你能根据场景挑对 Workload，并答出 「Deployment 滚动更新原理」「StatefulSet 和 Deployment 区别」等高频面试题。

    学习目标

    • 理解 Workload 控制器模式：期望状态 vs 实际状态
    • 掌握 Deployment 滚动更新、回滚、Recreate 策略及参数调优
    • 能解释 StatefulSet 的稳定标识、有序部署和固定存储
    • 会用 DaemonSet 部署节点级 Agent，理解新节点自动加入
    • 会写 Job 和 CronJob，区分 backoffLimit / completions / schedule
    • 能根据应用场景在五种 Workload 中正确选型

    1. 为什么需要 Workload 资源

    直接 kubectl run 出来的裸 Pod 看似简单，生产却几乎不用，原因有三个：

    • 挂了没人管：Pod 节点故障或被删，不会自动重建副本。
    • 不能滚动更新：换镜像版本要么手删手建，要么停服。
    • 副本数不可控：扩缩容得手动操作，没法和 HPA 联动。
    控制器模式（Reconcile Loop）

    所有 Workload 本质都是控制器：持续比较期望状态（用户在 spec 里写的） 和实际状态（集群里当前的），发现差异就做出动作让两者一致。 比如期望 3 副本、实际只剩 2，就再创建 1 个。这种循环叫 Reconcile Loop（调谐循环）， 是 K8s 声明式模型的核心机制。

    声明式 vs 命令式

    命令式：kubectl run nginx --image=nginx，告诉 K8s「现在干这个」。 声明式：kubectl apply -f deploy.yaml，告诉 K8s「我要的状态是这样，你来对齐」。 声明式天然支持版本管理、可重入、可 diff，生产全部用声明式 + GitOps。

    2. ReplicaSet

    ReplicaSet（RS）的作用很简单：维持指定数量的 Pod 副本，少了就建，多了就删。 

    apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: web-rs
spec:
  replicas: 3                    # 期望 3 个副本
  selector:                      # 选中哪些 Pod 归自己管
    matchLabels:
      app: web
  template:                      # Pod 模板
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: web
          image: nginx:1.25
          ports:
            - containerPort: 80
    实际不直接用 ReplicaSet

    生产中几乎不会直接写 ReplicaSet YAML。原因：RS 不支持滚动更新和回滚， 改镜像版本只能删旧建新。正确做法是用 Deployment，Deployment 自动管理 ReplicaSet （每次发版会生成一个新 RS，旧 RS 副本数逐步降到 0 但不删，方便回滚）。

    3. Deployment（重点）

    Deployment 是日常用得最多的 Workload。它在 ReplicaSet 之上加了一层 版本管理：每次改 Pod 模板（比如换镜像版本），Deployment 会创建一个新 RS， 通过新老 RS 的副本数此消彼长，完成滚动更新。

    3.1 完整 YAML（带滚动策略）

    apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-deploy
  labels:
    app: web
spec:
  replicas: 4
  selector:
    matchLabels:
      app: web
  strategy:
    type: RollingUpdate         # 滚动更新策略
    rollingUpdate:
      maxSurge: 1               # 升级过程中最多超出期望副本数 1 个
      maxUnavailable: 0         # 升级过程中最多比期望少 0 个 → 零停机
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: web
          image: nginx:1.25
          ports:
            - containerPort: 80

    3.2 滚动更新原理

    改镜像触发滚动更新时，Deployment 不直接动现有 Pod，而是创建一个新 ReplicaSet， 副本数从 0 开始逐步往上加；同时旧 ReplicaSet 副本数往下减。整个过程 新老版本 Pod 短暂共存，靠 maxSurge / maxUnavailable 控制节奏。

    滚动更新过程图
      replicas=4  maxSurge=1  maxUnavailable=0
  ┌─────────────┐
  │ 旧 RS (v1)  │ 4 副本
  │  新 RS (v2) │ 0 副本
  └─────────────┘
         │ set image nginx:1.26
         ▼
  ┌─────────────┐
  │ 旧 RS (v1)  │ 3 副本（先减 1）
  │  新 RS (v2) │ 1 副本（多建 1 个）
  └─────────────┘
         │ ...继续滚动
         ▼
  ┌─────────────┐
  │ 旧 RS (v1)  │ 0 副本（不删，留作回滚）
  │  新 RS (v2) │ 4 副本（最终状态）
  └─────────────┘
    maxSurge 和 maxUnavailable 的取舍

    maxSurge=0：升级时不允许多建 Pod → 必须先删旧再建新， 会有一段时间副本数不足，有停机风险。优点是不需要额外资源。 maxUnavailable=0：升级时不允许少于期望副本数 → 必须先建新再删旧， 保证零停机。代价是升级期间会有 surge 个多余 Pod 抢资源。 生产 7×24 服务建议 maxUnavailable=0, maxSurge=1（或更高）。

    3.3 实战命令

    # 触发滚动更新（改镜像）
kubectl set image deploy/web-deploy web=nginx:1.26

# 看滚动更新状态（阻塞直到完成或失败）
kubectl rollout status deploy/web-deploy

# 查看历史版本（每个 revision 对应一个 ReplicaSet）
kubectl rollout history deploy/web-deploy
kubectl rollout history deploy/web-deploy --revision=2

# 回滚到上一版本
kubectl rollout undo deploy/web-deploy

# 回滚到指定版本
kubectl rollout undo deploy/web-deploy --to-revision=2

# 暂停 / 恢复滚动更新（用于灰度：先放一小部分流量观察）
kubectl rollout pause deploy/web-deploy
kubectl rollout resume deploy/web-deploy

# 重启 Deployment（不改版本，重建所有 Pod，常用于强制重新拉镜像）
kubectl rollout restart deploy/web-deploy

    3.4 Recreate vs RollingUpdate

    # Recreate 策略：先全删旧 Pod，再建新 Pod
spec:
  strategy:
    type: Recreate       # 有停机，但能避免新老版本并存的不兼容
    Recreate 还是 RollingUpdate？
    • RollingUpdate（默认）：新老共存，零停机。适合无状态、前后兼容的应用。
    • Recreate：先全删再建，有停机。适合不允许多实例并存的应用， 比如单实例任务型、数据格式不兼容的新老版本（旧 Pod 必须先退干净）。
    • 建议生产无状态服务一律 RollingUpdate + maxUnavailable=0。

    4. StatefulSet

    有状态应用（MySQL、Redis Cluster、ZooKeeper、Elasticsearch）用 Deployment 会翻车， 因为它们对网络标识、启动顺序、持久化存储有强依赖。

    4.1 为什么 Deployment 不能跑有状态应用

    • Pod 名随机：Deployment 的 Pod 名带随机后缀（web-deploy-7b89f6c4d-abc12），客户端没法靠名字连。
    • 无序启停：滚动更新时 Pod 是无序的，主从角色没法保证先主后从。
    • 存储不固定：Pod 重建后挂的是新卷，数据丢了。
    StatefulSet 的三大特性

    稳定网络标识：Pod 名固定为 <sts-name>-0/1/2…， 配合 Headless Service 可以 pod-0.svc-name 直连。 有序启停：部署/扩容从 0 开始顺序（pod-0 → pod-1）， 删除逆序（pod-N → pod-0）。 固定存储：通过 volumeClaimTemplates， 每个 Pod 绑定固定的 PVC，重建后挂回原卷。

    4.2 完整 YAML（Headless Service + volumeClaimTemplates）

    # 1) Headless Service：返回 Pod IP 而非负载均衡 IP
apiVersion: v1
kind: Service
metadata:
  name: mysql-headless
spec:
  clusterIP: None             # 关键：None 才是 Headless
  selector:
    app: mysql
  ports:
    - port: 3306
---
# 2) StatefulSet
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: mysql
spec:
  serviceName: mysql-headless  # 必须绑 Headless Service
  replicas: 3
  selector:
    matchLabels:
      app: mysql
  template:
    metadata:
      labels:
        app: mysql
    spec:
      containers:
        - name: mysql
          image: mysql:8.0
          ports:
            - containerPort: 3306
          volumeMounts:
            - name: data
              mountPath: /var/lib/mysql
          env:
            - name: MYSQL_ROOT_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: mysql-secret
                  key: password
  volumeClaimTemplates:         # 每个 Pod 自动生成一个固定 PVC
    - metadata:
        name: data
      spec:
        accessModes: ["ReadWriteOnce"]
        resources:
          requests:
            storage: 20Gi
    StatefulSet 必备三件套

    StatefulSet 通常要配 Headless Service（让 DNS 返回每个 Pod 的 IP） + PVC/PV（固定存储，推荐用 StorageClass 动态供给）+ 有序脚本或 init container（区分主从角色，如通过 ordinal index 0=主，>0=从）。三者缺一，有状态应用都跑不稳。

    典型场景：MySQL / Redis / ZooKeeper

    这些应用都需要稳定身份（主从互连用 hostname）、有序启动（先选主再起从）、 持久化数据（重启数据不能丢），正好是 StatefulSet 三大特性的对应。 生产部署它们首选 StatefulSet + 持久化存储 + Headless Service。

    5. DaemonSet

    DaemonSet 保证每个（或指定）节点上运行一个 Pod 副本。新节点加入集群自动起， 节点被驱逐或删除，Pod 也跟着消失。典型用途是节点级基础设施。 

    apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: node-exporter
  namespace: monitoring
  labels:
    app: node-exporter
spec:
  selector:
    matchLabels:
      app: node-exporter
  template:
    metadata:
      labels:
        app: node-exporter
    spec:
      hostNetwork: true           # 用宿主机网络，省一层 NAT
      hostPID: true                # 能看到宿主机进程，便于采集
      containers:
        - name: node-exporter
          image: prom/node-exporter:v1.7.0
          ports:
            - containerPort: 9100
              hostPort: 9100       # 直接暴露到宿主机端口
      tolerations:                 # 容忍 master 污点，让 master 也采
        - key: node-role.kubernetes.io/control-plane
          operator: Exists
          effect: NoSchedule
    DaemonSet 典型场景
    • 日志采集：Fluentd、Filebeat、Vector，每节点读容器日志。
    • 监控 Agent：Node Exporter、Telegraf，采集节点指标。
    • 网络插件：Calico、Flannel、Cilium 的节点组件。
    • 存储插件：CSI driver 的节点端，如 RBD/Ceph-CSI。
    新节点自动运行 Pod

    DaemonSet 的调度由 DaemonSet Controller + 调度器协作：集群新加一台 Node， 无需手动操作，符合 selector 的 Pod 会自动在该节点拉起； 节点被移除时 Pod 自动清理。和 Deployment 的「按副本数调度」是两套机制。

    6. Job 和 CronJob

    有些任务就是要「跑完就退」（如数据迁移、备份），用 Deployment 反而奇怪（容器退了会重启）。 Job 就是为这种一次性任务设计的。

    6.1 Job

    apiVersion: batch/v1
kind: Job
metadata:
  name: db-migrate
spec:
  completions: 1               # 期望成功完成几次
  parallelism: 1                # 同时跑几个
  backoffLimit: 4               # 失败重试上限，超过标记 Job Failed
  activeDeadlineSeconds: 600   # 总耗时上限，超时强制停
  template:
    spec:
      restartPolicy: OnFailure  # Job 必须显式设这个，不能是 Always
      containers:
        - name: migrate
          image: myapp/migrate:v1
          command: ["./migrate.sh"]
    Job 关键字段

    completions：目标成功次数（默认 1）。 parallelism：并发执行数，用于批处理加速。 backoffLimit：失败重试上限，超出后整个 Job 标记 Failed。 activeDeadlineSeconds：总超时，超时强制停。 restartPolicy：Job 只能选 OnFailure 或 Never，不能是 Always。

    6.2 CronJob

    apiVersion: batch/v1
kind: CronJob
metadata:
  name: db-backup
spec:
  schedule: "0 2 * * *"         # 每天 02:00 执行（cron 格式）
  concurrencyPolicy: Forbid     # 上次没跑完就跳过本次
  successfulJobsHistoryLimit: 3 # 保留最近 3 次成功的 Job
  failedJobsHistoryLimit: 3
  jobTemplate:
    spec:
      backoffLimit: 2
      template:
        spec:
          restartPolicy: OnFailure
          containers:
            - name: backup
              image: myapp/backup:v1
              command: ["./backup.sh"]
    schedule 和 Linux crontab 完全一致

    CronJob 的 schedule 是标准 5 段 cron 表达式 分 时 日 月 周，时区默认是 K8s 控制平面所在时区 （通常是 UTC！生产强烈建议显式设时区，K8s 1.25+ 支持 timeZone: Asia/Shanghai）。 常见坑：在 UTC 集群上写 0 2 * * *，实际是北京时间早上 10 点才跑。

    CronJob 典型场景
    • 数据库定时备份：mysqldump / pg_dump。
    • 数据 ETL / 清洗：每天凌晨跑批。
    • 证书续期：Let's Encrypt / 自签证书自动签。
    • 定时报表生成：生成日报/周报推送到 IM。

    7. Workload 选择决策表

    什么场景用什么 Workload
    场景                              | 推荐 Workload
----------------------------------+----------------
Web/API 无状态服务                | Deployment
MySQL/Redis/ZK 等有状态服务       | StatefulSet
节点级日志/监控/网络 Agent        | DaemonSet
一次性任务（迁移、批处理）        | Job
定时任务（备份、ETL）             | CronJob
CI/CD pipeline 临时构建           | Job

    口诀：无状态 Deployment，有状态 StatefulSet， 节点级 DaemonSet，跑完退 Job，定时跑 CronJob。 生产 90% 的服务是 Deployment，剩下按场景分流。

    8. 面试高频题

    Q1：Deployment 和 StatefulSet 的区别？

    Deployment 管无状态应用，Pod 名随机、无序启停、共享存储； StatefulSet 管有状态应用，Pod 名固定（pod-0/1/2）、有序部署和删除、 通过 volumeClaimTemplates 绑定固定 PVC，配合 Headless Service 提供稳定 DNS。 Deployment 用 ReplicaSet 做版本管理支持滚动更新/回滚；StatefulSet 自己按 ordinal 滚动。

    Q2：说说 Deployment 滚动更新的原理

    改 Pod 模板触发更新，Deployment 不直接改现有 Pod，而是创建一个新 ReplicaSet （副本数从 0 起），同时把旧 RS 副本数往下减。新老 RS 同时存在， 副本数此消彼长，节奏由 maxSurge（最多多几个）和 maxUnavailable（最多少几个）控制。 旧 RS 不删，副本数置 0，留作回滚（kubectl rollout undo 把旧 RS 拉起来）。 想要零停机：maxUnavailable=0，让旧 Pod 一直在直到新 Pod 就绪。

    Q3：什么场景用 DaemonSet？

    需要每个节点跑一个副本的基础设施类场景：日志采集（Fluentd/Filebeat）、 监控 Agent（Node Exporter）、网络插件（Calico/Flannel）、存储 CSI 节点端。 新节点加入集群自动起 Pod，节点移除自动清。常配 hostNetwork: true 和污点容忍（让 master 也部署）。

    Q4：Job 和 CronJob 的区别？

    Job 是一次性任务，跑完退出（completions/backoffLimit 控制）； CronJob 在 Job 之上加了 schedule（cron 表达式）字段， 按时间定时触发 Job。CronJob 的关键参数还有 concurrencyPolicy （Forbid 禁止并发、Allow 允许、Replace 替换未完成的）和 history 保留数。 Job 的 restartPolicy 只能是 OnFailure / Never。

    本章小结

    • Workload 资源本质是控制器：持续 Reconcile 让实际状态对齐期望状态。
    • ReplicaSet 维持副本数，但生产用 Deployment 管理 RS，支持滚动更新/回滚。
    • Deployment 滚动更新靠新老 RS 副本数此消彼长；maxUnavailable=0 实现零停机。
    • Recreate 策略先全删再建有停机，适合新老不兼容场景；默认 RollingUpdate。
    • StatefulSet 提供稳定网络标识、有序启停、固定存储，是有状态应用的唯一选择。
    • StatefulSet 必须配 Headless Service 和 PVC（推荐 StorageClass 动态供给）。
    • DaemonSet 每节点一个副本，新节点自动加入，用于日志/监控/网络/存储 Agent。
    • Job 跑完即退（completions/backoffLimit）；CronJob 定时触发 Job，schedule 用 cron 格式。
