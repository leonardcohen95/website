    1.3 Polars 简介

    Polars 用 Rust 实现，支持惰性求值（Lazy API）和多线程并行， 处理千万级以上数据比 Pandas 快数倍到数十倍，内存占用也更低。API 与 Pandas 类似但有差异。 

    import polars as pl

# 读取
df = pl.read_csv("bonds.csv")

# 表达式（核心）：选择 + 过滤 + 计算一次完成
result = (
    df.lazy()                                  # 惰性执行
      .filter(pl.col("price") > 100)
      .with_columns((pl.col("coupon") * 100).alias("coupon_pct"))
      .group_by("rating")
      .agg([
          pl.col("price").mean().alias("avg_price"),
          pl.col("code").count().alias("cnt"),
      ])
      .sort("avg_price", descending=True)
      .collect()                               # 触发执行
)
print(result)
    Pandas vs Polars

    Pandas：生态成熟、资料多、所有库都支持，数据量百万级以内首选。 缺点是单线程、内存占用高、大表慢。
    Polars：Rust 实现、多线程、惰性求值优化、内存友好， 千万级以上数据速度提升明显。缺点是生态较新、部分第三方库不直接支持。
    选型：数据量小、依赖生态（如 sklearn 接 DataFrame）用 Pandas； 数据量大、ETL 密集、追求性能用 Polars。两者可共存，小数据用 Pandas，重计算转 Polars。

    1.4 大数据量处理技巧

    • 分块读取：pd.read_csv("big.csv", chunksize=100000) 逐块处理，避免一次性加载爆内存。
    • 类型优化：df["rating"] = df["rating"].astype("category")， 低基数字符串转 category 可省 80%+ 内存；数值用 int32/float32 代替默认 64 位。
    • 向量化操作：永远别用 for 逐行遍历，用列运算、 apply（列）、np.vectorize，性能差几个数量级。
    • 选 Parquet：列式存储 + 压缩，比 CSV 读取快 10 倍、体积小 1/3。
    • 用 Polars/DuckDB：真到千万级以上，直接换工具比优化 Pandas 更有效。

    2. 消息队列 Kafka / RabbitMQ

    消息队列（MQ）是分布式系统的「润滑油」，解决服务间耦合、流量削峰、异步处理三大问题。 金融场景里，行情推送、订单流转、报表生成都离不开 MQ。

    2.1 为什么需要消息队列

    • 解耦：生产者只管发消息，不用关心谁来消费、有几个消费者， 服务之间不直接依赖。
    • 削峰：秒杀、大促时流量洪峰先灌进 MQ，下游按自己的速度消费， 避免被打挂。
    • 异步：耗时操作（发邮件、生成报表、批量计算）丢进 MQ， 接口立即返回，用户体验好。

    2.2 Kafka 架构

    Kafka 架构一图流
                        Producer（生产者，发消息）
                         │
                         ▼
        ┌────────────────────────────────────────┐
        │              Kafka 集群                 │
        │                                        │
        │  Topic: bond-trades                    │
        │   ┌──────────┐ ┌──────────┐ ┌────────┐ │
        │   │Partition0│ │Partition1│ │Partitio2│ │   分区内有序
        │   │ (leader) │ │ (leader) │ │(leader)│ │   分区间并行
        │   └────┬─────┘ └────┬─────┘ └───┬────┘ │
        └────────┼────────────┼────────────┼──────┘
                 │            │            │
                 ▼            ▼            ▼
        ┌────────────────────────────────────────┐
        │           Consumer Group（消费者组）     │
        │  Consumer0  Consumer1  Consumer2        │   组内一个消费
        └────────────────────────────────────────┘       者只消费一个分区

        辅助：ZooKeeper / KRaft 管理集群元数据（新版 KRaft 不再依赖 ZK）
    • Topic：消息的逻辑分类，如 bond-trades。
    • Partition：Topic 分成多个分区，分区内消息有序， 分区间并行，是 Kafka 高吞吐的关键。
    • Producer：生产者，往 Topic 发消息，可指定 key 决定路由到哪个分区。
    • Consumer Group：消费者组，组内每个消费者消费不同分区， 实现负载均衡；不同组消费同一份消息，实现广播。
    • Offset：消息在分区内的偏移量，消费者靠它记录消费进度。

    2.3 Python 操作 Kafka（confluent-kafka）

    pip install confluent-kafka

# ===== 生产者 =====
from confluent_kafka import Producer

p = Producer({"bootstrap.servers": "kafka:9092"})

def delivery_report(err, msg):
    if err:
        print(f"发送失败: {err}")
    else:
        print(f"已发送到 {msg.topic()}[{msg.partition()}] offset={msg.offset()}")

# 发送债券成交消息
for bond_code in ["019640", "019641", "019642"]:
    p.produce(
        topic="bond-trades",
        key=bond_code,                       # 同一 key 路由到同一分区，保证顺序
        value=f'{{"code": "{bond_code}", "price": 98.5}}'.encode(),
        on_delivery=delivery_report,
    )
p.flush()   # 等待所有消息发送完成


# ===== 消费者 =====
from confluent_kafka import Consumer

c = Consumer({
    "bootstrap.servers": "kafka:9092",
    "group.id": "bond-consumer-group",
    "auto.offset.reset": "earliest",       # 没有已提交 offset 时从最早开始
})
c.subscribe(["bond-trades"])

try:
    while True:
        msg = c.poll(1.0)                  # 轮询，超时 1 秒
        if msg is None:
            continue
        if msg.error():
            print(f"消费错误: {msg.error()}")
            continue
        print(f"收到: key={msg.key().decode()} value={msg.value().decode()}")
        c.commit()                          # 手动提交 offset（更安全）
finally:
    c.close()

    2.4 RabbitMQ 简介

    RabbitMQ 基于 AMQP 协议，核心概念是 Exchange（交换机）、 Queue（队列）、Binding（绑定）。 生产者发消息到 Exchange，Exchange 按路由规则把消息分发到绑定的 Queue，消费者从 Queue 取。 

    pip install pika

import pika

connection = pika.BlockingConnection(pika.ConnectionParameters("localhost"))
channel = connection.channel()

# 声明交换机和队列，并绑定
channel.exchange_declare(exchange="bond_events", exchange_type="topic")
channel.queue_declare(queue="trade_queue")
channel.queue_bind(exchange="bond_events", queue="trade_queue",
                   routing_key="bond.trade.*")   # topic 通配路由

# 发布
channel.basic_publish(
    exchange="bond_events",
    routing_key="bond.trade.019640",
    body=b'{"price": 98.5}',
)
connection.close()
    Kafka vs RabbitMQ 选型
    维度KafkaRabbitMQ
    吞吐量极高（百万级/s）万级/s
    延迟ms 级μs 级
    消息保留按时间/大小保留，可回溯消费即删
    顺序性分区内有序单队列有序
    协议自定义 TCPAMQP
    典型场景大数据日志、流处理、行情业务解耦、任务分发、RPC

    选型口诀：要吞吐、要回溯、要流处理 → Kafka； 要灵活路由、要低延迟、要确认机制 → RabbitMQ。金融行情推送、日志采集用 Kafka； 订单流转、邮件通知用 RabbitMQ。

    消息丢失、重复消费、顺序消费
    • 消息丢失：Producer 要等 ack（Kafka acks=all）、 Broker 多副本同步、Consumer 处理完再手动提交 offset。
    • 重复消费：Consumer 处理成功但提交 offset 前崩溃，会重投。 解决：消费端做幂等（用业务唯一键去重，如债券成交编号）。
    • 顺序消费：Kafka 同一分区内有序，所以保证同一业务 key 的消息 发到同一分区（用 key 路由），且一个分区只让一个消费者消费。

    3. Celery 异步任务

    Celery 是 Python 生态最流行的分布式任务队列，把耗时操作从请求线程剥离， 丢给后台 Worker 异步执行，还支持定时任务。

    3.1 Celery 架构

    Celery 组件
      Flask API ──发任务──► Broker（Redis/RabbitMQ）──取任务──► Worker（执行）
                           │                              │
                           │                              └──► 结果存 Backend（Redis/DB）
                           │
                     Celery Beat（定时调度器，按周期往 Broker 丢任务）
                     Flower（Web 监控面板，看任务状态、Worker 负载）
    • Worker：真正执行任务的进程，可开多个实现并发。
    • Broker：任务队列，常用 Redis 或 RabbitMQ。
    • Backend：存储任务结果，常用 Redis。
    • Beat：定时任务调度器，按 crontab/interval 触发任务。

# tasks.py —— Celery 应用与任务定义
from celery import Celery

app = Celery(
    "bond_tasks",
    broker="redis://localhost:6379/0",
    backend="redis://localhost:6379/1",
)
app.conf.update(
    task_serializer="json",
    result_serializer="json",
    timezone="Asia/Shanghai",
)

@app.task(bind=True, max_retries=3, default_retry_delay=10)
def calc_bond_ytm(self, bond_code, price):
    """异步计算债券到期收益率"""
    try:
        # 模拟耗时计算
        import time
        time.sleep(2)
        result = {"code": bond_code, "price": price, "ytm": 0.035}
        return result
    except Exception as exc:
        raise self.retry(exc=exc)        # 失败自动重试 3 次


# web.py —— Flask 接口

from tasks import calc_bond_ytm

app = Flask(__name__)

@app.post("/api/bonds//ytm")
def calc_ytm(code):

    4. 分布式系统基础

    系统从单机走向分布式，会遇到一致性、可用性、锁、ID 等经典问题。 这些是后端面试的必考内容，必须理解原理。

    4.1 CAP 定理与 BASE 理论

    CAP 三选二

    C（Consistency，一致性）：所有节点同一时刻看到相同数据。
    A（Availability，可用性）：每个请求都能在有限时间内得到响应（不一定是最新数据）。
    P（Partition tolerance，分区容错性）：网络分区（节点间通信中断）时系统仍能运行。
    分布式系统网络分区不可避免（P 必须满足），所以只能在 CP 和 AP 之间选： CP（如 ZooKeeper、etcd）保一致性牺牲可用性； AP（如 Eureka、Cassandra）保可用性牺牲一致性。

    BASE 是对 CAP 的折中：Basically Available（基本可用）、 Soft state（软状态）、Eventually consistent（最终一致）。 互联网系统大多采用最终一致性，不追求强一致，通过补偿、对账达成最终一致。

    4.2 分布式锁

    多台机器同时操作同一资源（如抢购同一只债券、修改同一账户）时，需要分布式锁互斥。 常用实现：Redis（SET NX）或 ZooKeeper（临时顺序节点）。 

    # Redis 分布式锁（最简版）
import redis
import uuid

r = redis.Redis()

def acquire_lock(lock_key, timeout=10):
    token = str(uuid.uuid4())         # 唯一标识，防误删别人的锁
    # SET NX EX：不存在才设，同时设过期时间（防死锁）
    ok = r.set(lock_key, token, nx=True, ex=timeout)
    return token if ok else None

def release_lock(lock_key, token):
    # 用 Lua 脚本保证「判断 + 删除」原子性
    lua = """
    if redis.call('get', KEYS[1]) == ARGV[1] then
        return redis.call('del', KEYS[1])
    else
        return 0
    end
    """
    r.eval(lua, 1, lock_key, token)

# 使用
token = acquire_lock("bond:019640:trade")
if token:
    try:
        # 执行互斥操作：下单、扣减库存
        pass
    finally:
        release_lock("bond:019640:trade", token)
    面试：分布式锁怎么实现

    参考要点：1) Redis SET key value NX EX seconds 原子加锁， value 用唯一 token；2) 释放时用 Lua 脚本判断 token 再删，保证原子，防误删； 3) 设置过期时间防死锁；4) 高可靠用 RedLock（多节点）或 Redisson 框架； 5) 对比 Redis vs ZooKeeper：Redis 性能好但需处理过期续期，ZooKeeper 强一致但性能稍差。 生产中直接用 Redisson 不要自己造轮子。

    4.3 分布式 ID 生成（雪花算法 Snowflake）

    分布式系统不能用数据库自增 ID（多库多表后冲突）。 雪花算法用 64 位 long 生成趋势递增、全局唯一的 ID。 

    # 64 位结构：
# 1 位符号位（0）| 41 位时间戳（毫秒，可用 69 年）
# | 10 位机器 ID（最多 1024 节点）| 12 位序列号（每毫秒 4096 个）

import time

class Snowflake:
    def __init__(self, worker_id=1):
        self.worker_id = worker_id
        self.sequence = 0
        self.last_ts = -1

    def next_id(self):
        ts = int(time.time() * 1000)
        if ts == self.last_ts:
            self.sequence = (self.sequence + 1) & 0xFFF   # 12 位
            if self.sequence == 0:                       # 该毫秒用完，等下一毫秒
                while ts <= self.last_ts:
                    ts = int(time.time() * 1000)
        else:
            self.sequence = 0
        self.last_ts = ts
        return (ts << 22) | (self.worker_id << 12) | self.sequence

sf = Snowflake(worker_id=1)
print(sf.next_id())   # 如 1764234567890123456

    5. 实战：债券数据异步处理系统

    把本章知识点串起来：API 接收债券计算请求 → 丢进 Kafka → Celery Worker 消费并计算 → 结果写库。 这是金融系统中典型的异步处理架构。

      ┌──────────┐   提交任务    ┌──────────┐    消费    ┌─────────────┐

    5.1 生产者：API 发消息到 Kafka

    # producer.py / Flask 接口
from flask import Flask, request, jsonify
from confluent_kafka import Producer
import json

app = Flask(__name__)
p = Producer({"bootstrap.servers": "kafka:9092"})

@app.post("/api/bonds/calc")
def submit_calc():
    body = request.get_json()
    msg = {
        "task_id": body["task_id"],
        "code": body["code"],
        "price": body["price"],
        "coupon": body.get("coupon", 0.035),
    }
    p.produce("bond-calc-tasks", key=msg["code"],
              value=json.dumps(msg).encode())
    p.flush()
    return jsonify({"status": "accepted", "task_id": msg["task_id"]}), 202

    5.2 消费者：Kafka → Celery 任务

    # consumer.py —— 消费 Kafka，转交给 Celery 计算
from confluent_kafka import Consumer
from tasks import calc_bond_ytm_task
import json

c = Consumer({
    "bootstrap.servers": "kafka:9092",
    "group.id": "bond-calc-group",
    "auto.offset.reset": "earliest",
})
c.subscribe(["bond-calc-tasks"])

while True:
    msg = c.poll(1.0)
    if msg is None or msg.error():
        continue
    data = json.loads(msg.value().decode())
    # 交给 Celery Worker 异步计算
    calc_bond_ytm_task.delay(data["task_id"], data["code"],
                             data["price"], data["coupon"])
    c.commit()

    5.3 任务定义：计算并写库

    # tasks.py —— Celery 任务
from celery import Celery
import pymysql

app = Celery("bond", broker="redis://redis:6379/0",
             backend="redis://redis:6379/1")

@app.task(bind=True, max_retries=3)
def calc_bond_ytm_task(self, task_id, code, price, coupon):
    try:
        ytm = (coupon * 100 + (100 - price)) / price   # 简化 YTM
        # 写库
        conn = pymysql.connect(host="mysql", user="bond",
                               password="bond@2024", database="bond")
        with conn.cursor() as cur:
            cur.execute("INSERT INTO bond_results(task_id, code, ytm) "
                        "VALUES (%s, %s, %s)", (task_id, code, ytm))
        conn.commit()
        return {"task_id": task_id, "ytm": ytm}
    except Exception as exc:
        raise self.retry(exc=exc, countdown=10)

    6. 面试高频题

    消息队列的作用和选型？

    参考要点：作用是解耦（服务不直接依赖）、削峰（抗流量洪峰）、异步（耗时操作后台执行）。 选型：高吞吐、大数据量、需要消息回溯选 Kafka；低延迟、灵活路由、业务任务分发选 RabbitMQ； 简单轻量、和 Redis 共用选 Redis Stream/List。结合团队熟悉度和运维成本。

    Kafka 为什么快？

    参考要点：1) 顺序写磁盘（追加写，比随机写快几个数量级）；2) 零拷贝（sendfile 系统调用， 数据不经用户态直接从磁盘到网卡）；3) 分区并行（多 partition 多消费者并行消费）； 4) 批量发送压缩（Producer 攒批 + 压缩，减少网络 IO）；5) Page Cache 利用操作系统缓存。

    如何保证消息不丢失？

    参考要点：三段保障。Producer 端：开启 ack 确认（Kafka acks=all）、 失败重试；Broker 端：多副本同步（replication.factor >= 3，min.insync.replicas >= 2）； Consumer 端：处理完业务再手动提交 offset，不要自动提交。

    分布式锁怎么实现？

    参考要点：Redis 用 SET key token NX EX seconds 原子加锁， value 用唯一 token，释放用 Lua 脚本判断 token 再删保证原子防误删，设过期时间防死锁， 看门狗续期。生产用 Redisson。对比 ZooKeeper 临时顺序节点方案（强一致、自动释放）。

    Celery 是什么，怎么用？

    参考要点：Celery 是 Python 分布式任务队列，由 Worker、Broker（Redis/RabbitMQ）、 Backend 组成。定义 @app.task 函数，调用 .delay() 提交异步任务， Worker 进程消费执行。支持定时任务（Beat）、重试、结果存储、Flower 监控。 用于邮件、报表、批量计算等耗时异步操作。

    Pandas 处理大数据怎么优化？

    参考要点：1) chunksize 分块读取；2) 列类型优化（低基数字符串转 category， 数值降位 int32/float32）；3) 向量化操作避免 for 循环；4) 用 Parquet 列式存储； 5) 只读取需要的列（usecols）；6) 数据量再大换 Polars/DuckDB/Spark。

    本章小结

    • Pandas 核心是 DataFrame/Series/索引，金融数据处理常用时间序列索引、groupby 聚合、rolling 滚动窗口。
    • Polars 用 Rust 实现、多线程惰性求值，千万级以上数据比 Pandas 快数倍，可与 Pandas 共存互补。
    • 大数据处理技巧：分块读取、类型优化（category/int32）、向量化、Parquet 列式存储。
    • 消息队列三大作用：解耦、削峰、异步；Kafka 高吞吐可回溯，RabbitMQ 低延迟灵活路由。
    • Kafka 高吞吐靠顺序写磁盘、零拷贝、分区并行、批量压缩；同 key 同分区保证顺序。
    • 消息不丢失靠三段：Producer ack、Broker 多副本、Consumer 处理完再提交 offset；重复消费靠幂等。
    • Celery = Worker + Broker + Backend，适合异步耗时任务（邮件、报表、批量计算），Beat 定时、Flower 监控。
    • 分布式系统核心：CAP 三选二、BASE 最终一致；分布式锁用 Redis SET NX + Lua 释放；雪花算法生成全局唯一 ID。
