    第 32 章 K8s 专题 约 40 分钟

    调度与弹性伸缩

    K8s 调度器决定「Pod 跑到哪个节点」，弹性伸缩决定「该跑多少副本」。本章从调度器 三段式流程（过滤→打分→绑定）切入，覆盖 nodeSelector、nodeAffinity、Pod 亲和/反亲和、 Taint/Toleration、ResourceQuota/LimitRange、HPA/VPA/Cluster Autoscaler 和 QoS 等级。 每节都贴了完整 YAML、生产经验和面试高频题，帮你把零散的调度知识点串成一条线。

    学习目标

    • 理解调度器 Filter → Score → Bind 三段式工作流程
    • 掌握 nodeSelector、nodeAffinity、pod 亲和/反亲和的写法和适用场景
    • 会用 Taint/Toleration 做节点专用化与维护驱逐
    • 会用 ResourceQuota + LimitRange 给 namespace 做资源配额
    • 掌握 HPA 工作原理和扩缩容算法，能落地 CPU/自定义指标扩缩
    • 理解 QoS 三等级与驱逐顺序、PriorityClass 抢占调度

    1. 调度器工作原理

    kube-scheduler 是 Master 上的一个组件，它监听新建的、还没绑定节点的 Pod （spec.nodeName 为空），按「过滤→打分→绑定」三段式 完成调度决策，最后通过 Patch 把 nodeName 写回给 apiserver，由目标节点的 kubelet 接手。

    调度流程一图流
               新建 Pod (nodeName 为空)
                  │
                  ▼
   ┌──────────────────────────────────┐
   │ 1. Filter 过滤（不可调度的节点） │
   │   - 资源不足 (CPU/Mem/GPU)      │
   │   - nodeSelector / nodeAffinity  │
   │   - taints (NoSchedule/NoExecute)│
   │   - volume 限制 (zone/节点独占)  │
   └──────────────┬───────────────────┘
                  │ 剩余可调度节点
                  ▼
   ┌──────────────────────────────────┐
   │ 2. Score 打分 (0~100，高者优)   │
   │   - LeastResourceUsed (空闲多+分高) │
   │   - BalancedResourceAllocation  │
   │   - NodeAffinityPriority        │
   │   - InterPodAffinityPriority    │
   │   - TaintTolerationPriority     │
   └──────────────┬───────────────────┘
                  │ 选最高分节点
                  ▼
   ┌──────────────────────────────────┐
   │ 3. Bind 绑定                     │
   │   scheduler → apiserver Patch   │
   │   spec.nodeName = 选中节点        │
   └──────────────┬───────────────────┘
                  │
                  ▼
            kubelet 在该节点创建 Pod
    调度决策考虑因素

    调度器综合考虑五大类因素：①资源（节点剩余 CPU/Mem/GPU 是否够 requests）； ②亲和性（nodeSelector/nodeAffinity 硬性或软性要求）； ③污点（节点 taint 是否被 Pod toleration 容忍）； ④Pod 间亲和（podAffinity/AntiAffinity 把副本靠近或分散）； ⑤volume 限制（如 EBS 单节点挂载上限、PV 的 nodeAffinity）。 只要过滤阶段不通过，Pod 就会一直是 Pending。

    2. nodeSelector（最简单）

    nodeSelector 是最老的节点选择方式：给节点打 label，Pod 里指定 nodeSelector，必须全部匹配才会被调度到该节点。 

    # 1. 给节点打标签
kubectl label nodes node-1 disktype=ssd
kubectl label nodes node-1 gpu=true

# 2. Pod 指定 nodeSelector
apiVersion: v1
kind: Pod
metadata:
  name: db
spec:
  nodeSelector:
    disktype: ssd        # 必须有这个标签的节点才考虑
  containers:
    - name: db
      image: mysql:8
    nodeSelector 是硬性要求

    nodeSelector 是逻辑 AND，所有条件都必须满足；只要没有任何节点满足， Pod 直接 Pending，没有「软性偏好」。需要「优先但不强制」时，要用 nodeAffinity 的 preferredDuringScheduling。

    3. nodeAffinity（更灵活）

    nodeAffinity 是 nodeSelector 的增强版，支持 In/NotIn/Exists 等运算符， 还区分硬性（required）和软性（preferred）两种语义， 生产基本替代 nodeSelector。 

    apiVersion: v1
kind: Pod
metadata:
  name: web
spec:
  affinity:
    nodeAffinity:
      # 硬性：必须满足，否则 Pending
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
          - matchExpressions:
              - key: disktype
                operator: In        # 在 [ssd, nvme] 中
                values: ["ssd", "nvme"]
      # 软性：能满足最好（按权重打分），不满足也调度
      preferredDuringSchedulingIgnoredDuringExecution:
        - weight: 80              # 权重 1~100
          preference:
            matchExpressions:
              - key: zone
                operator: In
                values: ["east-1"]   # 优先调度到 east-1
  containers:
    - name: web
      image: nginx:1.25
    nodeSelector vs nodeAffinity

    nodeSelector：只支持「等值匹配 AND」，写法简单，老的、简单场景用。
    nodeAffinity：支持 In/NotIn/Exists/Gt/Lt 运算符，分 required（硬）和 preferred（软）两种语义，可以「优先但不强制」。
    命名注意：requiredDuringSchedulingIgnoredDuringExecution 里的 "IgnoredDuringExecution" 意思是运行中不再生效—— Pod 已经在跑后节点 label 变了也不会驱逐，调度只在调度时算数。

    4. Pod 亲和与反亲和

    Pod 亲和/反亲和不是「和节点的关系」，而是「和别的 Pod 的关系」。 调度器根据拓扑域（topologyKey，通常用 kubernetes.io/hostname 或 topology.kubernetes.io/zone）来计算 Pod 之间的位置。

    4.1 podAffinity（靠近）

    # 前端 Pod 优先调度到有 app=backend 的节点
apiVersion: v1
kind: Pod
metadata:
  name: frontend
  labels:
    app: frontend
spec:
  affinity:
    podAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        - labelSelector:
            matchExpressions:
              - key: app
                operator: In
                values: ["backend"]
          topologyKey: kubernetes.io/hostname  # 在同一节点（主机域）
      # preferred 写法：尽量和 backend 同 zone
      preferredDuringSchedulingIgnoredDuringExecution:
        - weight: 50
          podAffinityTerm:
            labelSelector:
              matchExpressions:
                - key: app
                  operator: In
                  values: ["backend"]
            topologyKey: topology.kubernetes.io/zone
  containers:
    - name: frontend
      image: nginx:1.25

    4.2 podAntiAffinity（分散）

    # 同 Deployment 的副本尽量分散到不同节点
spec:
  affinity:
    podAntiAffinity:
      preferredDuringSchedulingIgnoredDuringExecution:
        - weight: 100
          podAffinityTerm:
            labelSelector:
              matchExpressions:
                - key: app
                  operator: In
                  values: ["web"]
            topologyKey: kubernetes.io/hostname
  containers:
    - name: web
      image: nginx:1.25
    生产建议用 podAntiAffinity 分散副本

    多副本 Deployment 必须用 podAntiAffinity 把副本分散到不同节点（或不同 zone）， 避免单节点故障导致业务全挂。写法：用 topologyKey: kubernetes.io/hostname 做硬性分散（副本数≤节点数），或用 zone topologyKey 做软性偏好分散到不同可用区。

    大规模集群注意 AntiAffinity 性能

    podAntiAffinity 的 required 语义会让调度器遍历所有节点上所有 Pod 做 label 匹配， 节点和 Pod 数量上去后调度会变慢。超过几百节点建议改用 Topology Spread Constraints（topologySpread），效果接近但性能更好。

    5. Taints 和 Tolerations

    Taint 给节点打「污点」，让 Pod 默认不愿调度上去；Toleration 是 Pod 端的「容忍」声明， 写了对应 Toleration 才能上污点节点。这是「排斥 Pod」的核心机制， 常用于节点专用化和维护驱逐。

    5.1 三种效果

    NoSchedule（不调度）

    不容忍该 taint 的新 Pod 不会被调度到该节点；已经在跑的 Pod 不受影响。 最常用，用于专用节点（如 GPU 节点）。

    PreferNoSchedule（尽量不调度）

    软性版本，调度器尽量避开，没其它选择时仍可调度上去。适合「倾向于专用但不绝对」。

    NoExecute（驱逐）

    不容忍该 taint 的 Pod 会被立刻驱逐（可加 tolerationSeconds 延迟驱逐）， 已有 Pod 也跑不掉。常用于节点维护时清场。

    5.2 命令与 YAML 示例

    # 1. 给节点打污点：专用 GPU 节点
kubectl taint nodes gpu-node-1 gpu=true:NoSchedule
# 删除污点
kubectl taint nodes gpu-node-1 gpu=true:NoSchedule-

# 2. Pod 容忍该污点才能调度上去
apiVersion: v1
kind: Pod
metadata:
  name: train-job
spec:
  tolerations:
    - key: "gpu"
      operator: "Equal"
      value: "true"
      effect: "NoSchedule"
    # 维护场景：容忍 maintain 污点，但只容忍 60 秒后驱逐
    - key: "node.kubernetes.io/maintenance"
      operator: "Exists"
      effect: "NoExecute"
      tolerationSeconds: 60
  containers:
    - name: train
      image: tensorflow/tensorflow:latest-gpu
    Master 节点为什么默认不上业务 Pod？

    K8s 用 kubeadm init 后，Master 自动被打上 node-role.kubernetes.io/control-plane:NoSchedule 污点 （旧版叫 master）。业务 Pod 没有 Toleration 自然不会调度到 Master， 从而保护控制平面不被业务 Pod 抢资源。需要时打 Toleration 才能上。

    典型场景

    ①专用节点：GPU/高 IO 节点打 taint，只让带 Toleration 的任务上。 ②节点维护：给节点打 node.kubernetes.io/maintenance:NoExecute 把所有 Pod 驱逐出去，再 drain 节点做内核升级。
    ③特殊硬件：云厂商自动给带 GPU 的节点打 taint，避免误调度。

    6. 资源配额管理

    没有 ResourceQuota 的集群，一个团队一个 Pod 就能把整个 namespace 资源吃光， 把别的 namespace 拖死。生产必须配 ResourceQuota + LimitRange 两层防护。

    6.1 ResourceQuota（namespace 总量限制）

    apiVersion: v1
kind: ResourceQuota
metadata:
  name: team-quota
  namespace: team-a
spec:
  hard:
    requests.cpu: "10"          # 所有 Pod 的 CPU requests 总和上限 10 核
    requests.memory: "20Gi"    # 内存 requests 上限 20Gi
    limits.cpu: "20"
    limits.memory: "40Gi"
    pods: "50"                  # 最多 50 个 Pod
    services.loadbalancers: "2" # LB 类型 Service 上限
    persistentvolumeclaims: "10"
    # 注意：开了 ResourceQuota 后，Pod 必须设 requests/limits，否则创建失败

    6.2 LimitRange（单个 Pod 限制）

    apiVersion: v1
kind: LimitRange
metadata:
  name: default-limits
  namespace: team-a
spec:
  limits:
    # 没设 resources 的 Pod 自动用以下默认值
    - type: Container
      default:                  # 默认 limits
        cpu: "500m"
        memory: "512Mi"
      defaultRequest:           # 默认 requests
        cpu: "100m"
        memory: "128Mi"
      max:                      # 单容器上限
        cpu: "2"
        memory: "4Gi"
      min:                      # 单容器下限
        cpu: "50m"
        memory: "64Mi"
    生产必须配 ResourceQuota + LimitRange

    ResourceQuota 限总量（防 namespace 间互相挤兑），LimitRange 限单个 Pod （防忘了设 requests 的 Pod 拿默认值炸节点）。两者一起，既能保护集群， 又能给开发者兜底默认值。开了 ResourceQuota 后，Pod 强制要求写 requests/limits。

    7. HPA 自动扩缩容（重点）

    HPA（HorizontalPodAutoscaler）根据 CPU/内存/自定义指标自动调整 Deployment/StatefulSet 副本数，是「横向扩缩」最常用的弹性能力。面试 K8s 弹性必考。

    7.1 HPA YAML 示例

    apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: web-hpa
  namespace: prod
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web-deploy
  minReplicas: 3                 # 最少 3 副本（保底）
  maxReplicas: 20                # 最多 20 副本（封顶）
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization      # 利用率指标
          averageUtilization: 60 # 目标 CPU 利用率 60%
    - type: Resource
      resource:
        name: memory
        target:
          type: Utilization
          averageUtilization: 70
  behavior:                      # v2 行为控制
    scaleDown:
      stabilizationWindowSeconds: 300  # 缩容冷却 5 分钟
      policies:
        - type: Percent
          value: 50              # 每次最多缩 50%
          periodSeconds: 60
    HPA 需要 Pod 设 requests

    HPA 的 CPU 利用率 = 实际 CPU / Pod requests。不设 requests 的 Pod， CPU 指标取不到，HPA 不工作。同时集群必须装 metrics-server（基础 CPU/Mem 指标），自定义指标需装 Prometheus Adapter 或 KEDA。

    7.2 扩缩容算法详解

    # 公式：期望副本数 = ceil(当前副本数 × 当前指标值 / 目标指标值)

# 例：当前 4 副本，CPU 平均 90%，目标 60%
期望副本 = ceil(4 × 90 / 60) = ceil(6.0) = 6
# 扩容到 6 副本

# 例：当前 6 副本，CPU 平均 30%，目标 60%
期望副本 = ceil(6 × 30 / 60) = ceil(3.0) = 3
# 缩容到 3 副本（受 minReplicas 限制）
    扩容快、缩容慢

    扩容：默认无冷却期，几秒内立即扩，配合流量突增。 但新 Pod 启动慢（拉镜像+应用启动）所以实际见效可能要几十秒到分钟级。
    缩容：默认有 5 分钟冷却（stabilizationWindowSeconds）， 防止指标抖动频繁缩容。缩容还会优雅终止 Pod，避免瞬时下线导致 502。 生产建议通过 behavior.scaleDown 显式配置冷却窗口和速率。

    8. VPA 和 Cluster Autoscaler 概述

    VPA（VerticalPodAutoscaler）

    自动调整 Pod 的 requests/limits，解决「容量预估不准」问题。 缺点：默认模式下改 requests 会重启 Pod （K8s 不支持运行中改 resources），所以生产用得少，且与 HPA 不能同时作用于同一资源 的同一指标。主要用在预估困难的中间件、批处理任务。

    Cluster Autoscaler

    云上 K8s 的节点级弹性组件，监控 Pending 的 Pod， 自动向云厂商 API 申请新节点加入集群；节点空闲超过阈值又会下线节点。 和 HPA 配合形成「HPA 横向扩 Pod，CA 纵向扩节点」的完整弹性链。 云原生等价物还有 Karpenter（AWS 出的开源新版，调度+扩缩节点一体）。

    9. QoS 等级与调度优先级

    K8s 根据 Pod 的 requests/limits 配置，把 Pod 分为三个 QoS （Quality of Service）等级。节点资源不足时，按等级决定谁先被驱逐。

    Guaranteed（保证级）

    每个 container 的 requests == limits（且 CPU/Mem 都要设）。 优先级最高，资源紧张时最后被驱逐，是生产关键业务的推荐配置。

    Burstable（突发级）

    至少一个 container 设了 requests 或 limits，但 requests < limits。 中间档，常见于一般业务。

    BestEffort（尽力级）

    完全不设 requests/limits 的 Pod。优先级最低，节点资源一紧张就先被驱逐， 不适合生产。

    节点资源不足时驱逐顺序

    kubelet 在节点资源紧张（如 MemoryPressure）时按以下顺序驱逐： BestEffort → Burstable（超额的）→ Guaranteed（超额的）。 换句话说不设 requests/limits 的 Pod 最先被牺牲。生产 Pod 至少配成 Burstable， 关键业务配 Guaranteed。

    9.1 PriorityClass 抢占调度

    # 1. 定义优先级
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: high-priority
value: 1000000               # 数值越大优先级越高
globalDefault: false
description: "Critical production workloads."

---
# 2. Pod 使用该优先级
apiVersion: v1
kind: Pod
metadata:
  name: critical-job
spec:
  priorityClassName: high-priority
  containers:
    - name: app
      image: myapp
    PriorityClass 与抢占

    高优先级 Pod 在资源不足无法调度时，可以抢占低优先级 Pod： 调度器先把节点上的低优先级 Pod 驱逐掉，把资源让给高优先级 Pod。 生产可用于关键业务（如支付、监控组件）保障，但要小心被抢占的 Pod 不要设 terminationGracePeriodSeconds 过大。

    10. 面试高频题

    10.1 「K8s 调度器怎么工作的？」

    参考答案要点

    ①kube-scheduler 监听 spec.nodeName 为空的新 Pod，做三段式调度： Filter 过滤 → Score 打分 → Bind 绑定。 ②Filter 用 Predicates 把不可调度节点排除（资源不足、nodeSelector 不匹配、taint 不被容忍、 volume 限制等）。③Score 用 Priorities 给剩余节点打分（LeastResourceUsed、 BalancedAllocation、Affinity、Toleration 等），选最高分节点。 ④通过 Patch 把 nodeName 写回 apiserver，kubelet 在该节点拉起容器。 ⑤调度只考虑过滤/打分时刻的状态，运行后节点 label 变了默认不影响已调度 Pod （IgnoredDuringExecution）。

    10.2 「说说 Taint 和 Toleration」

    参考答案要点

    ①Taint 给节点打「污点」，Toleration 是 Pod 端的容忍声明，写了对应 Toleration 才能上污点节点。 ②三种 effect：NoSchedule（不调度新 Pod）、PreferNoSchedule（软性避开）、 NoExecute（驱逐已有 Pod，可用 tolerationSeconds 延迟）。③典型场景： Master 自动有 control-plane 污点挡业务 Pod；GPU/专用节点打 taint 做节点专用化； 节点维护用 NoExecute + drain 驱逐 Pod；云厂商对带 GPU 的节点自动打 taint。 ④和 nodeAffinity 区别：Taint 是「节点主动排斥 Pod」，Affinity 是「Pod 主动挑节点」， 二者配合能实现「专用节点 + 专用 Pod」双向匹配。

    10.3 「HPA 怎么工作的？」

    参考答案要点

    ①HPA（HorizontalPodAutoscaler）根据 CPU/内存/自定义指标自动调整 Deployment 副本数。 ②依赖 metrics-server 拿基础指标，自定义指标需 Prometheus Adapter 或 KEDA。 ③核心算法：期望副本 = ceil(当前副本 × 当前指标 / 目标指标)， 每 15 秒（默认）算一次。④前置条件：Pod 必须设 requests，否则 CPU 利用率算不出来。 ⑤行为：扩容无冷却快速扩，缩容有默认 5 分钟冷却 + 速率限制防抖动。 ⑥配合 Cluster Autoscaler 形成「横向扩 Pod + 纵向扩节点」的完整弹性链。

    10.4 「QoS 等级有什么用？」

    参考答案要点

    ①QoS 是 K8s 根据 Pod 的 requests/limits 自动算出来的等级，分 Guaranteed、Burstable、BestEffort。 ②Guaranteed 要求每个 container 的 requests==limits 且 CPU/Mem 都设，是最稳的等级。 ③作用：节点资源不足时 kubelet 按 BestEffort → Burstable → Guaranteed 的顺序 驱逐 Pod，QoS 高的最后被驱逐，等于给关键业务上了资源保险。 ④生产建议：关键业务配 Guaranteed，普通业务至少 Burstable，禁止 BestEffort 跑生产。 ⑤PriorityClass 控制的是调度优先级（能不能抢占别人）， 和 QoS 的运行优先级（能不能不被驱逐）是两件事，但都重要。

    本章小结

    • 调度器三段式：Filter 过滤 → Score 打分 → Bind 绑定 nodeName，调度只看调度时刻状态。
    • nodeSelector 是硬性等值匹配；nodeAffinity 支持 In/NotIn/Exists 和软硬两种语义，生产优先选。
    • podAntiAffinity + topologyKey 把副本分散到不同节点/zone，避免单节点故障全挂。
    • Taint 排斥 Pod，Toleration 容忍污点；Master 默认有 control-plane 污点挡业务 Pod。
    • 三种 effect：NoSchedule（不调度新 Pod）、PreferNoSchedule（软避）、NoExecute（驱逐已有 Pod）。
    • ResourceQuota 限 namespace 总量、LimitRange 限单 Pod 默认值和上下限，生产两层必配。
    • HPA 公式：期望副本 = ceil(当前副本 × 当前指标 / 目标指标)，扩容快、缩容有冷却，依赖 requests 和 metrics-server。
    • QoS 三等级：Guaranteed（requests==limits）> Burstable > BestEffort，节点压力下 BestEffort 先被驱逐。
