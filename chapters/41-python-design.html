    1. 系统设计核心原则

    系统设计不是"画架构图"那么简单，它本质上是在约束条件下做取舍。 没有银弹，但有一些经过几十年工程实践检验的原则，可以帮你少走弯路。

    1.1 SOLID 原则简述

    SOLID 是五个面向对象设计原则的首字母缩写，是模块拆分和接口设计的底层指导思想：

    S — 单一职责原则（SRP）

    一个类/模块只做一件事，只有一个引起它变化的原因。比如 BondPricingService 只负责债券定价，不该同时负责生成研究报告，否则定价逻辑改动会连带影响报告生成。

    O — 开闭原则（OCP）

    对扩展开放，对修改关闭。新增一种债券类型（如永续债）时，应该通过新增策略类实现， 而不是去修改原来的利率债定价函数，避免引入回归 bug。

    L — 里氏替换原则（LSP）

    子类必须能替换父类而不破坏程序行为。若 FixedRateBond 继承 Bond， 那么所有接受 Bond 的地方都应能正确处理 FixedRateBond。

    I — 接口隔离原则（ISP）

    客户端不应该依赖它不需要的接口。把一个胖接口拆成多个小接口， 使用者只实现自己需要的方法，避免被迫实现一堆空方法。

    D — 依赖倒置原则（DIP）

    高层模块不依赖低层模块，两者都依赖抽象；抽象不依赖细节，细节依赖抽象。 Service 层依赖 BondRepository 接口，而不是具体的 MySQL 实现， 这样换 PostgreSQL 时 Service 不用改。

    1.2 高内聚、低耦合

    高内聚：把相关的功能放在一起，一个模块内部的元素联系紧密。 低耦合：模块之间依赖尽量少、尽量松，改一个模块不牵连其他模块。 这两个原则是判断模块拆分是否合理的核心标准。

    判断口诀："改一个需求，要不要同时改好几个文件？"如果要，说明耦合高了； "一个文件里是不是混了好几件不相关的事？"如果是，说明内聚低了。

    1.3 KISS 与 YAGNI

    • KISS（Keep It Simple, Stupid）：保持简单。能用三行代码解决， 就别引入一个框架。过度设计是初学者最常犯的错。
    • YAGNI（You Aren't Gonna Need It）：你不会用到它。 别为"将来可能需要"提前加功能，需求会变，提前加的代码大概率用不上还徒增维护成本。
    原则是指导思想，不是教条

    SOLID、高内聚低耦合、KISS/YAGNI 这些原则是模块拆分的指导思想， 不是必须逐条满足的硬性指标。实际项目中要在原则和现实之间做权衡： 比如为了赶进度，单一职责可以适度放宽；但依赖倒置在涉及数据库、外部服务的地方一定要守住， 否则后期替换成本极高。原则的价值在于让你在写代码前先想一想，而不是写完再重构。

    2. 模块拆分与接口设计

    有了原则指导，接下来看具体怎么落地。Python 后端项目最经典的组织方式是 分层架构，在每一层内部再按业务领域拆模块。

    2.1 分层架构：Controller / Service / Repository

    三层架构是 Python Web 项目的事实标准，每一层职责单一、依赖方向明确：

    三层架构调用关系
       ┌─────────────────────────────────────────────┐
   │              HTTP 请求 / RPC 调用            │
   └──────────────────────┬──────────────────────┘
                          ▼
   ┌─────────────────────────────────────────────┐
   │  Controller 层（api/）                       │
   │  · 接收请求、参数校验、权限校验              │
   │  · 调用 Service，组装响应                    │
   │  · 不写业务逻辑                              │
   └──────────────────────┬──────────────────────┘
                          ▼
   ┌─────────────────────────────────────────────┐
   │  Service 层（service/）                      │
   │  · 核心业务逻辑（定价、风控、报表生成）      │
   │  · 事务控制、组合多个 Repository             │
   │  · 不关心数据存在哪（依赖 Repository 接口）  │
   └──────────────────────┬──────────────────────┘
                          ▼
   ┌─────────────────────────────────────────────┐
   │  Repository 层（repository/）                │
   │  · 数据访问（MySQL/Redis/ES）                │
   │  · 封装 SQL / ORM 操作                       │
   │  · 向上暴露领域无关的查询接口                │
   └──────────────────────┬──────────────────────┘
                          ▼
                  ┌───────────────┐
                  │   数据存储     │
                  │ MySQL/Redis   │
                  └───────────────┘

    依赖方向是单向的：Controller → Service → Repository，上层依赖下层的抽象接口， 而不是具体实现。这样替换数据库、拆分服务时，影响范围可控。

    2.2 模块拆分的依据

    分层解决了"上下怎么分"，那同一层内部"左右怎么分"？三个依据：

    • 业务领域：按业务边界拆。债券研究系统里，债券查询、收益率计算、 风险评估、报告生成是四个独立领域，各自一个 module。
    • 变化频率：变化频繁的和稳定的分开。定价模型经常迭代， 而基础数据查询很稳定，就把定价服务独立出来，避免频繁改动波及稳定代码。
    • 依赖方向：被依赖多的（基础组件）和依赖别人多的（业务编排）分开。 common 放工具类，service 放业务逻辑，避免循环依赖。

    2.3 接口定义原则

    • 最小化：接口只暴露必要的方法，内部实现细节藏起来。 Repository 对外暴露 get_bond_by_code()，不要把 SQL 拼接暴露给 Service。
    • 稳定：接口一旦发布就尽量不改签名。必须改时走版本化： URL 加 /v2/，或新方法并存，旧方法标记 deprecated，给迁移留时间。
    • 语义清晰：方法名、参数、返回值自解释。calc_yield(bond, date) 比 do_calc(b, d) 好一万倍。

    2.4 依赖注入（DI）解耦

    依赖倒置原则的落地手段就是依赖注入：不在类内部 new 依赖对象， 而是由外部传入。这样便于替换实现、便于单元测试（注入 Mock）。 

    # 不推荐：Service 内部硬编码依赖，无法替换、无法测
class YieldService:
    def __init__(self):
        self.repo = BondRepository()   # 硬编码，耦合死了

    def calc(self, code):
        bond = self.repo.get_by_code(code)
        ...

# 推荐：通过构造函数注入依赖，实现可替换、可测试
class YieldService:
    def __init__(self, repo: BondRepository):
        self.repo = repo               # 由外部注入

    def calc(self, code):
        bond = self.repo.get_by_code(code)
        ...

# 测试时注入 Mock，不需要真连数据库
from unittest.mock import MagicMock
repo = MagicMock()
repo.get_by_code.return_value = Bond(code="019656", ...)
service = YieldService(repo)
assert service.calc("019656") > 0

    3. 扩展性与可靠性设计

    系统能跑起来只是 60 分，能扛住流量、能在故障时自我保护才是 90 分。 扩展性解决"扛得住"，可靠性解决"不出事"。

    3.1 水平扩展 vs 垂直扩展

    • 垂直扩展（Scale Up）：给单台机器加 CPU/内存。简单但有上限， 单机性能到顶后无法继续，且是单点故障。
    • 水平扩展（Scale Out）：加机器数量。通过负载均衡把流量分散到多实例， 无上限（理论上），且天然容灾。Python 后端首选水平扩展。

    水平扩展的前提是无状态：任何一个请求落到任何一个实例都能正确处理， 不依赖本机内存里的状态。

    3.2 无状态设计

    有状态的服务无法水平扩展（用户的 Session 存在某台机器上，下次请求落到别的机器就丢了）。 解决办法：把状态外置到共享存储。 

    # Flask 中把 Session 存储到 Redis，实现应用层无状态
from flask import Flask
from flask_session import Session
import redis

app = Flask(__name__)
app.config["SESSION_TYPE"] = "redis"
app.config["SESSION_REDIS"] = redis.Redis(host="redis-server", port=6379)
Session(app)  # 之后 session 数据全部存 Redis，多实例共享

# 这样部署多个 gunicorn worker 时，用户登录态在所有实例间通用

    3.3 限流

    限流防止流量洪峰打垮服务。两种经典算法：

    • 令牌桶（Token Bucket）：桶里以固定速率生成令牌，请求来时消耗一个令牌， 没令牌就拒绝。允许突发流量（桶里攒的令牌可以一次性用光）。
    • 漏桶（Leaky Bucket）：请求进入桶，以固定速率流出处理。 流量被强行平滑，不允许突发。适合写入类接口。

    生产环境通常用 Redis + Lua 实现分布式限流，保证多实例共享限流计数。

    3.4 降级与熔断

    • 降级（Degradation）：系统压力大或依赖故障时，主动关闭非核心功能， 保住核心链路。比如行情查询超时，降级为返回缓存的上一笔价格，而不是让整个接口报错。
    • 熔断（Circuit Breaker）：当依赖服务连续失败达到阈值， 暂时切断对它的调用（"打开熔断器"），直接返回降级结果。一段时间后放一小部分请求试探， 恢复了就关闭熔断器。类似电路保险丝，防止故障蔓延。

    3.5 幂等性设计

    幂等：同一操作执行一次和执行多次，结果相同。 网络重试、消息重复投递都可能导致同一请求被处理多次，写接口必须保证幂等。

    常见实现手段：

    • 唯一请求 ID：客户端生成 request_id，服务端用 Redis 记录已处理的 ID， 重复请求直接返回上次结果。
    • 数据库唯一索引：如订单号建唯一索引，重复插入会报唯一键冲突， 捕获后返回成功。
    • 状态机：只有状态为"待支付"时才能扣减，已支付则忽略，用状态流转防重。

    3.6 重试机制与退避策略

    调用下游失败时自动重试可以提高成功率，但要注意：

    • 只对幂等接口重试，否则会重复扣钱。
    • 用指数退避（Exponential Backoff）：第 1 次等 100ms，第 2 次 200ms， 第 3 次 400ms……避免打爆下游。
    • 加重试上限（最多 3 次）和超时，避免无限等待。
    import time
import random

def retry_with_backoff(func, max_retries=3, base_delay=0.1):
    """指数退避 + 随机抖动的重试装饰器"""
    for attempt in range(max_retries):
        try:
            return func()
        except Exception as e:
            if attempt == max_retries - 1:
                raise  # 最后一次还失败，抛出
            # 指数退避 + 抖动（jitter），防止多实例同时重试形成惊群
            delay = base_delay * (2 ** attempt) + random.uniform(0, 0.1)
            time.sleep(delay)

# 使用：调用行情接口，失败自动重试
retry_with_backoff(lambda: fetch_market_data("019656"))
    可靠性设计自查清单
    • ✅ 服务是否无状态？状态是否都在 Redis/DB 里？
    • ✅ 核心接口是否有限流？（防止流量打垮）
    • ✅ 依赖下游失败时是否有降级/熔断？（防止故障蔓延）
    • ✅ 所有写接口是否保证幂等？（防止重复提交）
    • ✅ 失败重试是否只针对幂等接口？是否有退避和上限？
    • ✅ 是否有完整的监控告警？（P99 延迟、错误率、QPS）
    • ✅ 是否有数据备份和灾备预案？（数据安全底线）

    4. Python 常用设计模式

    设计模式是前人总结的"解决特定问题的套路"。Python 因为语言特性灵活， 很多模式的实现比 Java 简洁。下面介绍五种后端最常用的模式，每个都给代码示例和适用场景。

    4.1 单例模式（Singleton）

    保证一个类只有一个实例，并提供全局访问点。常用于配置对象、数据库连接池、日志器。

    Python 实现单例有三种常见方式：

    # 方式一：模块级实例（最简单，Python 最推荐）
# config.py
class Config:
    def __init__(self):
        self.db_url = "mysql://..."
        self.redis_url = "redis://..."

config = Config()  # 模块只加载一次，天然单例

# 其他文件：from config import config，拿到的永远是同一个实例

# 方式二：装饰器
def singleton(cls):
    instances = {}
    def get_instance(*args, **kwargs):
        if cls not in instances:
            instances[cls] = cls(*args, **kwargs)
        return instances[cls]
    return get_instance

@singleton
class DatabasePool:
    def __init__(self):
        self.pool = create_engine_pool()

# 方式三：元类（metaclass）
class SingletonMeta(type):
    _instances = {}
    def __call__(cls, *args, **kwargs):
        if cls not in cls._instances:
            cls._instances[cls] = super().__call__(*args, **kwargs)
        return cls._instances[cls]

class Logger(metaclass=SingletonMeta):
    pass

    适用场景：全局唯一的配置、连接池、日志器。注意多线程下要加锁， 模块级实例因为 CPython 的 GIL 和模块加载机制，天然线程安全。

    4.2 工厂模式（Factory）

    把对象创建逻辑封装起来，调用方不关心具体实例化哪个类。适合"根据条件创建不同对象"的场景。

    from abc import ABC, abstractmethod

# 抽象产品
class Bond(ABC):
    @abstractmethod
    def calc_coupon(self) -> float:
        ...

# 具体产品
class FixedRateBond(Bond):
    def calc_coupon(self):
        return self.face * self.coupon_rate

class FloatingRateBond(Bond):
    def calc_coupon(self):
        return self.face * (self.base_rate + self.spread)

class ZeroCouponBond(Bond):
    def calc_coupon(self):
        return 0.0

# 工厂
class BondFactory:
    @staticmethod
    def create(bond_type: str, **kwargs) -> Bond:
        if bond_type == "fixed":
            return FixedRateBond(**kwargs)
        elif bond_type == "floating":
            return FloatingRateBond(**kwargs)
        elif bond_type == "zero":
            return ZeroCouponBond(**kwargs)
        else:
            raise ValueError(f"未知债券类型: {bond_type}")

# 调用方无需知道具体类，只管传类型
bond = BondFactory.create("fixed", face=100, coupon_rate=0.03)
print(bond.calc_coupon())  # 3.0

    适用场景：多种相似产品、需要根据配置/输入动态选择实现时。 新增债券类型只需加一个类并在工厂注册，符合开闭原则。

    4.3 策略模式（Strategy）

    定义一族算法，把每个算法封装成独立的策略类，使它们可以互相替换。 FICC 业务里定价就是典型场景：不同债券类型用不同定价模型。

    from abc import ABC, abstractmethod

# 策略接口
class PricingStrategy(ABC):
    @abstractmethod
    def price(self, bond, market_data) -> float:
        ...

# 具体策略：利率债用现金流贴现
class CashFlowDiscountStrategy(PricingStrategy):
    def price(self, bond, market_data):
        # 简化：把未来每期票息和本金按市场利率贴现
        pv = sum(cf / (1 + market_data["rate"]) ** t
                 for t, cf in enumerate(bond.cashflows))
        return pv

# 具体策略：可转债用二叉树/蒙特卡洛
class ConvertibleBondStrategy(PricingStrategy):
    def price(self, bond, market_data):
        # 简化：用蒙特卡洛模拟股价路径计算期权价值
        return self._monte_carlo(bond, market_data)

# 上下文：持有一个策略，动态切换
class BondPricer:
    def __init__(self, strategy: PricingStrategy):
        self.strategy = strategy

    def set_strategy(self, strategy: PricingStrategy):
        self.strategy = strategy

    def price(self, bond, market_data):
        return self.strategy.price(bond, market_data)

# 使用：不同债券用不同策略
pricer = BondPricer(CashFlowDiscountStrategy())
price = pricer.price(rate_bond, market_data)

pricer.set_strategy(ConvertibleBondStrategy())
price = pricer.price(convertible_bond, market_data)

    适用场景：同一问题有多种算法/规则，需要运行时切换。 比用大量 if-else 清晰得多，新增定价模型只需加一个策略类。

    4.4 观察者模式（Observer）

    定义对象间一对多的依赖关系，当一个对象状态改变时，所有依赖它的对象自动收到通知。 适合事件驱动、消息通知场景。

    class MarketDataSubject:
    """行情发布者（被观察者）"""
    def __init__(self):
        self._observers = []

    def attach(self, observer):
        self._observers.append(observer)

    def detach(self, observer):
        self._observers.remove(observer)

    def notify(self, data):
        for obs in self._observers:
            obs.update(data)

    def update_price(self, code, price):
        self.notify({"code": code, "price": price})

class YieldCurveObserver:
    """观察者：收益率曲线服务，行情变化时重算曲线"""
    def update(self, data):
        print(f"[收益率曲线] 更新: {data}")

class RiskMonitorObserver:
    """观察者：风控监控，行情变化时重算 VaR"""
    def update(self, data):
        print(f"[风控] 重算风险指标: {data}")

# 使用
subject = MarketDataSubject()
subject.attach(YieldCurveObserver())
subject.attach(RiskMonitorObserver())
subject.update_price("019656", 100.25)  # 两个观察者都会收到通知

    适用场景：事件通知、解耦发布者与订阅者。Python 中也常用信号机制 （如 Django signal、blinker 库）实现观察者模式。

    4.5 适配器模式（Adapter）

    把一个类的接口转换成客户端期望的另一个接口，让不兼容的类能协作。 常用于对接第三方接口、遗留系统改造。

    # 第三方行情接口（接口不兼容我们的系统）
class ThirdPartyMarketAPI:
    def query(self, symbol):
        return {"sym": symbol, "px": 100.25, "dt": "2026-09-23"}

# 我们系统期望的接口
class MarketDataProvider:
    def get_price(self, code: str) -> dict:
        ...

# 适配器：把第三方接口转成我们期望的格式
class MarketAdapter(MarketDataProvider):
    def __init__(self, api: ThirdPartyMarketAPI):
        self.api = api

    def get_price(self, code: str) -> dict:
        raw = self.api.query(code)
        # 字段名转换 + 格式标准化
        return {"code": raw["sym"], "price": raw["px"], "date": raw["dt"]}

# 客户端只认 MarketDataProvider 接口
def display(provider: MarketDataProvider, code):
    data = provider.get_price(code)
    print(f"{data['code']} 最新价: {data['price']}")

api = ThirdPartyMarketAPI()
adapter = MarketAdapter(api)
display(adapter, "019656")  # 输出：019656 最新价: 100.25

    适用场景：对接第三方接口、兼容旧代码、统一多种异构数据源。 适配器是"胶水层"，让系统内部保持一致的接口约定。

    6. 面试高频题汇总（30+ 题）

    下面按模块整理 Python 后端面试高频题，每题给出精要参考答案要点。 面试时不要死记硬背，要结合自己的项目经验展开讲。

    6.1 Python 基础（8 题）

    Q1. 装饰器的原理和执行顺序？

    装饰器本质是"函数的函数"：接收被装饰函数作为参数，返回一个新函数（包装器）， 在不修改原函数代码的前提下增强功能。底层基于闭包和函数是一等公民。 执行顺序：定义时从下往上应用装饰器，调用时从上往下执行。 多个装饰器叠加时，靠近函数的先被包装。用 @functools.wraps 保留原函数元信息。

    Q2. 生成器和迭代器的区别？

    迭代器是实现了 __iter__ 和 __next__ 方法的对象， 可以被 for 遍历，惰性计算。生成器是一种特殊的迭代器， 用 yield 关键字实现，写法更简洁，每次 yield 暂停并返回值， 下次 next 时从暂停处继续。生成器一定是迭代器，但迭代器不一定是生成器。 好处是省内存（惰性求值，适合处理大数据流/文件）。

    Q3. 上下文管理器的实现方式？

    两种方式：① 基于类：实现 __enter__ 和 __exit__ 方法， with 进入时调用 __enter__，退出时调用 __exit__ （异常也会传入 __exit__，返回 True 可吞掉异常）。 ② 基于生成器 + @contextlib.contextmanager 装饰器， yield 前是 enter 逻辑，yield 后是 exit 逻辑，写法更简洁。 常用于资源释放（文件、锁、数据库连接）。

    Q4. is 和 == 的区别？

    == 比较的是值（调用 __eq__ 方法）， is 比较的是内存地址（即 id() 是否相同）。 所以 a == b 为 True 不代表 a is b 为 True。 特例：小整数（-5~256）和短字符串在 CPython 中有缓存，is 也为 True， 但不要依赖这个特性。判断 None 时用 is None 是最佳实践。

    Q5. Python 垃圾回收机制？

    主要用引用计数：对象被引用时计数 +1，释放时 -1， 计数为 0 立即回收。优点是实时，缺点是无法解决循环引用。 所以辅以分代回收（Generational GC）：把对象按存活时间分三代， 新对象频繁扫描，老对象少扫描，用 gc 模块触发，专门处理循环引用。 另外还有标记-清除算法辅助。

    Q6. *args 和 **kwargs 的作用？

    *args 收集任意数量的位置参数为元组， **kwargs 收集任意数量的关键字参数为字典。 两者可混用，顺序必须是 *args 在 **kwargs 前。 常用于函数参数不固定的场景（如装饰器、转发参数）。 同样可以在调用函数时用 * 和 ** 解包列表/字典为参数。

    Q7. 深浅拷贝的区别？

    浅拷贝（copy.copy()、切片、list()）： 只复制最外层对象，内部嵌套对象仍是引用，改嵌套对象会影响原对象。 深拷贝（copy.deepcopy()）：递归复制所有层级， 新旧对象完全独立，互不影响。性能上深拷贝更慢、更占内存。 对于不可变对象（int/str/tuple），深浅拷贝结果一样（都指向原对象）。

    Q8. GIL 是什么，有什么影响？

    GIL（全局解释器锁）是 CPython 的机制：同一时刻只允许一个线程执行 Python 字节码。 影响：CPU 密集型任务多线程无法利用多核（反而因线程切换变慢）， 要用多进程；IO 密集型任务（网络请求、文件读写）多线程有效， 因为 IO 等待时 GIL 会释放。Python 3.7+ 对 GIL 有优化（基于请求时间的切换）， 但本质没变。想真正并行用 multiprocessing 或 asyncio。

    6.2 Web 开发（6 题）

    Q1. Flask 和 Django 的区别？

    Flask 是微框架，核心只提供路由和请求响应，其他靠插件扩展， 灵活轻量，适合小项目、API 服务、快速原型。Django 是全栈框架， 自带 ORM、Admin、Auth、模板引擎，"电池齐全"，约定大于配置，适合中大型项目、 内容管理系统。选型看团队规模和项目复杂度：快速灵活选 Flask，功能完备选 Django。

    Q2. RESTful 设计原则？

    核心是"资源"和"HTTP 动词"对应：用 URL 表示资源（名词复数，如 /api/bonds）， 用 HTTP 方法表示操作（GET 查、POST 增、PUT 改、DELETE 删）。 无状态、统一接口、用状态码表达结果（200/201/400/404/500）。 版本化（/api/v1/）、分页、过滤用 query 参数。 返回 JSON，错误信息结构化。

    Q3. JWT 和 Session 的区别？

    Session：服务端存储会话，客户端存 session_id（Cookie）， 服务端查 session 验证。优点可随时失效，缺点分布式需共享存储（Redis）。 JWT：令牌自包含（header.payload.signature），服务端不存， 验签即可。优点无状态、天然支持分布式，缺点无法主动失效（除非黑名单）、 令牌较大。微服务/跨域场景用 JWT 更方便。

    Q4. Django ORM select_related vs prefetch_related？

    都是解决 N+1 查询问题。select_related：用 SQL JOIN 一次查出关联对象， 只支持外键和一对一（Forward ForeignKey、OneToOne）， 减少查询次数但单次查询结果大。prefetch_related： 分两次查询（先查主表，再用 IN 查关联表），Python 层拼装， 支持多对多、反向外键。一对一/外键用 select_related， 多对多用 prefetch_related。

    Q5. 蓝图（Blueprint）的作用？

    蓝图是 Flask 的模块化机制，把路由、模板、静态文件按功能拆分到不同模块， 实现代码组织和复用。好处：① 大型项目按业务分文件（如 bond_bp、yield_bp）， 避免所有路由堆在一个文件；② 蓝图可挂载到不同 URL 前缀（如 /api/v1）； ③ 同一蓝图可多次注册（带不同前缀）。

    Q6. 中间件和钩子的区别？

    中间件（Middleware）：在请求和响应的外层包裹， 可以对所有请求/响应做统一处理（如日志、CORS、鉴权）， Django 的 MIDDLEWARE、FastAPI 的中间件都是这种。 钩子（Hook）：在请求生命周期的特定时点触发， 如 Flask 的 before_request、after_request、 teardown_request，更灵活但作用粒度更细。 中间件是全局管道，钩子是特定回调。

    6.3 数据库与缓存（6 题）

    Q1. 索引为什么用 B+ 树？

    B+ 树特点：① 非叶子节点只存索引不存数据，能存更多索引，树更矮（一般 3-4 层）， 减少磁盘 IO；② 叶子节点用链表相连，范围查询只需遍历链表，效率高； ③ 查询稳定，每次都走到叶子节点。相比 B 树（数据存在所有节点）， B+ 树更适合数据库的磁盘存储和范围查询场景。

    Q2. 覆盖索引是什么？

    查询所需的列全部包含在索引中，数据库只需读索引（在内存中）就能返回结果， 无需回表查主键索引对应的行数据，性能高。 例如表有联合索引 (name, age)，SELECT age FROM user WHERE name='x' 就是覆盖索引。Explain 中 Extra 显示 Using index 表示用到了覆盖索引。

    Q3. 缓存穿透/击穿/雪崩的区别和解决方案？

    穿透：查的数据不存在，缓存没命中直接打 DB。 解决：缓存空值、布隆过滤器过滤。击穿：某个热点 key 过期， 大量并发请求同时打 DB。解决：互斥锁（只放一个请求查 DB）、永不过期 + 异步刷新。 雪崩：大量 key 同时过期或 Redis 宕机，DB 瞬间被打垮。 解决：过期时间加随机值、Redis 集群高可用、多级缓存、限流降级。

    Q4. Redis 为什么快？

    四个原因：① 纯内存操作，IO 极快；② 单线程模型，避免线程切换和锁竞争 （Redis 6.0 后网络 IO 多线程，但命令执行仍单线程）；③ IO 多路复用（epoll）， 单线程高效处理大量并发连接；④ 高效数据结构（SDS、跳表、压缩列表等）， 针对不同场景优化。

    Q5. MySQL 事务隔离级别？

    四种级别，从低到高：① 读未提交（RU）：能读到未提交数据，有脏读； ② 读已提交（RC）：只能读已提交数据，解决脏读，有不可重复读（Oracle 默认）； ③ 可重复读（RR）：同一事务内多次读结果一致，解决不可重复读， 有幻读（MySQL 默认，用 next-key lock 缓解幻读）； ④ 串行化：最高级别，事务串行执行，解决所有问题但性能差。 级别越高并发越低。

    Q6. 数据库连接池的作用？

    数据库连接创建/销毁开销大（TCP 握手、认证）。连接池预先创建一批连接复用， 请求来了直接拿，用完归还不关闭。好处：① 减少连接创建开销，提升响应速度； ② 控制并发连接数，防止 DB 被打爆；③ 统一管理连接（超时、探活）。 Python 常用 DBUtils.PooledDB、SQLAlchemy 的 pool、 Django 的 CONN_MAX_AGE。

    6.4 并发编程（4 题）

    Q1. 多线程和多进程的区别？

    多线程：同一进程内共享内存，通信方便，创建开销小， 但受 GIL 限制，CPU 密集型无法并行。多进程：每个进程独立内存空间， 不受 GIL 限制，能真正利用多核，适合 CPU 密集型；但进程间通信（管道/队列/共享内存）复杂， 创建开销大。总结：IO 密集用多线程/协程，CPU 密集用多进程。

    Q2. GIL 对并发的影响？

    GIL 让同一进程内同一时刻只有一个线程执行字节码。所以：CPU 密集型任务多线程没用， 甚至更慢（线程切换开销）；IO 密集型有效，因为 IO 阻塞时 GIL 释放，其他线程可执行。 想绕开 GIL：用多进程（multiprocessing）、用 C 扩展（如 numpy 释放 GIL）、 用协程（asyncio 单线程并发，绕过线程切换）。

    Q3. 什么时候用 AsyncIO？

    AsyncIO 是单线程协程并发，适合高并发 IO 密集型场景： 大量网络请求（爬虫、API 网关、微服务调用）、WebSocket、实时聊天。 不适合 CPU 密集型（协程不释放 GIL，CPU 任务会阻塞事件循环）。 优点：比多线程开销小（协程切换无内核态切换），单线程无锁竞争； 缺点：整个生态需异步支持（aiohttp/aioredis），不能混用阻塞调用。

    Q4. 协程和线程的区别？

    线程：内核调度的最小单位，有独立栈，切换涉及内核态（开销大）， 有数据竞争需加锁。协程：用户态调度的轻量级"线程"， 切换在用户态完成（开销极小），由程序主动让出（await），单线程内无锁竞争。 协程本质是函数，一个线程可跑上万个协程，适合高并发 IO；线程受内核调度， 数量受限（几千个就有压力）。

    6.5 工程化与分布式（5 题）

    Q1. CI/CD 流程是怎样的？

    CI（持续集成）：代码 push 后自动拉取、安装依赖、 跑单元测试/静态检查（flake8/mypy）、构建镜像，通过后合并到主干。 CD（持续交付/部署）：镜像推送到仓库，自动部署到测试/预发/生产环境， 生产环境通常加审批或灰度。常用工具：GitLab CI、Jenkins、GitHub Actions。 核心价值：频繁小步发布，降低风险，自动化减少人为错误。

    Q2. 单元测试怎么写？

    用 pytest（主流）或 unittest。 原则：① 每个测试只测一个功能，命名清晰（test_功能_场景_预期）； ② 用 fixture 准备测试数据和 mock 依赖； ③ 外部依赖（DB/网络）用 unittest.mock 打桩，保证测试独立可重复； ④ 断言明确（assert 结果 == 预期）。覆盖率目标 70%+，核心逻辑 100%。 配合 pytest-cov 看覆盖率。

    Q3. 消息队列的作用？

    三大作用：① 异步：耗时操作（发邮件、生成报告）丢到队列， 接口立即返回，提升响应速度；② 解耦：生产者只管发消息， 消费者独立处理，互不依赖，新增消费者不改生产者；③ 削峰： 流量洪峰时消息堆积在队列，消费者慢慢消费，保护下游 DB。 常见：RabbitMQ（功能全）、Kafka（高吞吐日志）、Redis Stream（轻量）。

    Q4. 分布式锁怎么实现？

    常用三种：① Redis：SET key value NX EX 30 原子加锁，value 用唯一标识（如 UUID），释放时用 Lua 脚本校验 value 后删除， 防止误删别人的锁；要设置过期时间防死锁。② ZooKeeper： 用临时顺序节点，最小节点获取锁，监听前一个节点释放，自动续期。 ③ 数据库：唯一索引/for update 行锁，实现简单但性能差。 生产首选 Redis（Redisson 框架封装了续期和可重入）。

    Q5. Celery 架构是怎样的？

    Celery 是 Python 分布式任务队列，三组件：① Producer： 业务代码调用 task.delay() 把任务发到 Broker； ② Broker：消息中间件（Redis/RabbitMQ），存任务消息； ③ Worker：消费 Broker 里的任务并执行，可多进程多节点水平扩展。 结果可存 Backend（Redis/DB）。支持定时任务（beat）、任务重试、链式任务、 任务路由。适合异步处理、定时任务、耗时计算。

    6.6 系统设计（4 题）

    Q1. 如何设计一个高并发系统？

    从三个层面：① 架构层：无状态服务 + 多实例水平扩展，前置负载均衡； ② 数据层：Redis 缓存扛读，DB 读写分离 + 分库分表扛写， 热点数据预加载；③ 保护机制：限流（令牌桶）、降级、熔断， 异步化（消息队列削峰）。面试时按"流量从哪来、怎么挡、怎么存、怎么保"的顺序讲， 结合具体 QPS 估算更可信。

    Q2. 如何保证接口幂等？

    核心思路是"唯一标识 + 去重"。三种手段：① 唯一请求 ID： 客户端传 request_id，服务端 Redis 记录，重复请求直接返回上次结果； ② 数据库唯一索引：如订单号建唯一索引，重复插入捕获异常返回成功； ③ 状态机：用状态流转控制（如只有"待支付"能扣减，已支付忽略）。 关键是写接口都要有幂等保障，特别是支付、下单、发券。

    Q3. 服务降级和熔断的区别？

    降级：主动行为，系统压力大或非核心功能故障时，关闭非核心功能 （如推荐、评论），返回兜底数据，保住核心链路（下单、支付）。 熔断：被动保护，当下游连续失败达阈值，暂时切断调用， 直接返回，防止故障蔓延拖垮自己，过会儿放流量试探（半开状态）。 降级是"丢车保帅"，熔断是"保险丝"。两者常配合使用。

    Q4. 模块拆分的原则是什么？

    四个原则：① 单一职责：一个模块只做一件事； ② 高内聚低耦合：相关的放一起，模块间依赖少； ③ 按业务领域：按业务边界拆，而非按技术层（如按"债券""收益率"分， 不按"controller""service"分大包）；④ 依赖方向清晰： 上层依赖下层抽象，避免循环依赖。最终目标是"改一个需求，尽量只动一个模块"。

    7. 面试准备建议

    技术题背得再熟，面试表现也只占 50%。剩下 50% 是怎么讲项目、怎么体现深度、怎么谈薪资。 下面几点建议帮你把技术实力"卖"出去。

    项目经验怎么讲？用 STAR 法则

    S（Situation）：项目背景——什么业务、规模多大、遇到什么问题。 如"我们有个债券定价接口，行情高峰时 QPS 翻三倍，接口 P99 从 200ms 飙到 2s"。
    T（Task）：你的任务——你负责什么、目标是什么。 如"我负责优化这个接口的响应时间和吞吐量"。
    A（Action）：你做了什么——这是重点，要讲技术细节。 如"加了 Redis 缓存行情数据、YTM 计算做预计算存缓存、定价逻辑用策略模式重构、 接入限流保护下游"。
    R（Result）：结果——用数据说话。 如"P99 降到 150ms，吞吐量提升 5 倍，行情高峰零故障"。 讲项目的核心是"你解决了什么问题、用了什么技术、带来了什么量化收益"。

    技术深度怎么体现？

    面试官问一个点，不要只答表面，要能往下挖 2-3 层。比如问 Redis 缓存， 不要只说"用来缓存数据"，要讲：缓存穿透/击穿/雪崩怎么解决 → 用了布隆过滤器和互斥锁 → 布隆过滤器原理是位数组 + 多个 hash → 误判率怎么算。这种"深挖"的回答最能体现深度。 另外，准备 1-2 个你最熟悉的技术点，能从原理讲到源码细节，作为"杀手锏"。 对于不熟悉的问题，坦诚说"这个我没深入研究过，但我理解是……"，不要硬编。

    薪资沟通的技巧

    ① 不要先报期望薪资，让对方先给范围（"请问这个岗位的薪资带宽是多少？"）； ② 真要报时，报一个略高于心理预期的区间（如期望 25-30，报 28-35）； ③ 谈薪的底气来自你的不可替代性——技术深度 + 项目成果 + 行业匹配度 （FICC 业务经验是券商的硬通货）； ④ 不要只看月薪，要看总包（base + 年终奖 + 股票 + 福利），券商年终奖占比高； ⑤ 拿到 offer 后不要马上答应，争取 1-2 天考虑时间，必要时用其他 offer 谈判。

    本章小结

    • SOLID 原则（单一职责、开闭、里氏替换、接口隔离、依赖倒置）是模块拆分的底层指导思想，配合高内聚低耦合、KISS/YAGNI 一起用。
    • 三层架构（Controller/Service/Repository）是 Python 后端标准分层，依赖方向单向，上层依赖下层抽象接口。
    • 模块拆分按业务领域、变化频率、依赖方向三个依据，目标是"改一个需求只动一个模块"。
    • 接口定义遵循最小化、稳定、版本化三原则，依赖注入（DI）是依赖倒置的落地手段，便于替换和测试。
    • 扩展性靠无状态 + 水平扩展，可靠性靠限流、降级、熔断、幂等、重试退避，缺一不可。
    • Python 常用五大设计模式：单例（模块级/装饰器/元类）、工厂、策略（FICC 定价典型）、观察者、适配器。
    • FICC 债券研究系统：API 网关 → 无状态服务层 → 数据层，报告生成走 Celery 异步，是系统设计题的标准答法。
    • 面试高频题按 Python 基础/Web/数据库缓存/并发/工程化分布式/系统设计六模块准备，每题答 2-3 句要点 + 项目结合。
    • 面试准备：项目用 STAR 法则讲（量化结果）、技术深挖 2-3 层体现深度、薪资谈总包不报裸薪。
    • 系统设计的本质是"在约束下做取舍"，没有银弹，原则 + 实战 + 复盘才能真正掌握。
