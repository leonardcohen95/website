    Pod 深入解析

    Pod 是 Kubernetes 中最小的调度单元，也是面试官最爱下手的切入点。 前一章我们快速带过了 Pod 的基本写法，本章把它彻底拆开： 从 Pod 为什么存在、生命周期、Init/Sidecar 容器设计模式，到资源管理（requests/limits/QoS）、 三类探针、优雅终止与调试命令。学完你能解释「Pod 是什么」「探针怎么配」 「节点资源不足时谁先被驱逐」这类高频面试题，并能在生产中写出健壮的 Pod YAML。

    学习目标

    • 理解 Pod 的本质：为什么不直接管容器，而要包一层 Pod
    • 掌握 Pod 生命周期与 Phase/Container State 的区别
    • 会写 Init Container 和 Sidecar 容器，并说清两者差异
    • 掌握 requests/limits 与 QoS 三等级及驱逐顺序
    • 能正确配置 liveness/readiness/startup 三类探针并调参
    • 理解 Pod 优雅终止流程，会用 preStop hook 避免丢请求

    1. Pod 的本质

    容器 runtime（containerd、CRI-O）管理的对象是「容器」，但 K8s 调度的最小单元却是 Pod。 面试官常问的第一个问题就是：「为什么 K8s 不直接调度容器，而要包一层 Pod？」

    Pod 是什么

    Pod 是一组紧密耦合的容器的集合，它们共享网络命名空间（同一个 IP、同一组端口） 和存储卷，被一起调度到同一个 Node 上，生命周期也绑在一起。K8s 不直接操作容器， 而是操作 Pod，由 Pod 内部的 pause 容器持有网络/IPC 命名空间，业务容器加入它。

    K8s 选择 Pod 而不是单个容器，主要原因是：现实中的应用往往需要多个进程协同（比如一个 Web 进程加一个日志采集进程），这些进程必须共享 localhost、共享卷、一起重启。 如果直接以容器为调度单元，容器间的这种紧耦合关系就没法表达。Pod 就是把这层「共生」关系 显式建模出来。

    为什么需要 Pod 这一层
    • 共享网络：Pod 内多个容器共享同一个 IP 和端口空间，互相用 localhost 通信。
    • 共享存储：Pod 内的 volumes 可以被多个容器同时挂载，文件互通。
    • 统一调度：Pod 是调度的最小单元，里面所有容器一起被调度到同一 Node，一起生死。
    • 解耦运行时：K8s 通过 Pod 抽象屏蔽了 containerd/Docker/CRI-O 的差异。
    一个 Pod 一个 IP

    每个 Pod 拿到一个独立的集群内 IP，Pod 内所有容器共享这个 IP。 这意味着 Pod 内容器间不能用相同端口（比如不能两个容器都监听 80）， 但跨 Pod 通信用 Pod IP 即可，无需关心容器。Service 也是给一组 Pod IP 做负载均衡的入口。 

    # Pod 内多容器共享网络和存储的典型场景：Nginx + filebeat
apiVersion: v1
kind: Pod
metadata:
  name: web-with-sidecar
  labels:
    app: web
spec:
  volumes:
    - name: shared-logs          # Pod 级共享卷
      emptyDir: {}
  containers:
    - name: nginx                # 主容器：写日志到共享卷
      image: nginx:1.25
      volumeMounts:
        - name: shared-logs
          mountPath: /var/log/nginx
    - name: filebeat             # sidecar 容器：从共享卷读日志转发
      image: elastic/filebeat:8.11
      volumeMounts:
        - name: shared-logs
          mountPath: /var/log/nginx
          readOnly: true

    2. Pod 生命周期

    一个 Pod 从被创建到被销毁，会经历多个阶段。理解状态流转对排查「Pod 起不来」至关重要。

    Pod 状态流转图
      [kubectl create]
        │
        ▼
   ┌─────────┐    调度失败/资源不足    ┌──────────┐
   │ Pending │ ─────────────────────► │   失败   │
   └────┬────┘                        └──────────┘
        │ 调度成功
        ▼
   ┌────────────────────┐
   │ ContainerCreating  │  拉镜像 / 挂卷 / 起容器
   └─────────┬──────────┘
             │ 所有容器 Running
             ▼
   ┌──────────┐    liveness 失败    ┌──────────────┐
   │ Running  │ ──────────────────► │  重启容器    │
   └────┬─────┘                      └──────┬───────┘
        │ delete Pod                        │ 反复崩溃
        ▼                                   ▼
   ┌──────────────┐                 ┌───────────────────┐
   │ Terminating  │                 │ CrashLoopBackOff   │
   └──────┬───────┘                 └───────────────────┘
          │ grace period 到
          ▼
       [Deleted]
    Pod 状态速查表
    • Pending：已提交但未调度，或镜像/卷还在准备，常见于资源不足。
    • ContainerCreating：已调度到节点，正在拉镜像、挂卷、起容器。
    • Running：所有容器已起来，但不代表应用就绪，要看 readiness。
    • Succeeded：所有容器正常退出（code=0），常见于 Job 类型 Pod。
    • Failed：所有容器都退出且至少一个失败（code != 0）。
    • Unknown：通常因和 Node 失联，无法获取状态。
    • CrashLoopBackOff：容器反复崩溃重启（不是 Phase，是 Container State）。
    • ImagePullBackOff：镜像拉取失败，会一直 BackOff 重试。
    • Terminating：正在优雅终止，等待 grace period 到或 preStop 完成。

    2.1 Pod Phase vs Container State

    这是面试常考的细节点：Pod Phase 是 Pod 级别的高层状态（Pending/Running/Succeeded/Failed/Unknown）， 而 Container State 是单个容器的状态，分为三种：

    Container State 三态

    Waiting：容器还没起，正在拉镜像/拉卷/等待依赖，对应 ContainerCreating 或 Pending。 Running：容器进程在前台运行，已分配 PID。 Terminated：容器进程已退出，会记录退出码和退出原因。

    一个 Pod 的 Phase=Running 只表示「至少有一个容器在 Running」，并不代表应用能接流量。 真正决定能不能接流量的是 readinessProbe，下面专门讲。

    3. 容器设计模式

    Pod 内多容器是有套路的，社区总结出几种常见设计模式。掌握它们能让你在面试时 脱口而出「Init Container」「Sidecar」「Ambassador」「Adapter」这些词。

    3.1 Init Container（初始化容器）

    Init Container 在主容器之前运行，必须按顺序成功完成（exit 0）才会启动下一个， 全部完成后才起主容器。典型用途：等数据库就绪、初始化配置文件、注册到服务发现。 

    apiVersion: v1
kind: Pod
metadata:
  name: web-init
spec:
  initContainers:
    - name: wait-for-db          # 第一个 init：等待 MySQL 起来
      image: busybox:1.36
      command:
        - sh
        - -c
        - |
          echo "waiting for mysql..."
          until nc -z mysql-svc 3306; do
            sleep 2
          done
          echo "mysql is ready"
    - name: init-config          # 第二个 init：生成配置文件到共享卷
      image: busybox:1.36
      command: ['sh','-c','echo "db_host=mysql-svc" > /config/app.conf']
      volumeMounts:
        - name: config
          mountPath: /config
  containers:
    - name: web                 # 主容器：使用 init 生成的配置
      image: nginx:1.25
      volumeMounts:
        - name: config
          mountPath: /etc/app
  volumes:
    - name: config
      emptyDir: {}

    3.2 Sidecar（旁车容器）

    Sidecar 是和主容器同时运行的辅助容器，负责日志收集、监控代理、代理服务、 配置同步等「边角料」工作，把主容器逻辑保持纯粹。 

    # 经典 Sidecar：Nginx 主容器 + busybox 日志转发 sidecar
apiVersion: v1
kind: Pod
metadata:
  name: web-sidecar
spec:
  volumes:
    - name: nginx-logs
      emptyDir: {}
  containers:
    - name: nginx
      image: nginx:1.25
      volumeMounts:
        - name: nginx-logs
          mountPath: /var/log/nginx
    - name: log-shipper          # sidecar：tail 日志并打到 stdout 给 kubectl logs 抓
      image: busybox:1.36
      command: ['sh','-c','tail -f /var/log/nginx/access.log']
      volumeMounts:
        - name: nginx-logs
          mountPath: /var/log/nginx
          readOnly: true
    常见 Pod 内容器设计模式
    • Init Container：先跑完退出，做初始化、依赖等待、配置生成。
    • Sidecar：和主容器并行，做日志/监控/代理，与主容器解耦。
    • Ambassador：代理外部服务（如把外部 MySQL 包装成本地 localhost）。
    • Adapter：把主容器输出适配成统一格式（如日志标准化）。
    Init 和 Sidecar 不是一回事

    面试常被坑：Init Container 必须成功退出才会进入主容器阶段， 而 Sidecar 和主容器同时长期运行，不会退出。 K8s 1.28+ 起支持 initContainers 中带 restartPolicy: Always 的「Sidecar 形态 Init 容器」， 但语义上仍是「先启动、与主容器并行运行」的辅助容器。

    4. 资源管理

    没有资源限制的 Pod 会和无约束的进程一样互相抢资源，最终被 OOM Killer 干掉。 K8s 通过 requests 和 limits 两个字段管理 CPU 和内存。

    4.1 requests vs limits

    resources:
  requests:                # 调度依据：保证 Pod 至少能拿到这么多
    cpu: 250m              # 250 millicore = 0.25 核
    memory: 256Mi         # 256 Mebibyte
  limits:                  # 上限：超过会被限制或杀死
    cpu: 500m              # 最多用 0.5 核（CPU 可被 throttle，不杀进程）
    memory: 512Mi         # 内存超限直接 OOMKilled
    CPU 和内存单位

    CPU：1 = 1 核，单位 m（millicore，千分之一核），如 500m = 0.5 核。 不允许写成小数如 0.5？可以写 0.5，但生产建议用 500m。 内存：用二进制单位 Ki/Mi/Gi/Ti（1Mi=1024Ki），不要用 KB/MB（十进制）。

    4.2 QoS 等级

    K8s 根据 requests/limits 的设置，把 Pod 划分到三个 QoS（Quality of Service） 等级。 节点资源紧张时，按等级决定谁先被驱逐。

    Guaranteed（保证级）

    所有容器的 requests = limits（CPU 和内存都设了且相等）。 优先级最高，资源紧张时最后被驱逐。生产关键服务建议用这个等级。

    Burstable（突发级）

    至少有一个容器设了 requests，但 requests != limits，或只设了部分资源。 中等优先级，资源紧张时优先于 Guaranteed 被驱逐。

    BestEffort（尽力级）

    所有容器都没有设 requests 和 limits。优先级最低，资源紧张时最先被驱逐。 开发/测试环境可以用，生产绝对不要。

    驱逐顺序（重要）

    节点资源不足（MemoryPressure/DiskPressure）时，kubelet 触发驱逐， 顺序是 BestEffort → Burstable → Guaranteed。 同等级内按「超出 requests 最多」的 Pod 优先驱逐。所以生产服务想稳定， 一定要把 requests=limits 设成相等，让它拿到 Guaranteed 等级。 

    # Guaranteed 等级 Pod 示例：requests == limits
apiVersion: v1
kind: Pod
metadata:
  name: web-guaranteed
spec:
  containers:
    - name: web
      image: nginx:1.25
      resources:
        requests:           # ===
          cpu: 500m          # 严格相等 → Guaranteed
          memory: 512Mi      # ===
        limits:
          cpu: 500m
          memory: 512Mi

    5. 探针详解

    探针是 K8s 感知应用真实状态的「传感器」。配好探针，K8s 才知道应用什么时候就绪、 什么时候卡死、什么时候需要重启。

    livenessProbe（存活探针）

    判断容器是否「活着」。失败时 kubelet 会重启容器（按 restartPolicy 处理）。 用于捕获死锁、 hang 住、线程池耗尽这类「进程还在但功能坏了」的情况。

    readinessProbe（就绪探针）

    判断容器是否「准备好接流量」。失败时 Pod 会被从 Service 的 endpoints 中摘除， 不重启容器。用于启动慢、依赖未就绪、过载时主动让流量。

    startupProbe（启动探针）

    K8s 1.16+ 引入。判断容器是否「首次启动完成」。 启动期间 liveness/readiness 都被禁用，直到 startup 成功。 用于启动很慢的应用（如 Java Spring Boot），避免被 liveness 误杀。

    5.1 探针类型

    每种探针都可以选三种检查方式：

    • httpGet：HTTP GET，状态码 2xx/3xx 视为成功。最常用。
    • tcpSocket：TCP 连接能建立即成功。用于非 HTTP 服务（MySQL、Redis）。
    • exec：在容器内执行命令，退出码 0 视为成功。灵活但开销略大。

    5.2 完整探针 YAML 示例

    apiVersion: v1
kind: Pod
metadata:
  name: web-probes
  labels:
    app: web
spec:
  containers:
    - name: web
      image: nginx:1.25
      ports:
        - containerPort: 80
      # === 启动探针：保护慢启动应用 ===
      startupProbe:
        httpGet:
          path: /healthz
          port: 80
        failureThreshold: 30      # 允许连续失败 30 次
        periodSeconds: 10         # 每 10s 探一次 → 最长等 5 分钟
      # === 就绪探针：失败就摘流量 ===
      readinessProbe:
        httpGet:
          path: /ready
          port: 80
        initialDelaySeconds: 5    # 容器启动后 5s 才开始探
        periodSeconds: 5
        failureThreshold: 3       # 连续 3 次失败 → 摘流量
      # === 存活探针：失败就重启 ===
      livenessProbe:
        httpGet:
          path: /healthz
          port: 80
        initialDelaySeconds: 15
        periodSeconds: 10
        failureThreshold: 3
        timeoutSeconds: 2
    没有探针会怎样

    不配探针时，K8s 只看容器进程是否在运行，无法感知应用内部死活。 典型坑：Java 应用启动 2 分钟，期间没配 startup 探针 → liveness 在第 30 秒就开始探， 连续失败就重启 → 永远起不来（CrashLoopBackOff）。生产 Pod 一定要三类探针齐全。

    探针参数调优建议
    • initialDelaySeconds：留够应用启动时间，慢启动应用宁可设大点。
    • periodSeconds：默认 10s，对延迟敏感可降到 5s，过低会增加压力。
    • failureThreshold：默认 3 次，避免单次抖动误判，关键服务可调到 5。
    • timeoutSeconds：默认 1s，HTTP 探针一般够，慢接口建议 2-3s。
    • 慢启动应用用 startupProbe 替代 initialDelaySeconds 的「盲等」。

    6. Pod 优雅终止

    直接 kubectl delete pod 时，K8s 不会立刻 kill 容器，而是走一段「优雅终止」流程， 给应用留出收尾时间。这段流程理解错了，就是「发版丢请求」的元凶。

    Pod 终止流程
    1. kubelet 设置 Pod 为 Terminating，从 Service endpoints 摘除
2. 同时执行 preStop hook（如果有）
3. 给容器发 SIGTERM，应用开始收尾（关闭连接、flush 缓存）
4. 等待 terminationGracePeriodSeconds（默认 30s）
5. 时间到还没退出 → 发 SIGKILL 强杀
6. 清理卷、删 Pod 对象
    为什么直接 kill Pod 会丢请求

    关键时间差：Pod 被摘出 endpoints 和 kube-proxy 同步 iptables/IPVS 规则 是异步的，客户端可能还按旧规则往这个 Pod 发请求。如果此时立刻 SIGKILL， 这些在途请求就丢了。解决：用 preStop hook 让 Pod 多睡一会儿， 等客户端的连接都断开。 

    # 完整优雅终止示例：preStop hook + 缩短 grace period
apiVersion: v1
kind: Pod
metadata:
  name: web-graceful
spec:
  terminationGracePeriodSeconds: 60   # 最多等 60s 才强杀
  containers:
    - name: web
      image: nginx:1.25
      lifecycle:
        preStop:                       # 在 SIGTERM 之前执行
          exec:
            command:
              - sh
              - -c
              - |
                echo "draining..."
                nginx -s quit          # 让 nginx 处理完现有连接再退
                sleep 15               # 关键：等 kube-proxy 规则同步完

    典型坑：用了 nginx 但没配 preStop，nginx 收到 SIGTERM 直接退出， iptables 规则可能还没更新完，正在途的请求被 RST。生产服务发版丢请求数第一的元凶。

    7. Pod 调试命令速查

    # 看 Pod 列表和所在节点、IP、状态
kubectl get pods -o wide
kubectl get pods -n kube-system -o wide

# 看详细信息和 Events（排查起不来的第一站）
kubectl describe pod <pod-name>

# 看日志（-c 指定多容器的某一个；--previous 看上一个挂掉的容器）
kubectl logs <pod-name> [-c container-name] -f
kubectl logs --previous <pod-name>

# 进入容器
kubectl exec -it <pod-name> -- /bin/sh
kubectl exec -it <pod-name> -c sidecar -- /bin/sh

# 端口转发（本地调试 Pod，不经过 Service）
kubectl port-forward <pod-name> 8080:80
# 然后浏览器访问 http://localhost:8080

# 临时跑一个调试 Pod，用完即删
kubectl run debug --image=nicolaka/netshoot --rm -it -- sh

# 看 Pod 的 YAML（看 K8s 自动补的字段，如 serviceAccount、nodeSelector）
kubectl get pod <pod-name> -o yaml

# 看 Pod 的资源占用（需要 metrics-server）
kubectl top pod
kubectl top pod -l app=web --sort-by=memory
    排查 Pod 起不来的三步法
    • 第一步：kubectl get pod 看 Phase 状态。
    • 第二步：kubectl describe pod 看 Events 段（FailedScheduling / ErrImagePull / CrashLoopBackOff）。
    • 第三步：kubectl logs / kubectl logs --previous 看应用日志。

    8. 面试高频题

    Q1：Pod 有哪些状态？

    Pod 级别 Phase 有 5 种：Pending、Running、Succeeded、Failed、Unknown。 注意 CrashLoopBackOff、ImagePullBackOff 这些其实不是 Phase， 而是 Container State 的等待原因（Reason），体现在 kubectl get pod 的 READY 列旁边的状态字符串。排查时先 describe 看 Events，再 logs --previous。

    Q2：三类探针的区别？

    liveness 失败 → 重启容器；readiness 失败 → 摘流量不重启； startup 只在启动期生效，启动期间禁用 liveness，避免慢启动应用被误杀。 生产建议三类齐配，readiness 是流量控制核心，liveness 用于死锁兜底。

    Q3：QoS 等级是什么？怎么划分？

    QoS 是 K8s 根据 Pod 的 requests/limits 自动算出来的优先级， 分 Guaranteed（requests=limits）、Burstable（部分设置）、BestEffort（全不设）三档。 节点资源紧张时按 BestEffort → Burstable → Guaranteed 顺序驱逐。 生产关键服务要保证 Guaranteed：所有容器 requests 和 limits 设成相等。

    Q4：Init Container 和 Sidecar 的区别？

    Init Container 在主容器之前串行运行，必须成功退出（exit 0）才进入下一阶段， 用于依赖等待、配置初始化。Sidecar 和主容器并行长期运行，不退出， 用于日志/监控/代理。两者都和主容器共享网络和存储，但生命周期完全不同。

    本章小结

    • Pod 是 K8s 最小调度单元，包了一组共享网络/存储的容器，解耦了运行时差异。
    • Pod Phase 是高层状态，Container State 是单容器状态；Running 不等于就绪，要看 readiness。
    • Init Container 串行先跑完退出，Sidecar 和主容器并行；常见模式还有 Ambassador、Adapter。
    • requests 是调度保障，limits 是上限；CPU 用 m，内存用 Mi/Gi。
    • QoS 三等级：Guaranteed（requests=limits）最稳，BestEffort 最易被驱逐。
    • 三类探针：liveness 重启、readiness 摘流量、startup 保护慢启动；生产要全配。
    • 优雅终止靠 preStop hook + terminationGracePeriodSeconds，避免发版丢在途请求。
    • 排查 Pod 起不来三步：get 看状态 → describe 看 Events → logs 看日志。
