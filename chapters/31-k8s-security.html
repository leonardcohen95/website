    第 31 章 K8s 专题 约 40 分钟

    安全与 RBAC

    安全是 K8s 生产化的最后一公里。本章把 K8s 安全模型拆成「认证 → 授权 → 准入」三道 防线，重点吃透 RBAC 四大对象（Role / ClusterRole / RoleBinding / ClusterRoleBinding）， 再覆盖 ServiceAccount、SecurityContext、Pod Security Standards 和安全加固清单。 每一节都标注「面试怎么问」，帮你把零散的安全知识点串成一条能讲清楚的主线。

    学习目标

    • 理解 K8s 三道安全防线：Authentication → Authorization → Admission Control
    • 掌握 RBAC 四大核心对象及其区别与适用场景
    • 会用 kubectl auth can-i 验证权限，会写 Role / RoleBinding YAML
    • 理解 ServiceAccount 的工作原理与最小权限配置
    • 会用 SecurityContext 让 Pod 以非 root、最小权限运行
    • 掌握 Pod Security Standards 三个级别和生产安全加固清单

    1. K8s 安全模型概述

    K8s 的所有 API 请求都要经过三道防线才能落地到 etcd。 理解这三道防线是回答任何 K8s 安全问题的总纲：第一道确认「你是谁」， 第二道确认「你能做什么」，第三道确认「你这么做到底合不合规」。

    三道防线一图流
              API 请求 (kubectl / Pod / 外部用户)
                       │
                       ▼
        ┌──────────────────────────────────┐
        │ 1. Authentication 认证            │  → "你是谁?"
        │    - 客户端证书 / Bearer Token    │
        │    - ServiceAccount Token / OIDC  │
        └──────────────┬───────────────────┘
                       │ 通过 → 已知身份
                       ▼
        ┌──────────────────────────────────┐
        │ 2. Authorization 授权 (RBAC)      │  → "能做吗?"
        │    - Role / ClusterRole          │
        │    - RoleBinding / ClusterRoleBinding
        └──────────────┬───────────────────┘
                       │ 通过 → 权限匹配
                       ▼
        ┌──────────────────────────────────┐
        │ 3. Admission Control 准入控制     │  → "合规吗?"
        │    - Mutating  Webhook (改对象)  │
        │    - Validating Webhook (校验)    │
        │    - ResourceQuota / PSP / PSS   │
        └──────────────┬───────────────────┘
                       │ 通过
                       ▼
                   写入 etcd
    三道防线一句话总结

    Authentication（认证）：验证请求者身份，常用 X.509 客户端证书、 Bearer Token、ServiceAccount Token 或外部 OIDC。
    Authorization（授权）：判断身份能否执行该操作，默认走 RBAC。 还有 ABAC（已不推荐）和 Node 授权（kubelet 用）。
    Admission Control（准入控制）：在对象写入 etcd 前的最后一道校验， 可修改或拒绝对象，例如强制打标签、限制镜像仓库、配额检查。

    2. 认证（Authentication）

    K8s 不内置用户数据库，「用户」只是证书或 Token 里携带的身份。 系统层面分两类：真实用户（人/外部系统，用证书或 OIDC）和 ServiceAccount（Pod 用的，存在 K8s 内部）。

    客户端证书（X.509 Certificate）

    用集群 CA 签发的证书，CN（Common Name）就是用户名，O（Organization）是组名。 kubeadm init 生成的 /etc/kubernetes/admin.conf 就是 这种方式。优点是稳定、不依赖外部组件；缺点是签发/吊销麻烦， 证书过期会引发集群瘫痪（生产事故高发点）。

    Bearer Token

    请求头里带 Authorization: Bearer <token>，apiserver 校验通过即放行。 静态 Token 文件方式（--token-auth-file）维护麻烦、token 无法吊销， 生产基本不用，更多用 ServiceAccount Token 或 OIDC。

    ServiceAccount Token

    Pod 调 apiserver 的默认方式。每个 SA 有一个或多个 Secret， 里面装 CA 证书和 JWT Token，自动挂载到 Pod 的 /var/run/secrets/kubernetes.io/serviceaccount/。 K8s 1.24+ 改为投影卷 Token，按需生成、1 小时过期、可滚动刷新， 更安全。

    生产别用静态 Token 文件

    静态 Token 明文存磁盘、改了要重启 apiserver、无法吊销。 生产推荐用 OIDC（对接企业 SSO，如飞书、钉钉、Keycloak） 或新版 ServiceAccount 短期 Token。

    3. RBAC 权限模型（重点）

    RBAC（Role-Based Access Control，基于角色的访问控制）是 K8s 1.6 起的默认授权模式， 也是面试 K8s 安全的最高频考点。核心思想：权限不直接给用户， 而是先给「角色」，再用「绑定」把角色分给用户，方便批量管理。

    3.1 四个核心对象

    RBAC 一共只有 4 个核心对象，分两个维度交叉：

    • 角色范围维度：Role（namespace 级别）/ ClusterRole（集群级别）
    • 绑定范围维度：RoleBinding（namespace 级别）/ ClusterRoleBinding（集群级别）
    RBAC 关系一图流
      ┌─────────────┐        ┌──────────────┐        ┌──────────────┐
  │  Role /      │  rules │              │ subjects│              │
  │  ClusterRole │ ──────▶│ RoleBinding /│ ────────▶│ User / SA /  │
  │  (权限定义)  │  允许  │  ClusterRB   │  绑定给  │  Group       │
  └─────────────┘        └──────────────┘        └──────────────┘
        ▲                                                ▲
        │                                                │
        └────────── 权限经绑定流向最终的使用者 ──────────┘

  rules:    verbs + resources + resourceNames (可空)
  subjects: User / Group (人) 或 ServiceAccount (Pod)
    Role vs ClusterRole

    Role：namespace 级别，只能授权该 namespace 内的资源 （如 get pods in default）。
    ClusterRole：集群级别，既可授权集群级资源 （nodes、persistentvolumes、namespace），也可授权所有 namespace 的资源 （get pods across all namespaces）。
    经验：常用 ClusterRole 定义通用权限模板 （如 view、edit、admin），再用 RoleBinding 在某个 namespace 内绑定给用户， 做到「权限模板集群级、授权范围 namespace 级」。

    3.2 完整 YAML 示例

    下面演示一条完整的授权链：创建 SA → 创建 Role → 用 RoleBinding 绑定。

    # 1. 创建 ServiceAccount
apiVersion: v1
kind: ServiceAccount
metadata:
  name: ci-sa            # CI 流水线用
  namespace: dev

---
# 2. 创建 Role：允许操作 dev 命名空间的 Pod/Deployment
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-manager
  namespace: dev         # 作用范围限制在 dev
rules:
  - apiGroups: [""]                              # core 组 (Pod/Service 等)
    resources: ["pods", "pods/log", "pods/exec"]
    verbs: ["get", "list", "watch", "exec"]      # 只读 + exec
  - apiGroups: ["apps"]
    resources: ["deployments"]
    verbs: ["get", "list", "watch", "create", "update", "patch"]

---
# 3. RoleBinding：把 Role 绑给 ci-sa
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: ci-sa-pod-manager
  namespace: dev
subjects:
  - kind: ServiceAccount
    name: ci-sa
    namespace: dev         # 注意 subjects 里 SA 必须写 namespace
roleRef:
  kind: Role               # 引用上面定义的 Role
  name: pod-manager
  apiGroup: rbac.authorization.k8s.io

    3.3 验证权限 kubectl auth can-i

    权限配完一定要用 can-i 实测，光看 YAML 不能保证生效。

    # 用 default SA 看看能不能在 default 命名空间创建 Pod
kubectl auth can-i create pods -n default --as system:serviceaccount:default:default
# no   ← 默认 SA 没权限，符合预期

# 用上面创建的 ci-sa 看看能不能 list pods
kubectl auth can-i list pods -n dev --as system:serviceaccount:dev:ci-sa
# yes

# 看自己当前用户在 dev 命名空间能干什么
kubectl auth can-i --list -n dev

# 模拟某用户能否 delete deploy
kubectl auth can-i delete deployments.apps -n dev --as zhangsan

    3.4 常用 verbs 速查

    verbs 速查表
    • get：取单个资源（kubectl get pod NAME）
    • list：列出多个资源（kubectl get pods）
    • watch：监听变化（控制器常用）
    • create：创建（kubectl apply）
    • update：整体更新（少见，幂等性差）
    • patch：局部更新（kubectl edit/label）
    • delete：删除（kubectl delete）
    • exec：进入容器（kubectl exec）
    • *：通配，等于全部 verbs（生产慎用）
    最小权限原则

    永远只给「业务确实需要的 verbs + resources」，不要图省事给 verbs: ["*"]。严禁把 cluster-admin 直接绑给业务 Pod 或个人， 一次误操作（删 namespace、改 CRD）就能让整个集群报废。生产默认账号要剥离 cluster-admin。

    4. ServiceAccount

    ServiceAccount（SA）是 K8s 内部的「机器用户」，主要给 Pod 用。每个 namespace 自动 有一个名为 default 的 SA，Pod 不指定 serviceAccountName 时默认用它。

    4.1 自定义 SA 与 Pod 绑定

    # 1. 创建自定义 SA
apiVersion: v1
kind: ServiceAccount
metadata:
  name: app-sa
  namespace: prod
# 创建后会自动生成关联的 Secret (1.24+ 为投影卷 Token)

---
# 2. Pod 显式指定 serviceAccountName
apiVersion: v1
kind: Pod
metadata:
  name: web
  namespace: prod
spec:
  serviceAccountName: app-sa     # 关键：用我们刚建的 SA，不用 default
  containers:
    - name: web
      image: nginx:1.25

    4.2 Token 自动挂载与关闭

    # K8s 默认把 SA Token 挂到 /var/run/secrets/...
# 如果 Pod 不需要访问 apiserver（如纯静态站点），可关闭自动挂载
spec:
  automountServiceAccountToken: false   # Pod 级别关
  containers:
    - name: web
      image: nginx:1.25

# 也可在 SA 级别关，影响所有用这个 SA 的 Pod
apiVersion: v1
kind: ServiceAccount
metadata:
  name: app-sa
  namespace: prod
automountServiceAccountToken: false
    不要用 default SA 跑业务

    default SA 通常没有权限或权限混乱，一旦给 default SA 绑了角色， 该 namespace 内所有未指定 SA 的 Pod 都拿到这权限，攻击面极大。 生产规矩：每个业务单独建 SA、单独绑最小权限、Pod 显式 serviceAccountName， 没用的 Pod 关掉 automountServiceAccountToken。

    5. SecurityContext

    SecurityContext 控制容器运行时的安全行为：以什么用户跑、 有没有 root 权限、能不能写根文件系统、用哪些 Linux capabilities。 这是「Pod 自身安全」最重要的字段，面试里几乎必问。

    5.1 完整 YAML 示例

    apiVersion: v1
kind: Pod
metadata:
  name: secure-pod
  namespace: prod
spec:
  securityContext:                 # Pod 级别，所有容器继承
    runAsUser: 1000                # 非 0 (root)，用 1000
    runAsGroup: 3000               # 主组 3000
    runAsNonRoot: true             # 强制不允许 root (apiserver 与 kubelet 双重校验)
    fsGroup: 2000                  # 挂载卷的文件 group
  containers:
    - name: app
      image: myapp:1.0
      securityContext:            # 容器级别，覆盖 Pod 级别
        runAsUser: 1000
        readOnlyRootFilesystem: true   # 根文件系统只读，写只能写 emptyDir
        allowPrivilegeEscalation: false # 禁止 setuid 提权
        capabilities:
          drop: ["ALL"]            # 先把所有 root capability 全删
          add: ["NET_BIND_SERVICE"]# 只加"绑 <1024 端口"这一个
      volumeMounts:
        - name: tmp
          mountPath: /tmp         # 要写就挂 emptyDir
  volumes:
    - name: tmp
      emptyDir: {}
    不设 SecurityContext = 默认 root 跑

    容器镜像默认以 root (UID 0) 启动，拿到 Pod 就等于拿到节点上的 root， 因为容器和宿主机共享内核，root capabilities 又给了一大堆危险权限（CAP_SYS_ADMIN 等）。 一旦应用有 RCE 漏洞，攻击者能逃逸到节点。生产强制： runAsNonRoot: true + drop: [ALL] + readOnlyRootFilesystem。

    常用 SecurityContext 字段

    runAsUser / runAsGroup：指定 UID/GID，非 0 即非 root。
    runAsNonRoot：true 时 kubelet 会拒绝 root 容器，是兜底防线。
    readOnlyRootFilesystem：根文件系统只读，恶意脚本无法落盘。
    allowPrivilegeEscalation：禁止 setuid/setgid 提权。
    capabilities drop/add：精细化 Linux capability 控制。
    seccompProfile：限制容器能调用的系统调用，进一步缩小攻击面。

    6. Pod Security Standards（PSS）

    K8s 1.25 起 Pod Security Standards 正式替代旧的 PSP （PodSecurityPolicy，1.25 已删除）。它是一个namespace 级别的开关， 通过 label 声明该 namespace 接受哪个安全级别，由 apiserver 内置准入控制器自动校验。

    privileged（特权级）

    完全不限制，等于「想干啥干啥」：能挂宿主机路径、能用 hostNetwork、能 privileged 容器、 能加全部 capability。仅用于系统组件（如 CNI、存储插件），严禁业务 Pod 用。

    baseline（基线级）

    防最明显的越权，但允许合理灵活性：禁 privileged、禁 hostNetwork/hostPID、禁加危险 capability，但允许普通非 root 容器、允许 emptyDir/hostPath 以外的卷。 适合无法改造的老应用。

    restricted（受限级，推荐）

    最严格，生产默认：必须 runAsNonRoot、必须 drop ALL 后才能按需 add、 禁止 seccompProfile=Unconfined、必须设 allowPrivilegeEscalation=false。 业务 namespace 一律建议开 restricted。

    6.1 namespace 启用 PSS

    # 给 namespace 打两个 label：enforce 强制 + audit 审计
apiVersion: v1
kind: Namespace
metadata:
  name: prod
  labels:
    # 强制级别：违反就拒绝创建/更新
    pod-security.kubernetes.io/enforce: restricted
    pod-security.kubernetes.io/enforce-version: latest
    # 审计级别：违反只记录到审计日志，不拒绝
    pod-security.kubernetes.io/audit: restricted
    pod-security.kubernetes.io/audit-version: latest
    # 告警级别：违反在告警里提示
    pod-security.kubernetes.io/warn: restricted
    PSS 三档开关区别

    enforce：违反就 Reject，硬性阻断。
    audit：违反只写审计日志，不阻断（用于过渡期观察影响）。
    warn：违反给客户端返回 warning（kubectl 会显示），不阻断。
    落地建议：新集群直接 enforce=restricted；老集群先 warn/audit 跑一段时间，改造完再切 enforce。

    7. 安全最佳实践清单

    生产安全加固 10 条清单
    1. RBAC 最小权限：每个 SA 单独绑最小 Role，禁止 cluster-admin 滥用。
    2. 非 root 运行：所有 Pod 强制 runAsNonRoot + runAsUser 非 0。
    3. 根文件系统只读：readOnlyRootFilesystem: true，要写挂 emptyDir。
    4. NetworkPolicy：默认拒绝所有入向/出向，按业务白名单放行。
    5. etcd 静态加密：开启 --encryption-provider-config，Secret 落地 etcd 即密文。
    6. 审计日志：apiserver 开 --audit-log，所有写操作留痕，便于追责。
    7. 镜像扫描：CI 集成 Trivy/Grype，有高危 CVE 直接卡构建。
    8. 限制镜像仓库：准入 webhook 只允许公司私有仓库，禁止 docker.io 公网镜像。
    9. ResourceQuota + LimitRange：每 namespace 配额，防一个业务吃光资源。
    10. 定期更新：跟踪 K8s CVE 公告，跟随官方补丁节奏升级，至少一年一次。

    8. 面试高频题

    8.1 「说说 K8s 的 RBAC 模型」

    参考答案要点

    ①RBAC = Role-Based Access Control，K8s 默认授权模式（apiserver --authorization-mode=Node,RBAC）。 ②四个核心对象：Role / ClusterRole 定义权限模板，RoleBinding / ClusterRoleBinding 把模板绑定给 subject。 ③Role 是 namespace 级别，ClusterRole 是集群级别，也可在所有 namespace 共用模板。 ④subject 三种：User（人）、Group（组）、ServiceAccount（Pod）。 ⑤生产最佳实践：先建最小 Role/ClusterRole，再用 RoleBinding 在指定 namespace 绑给业务 SA， 杜绝 cluster-admin 滥用。

    8.2 「Role 和 ClusterRole 的区别？」

    参考答案要点

    ①作用域：Role 只在所属 namespace 生效；ClusterRole 集群级生效，能授权 集群级资源（nodes、namespaces、CRD）和跨 namespace 资源。
    ②绑定方式：Role 必须用 RoleBinding 绑定才在该 namespace 内生效； ClusterRole 可用 ClusterRoleBinding 集群级生效，也可用 RoleBinding 在某 namespace 生效 （「模板集群定义、授权 namespace 级」常用套路）。
    ③使用场景：业务权限用 Role + RoleBinding；监控、运维、系统组件 通常用 ClusterRole + ClusterRoleBinding（如 prometheus 要 list 所有 namespace 的 Pod）。

    8.3 「ServiceAccount 是什么？Pod 怎么用它？」

    参考答案要点

    ①SA 是 K8s 内部的「机器用户」，主要供 Pod 访问 apiserver 用，和「人」用的 User 区分。 ②每个 namespace 自动有一个 default SA，Pod 不指定就默认用 default。
    ③Pod 通过 spec.serviceAccountName 指定 SA，Token 自动挂到 /var/run/secrets/kubernetes.io/serviceaccount/，client-go 默认读取后调用 apiserver。 ④K8s 1.24+ Token 改为投影卷，按需生成、1 小时过期、可滚动刷新，更安全。
    ⑤生产建议：每个业务单独建 SA、单独绑最小权限、Pod 显式指定、不需要访问 apiserver 的 Pod 关掉 automountServiceAccountToken。

    8.4 「怎么保证 Pod 安全运行？」

    参考答案要点

    从三层回答：①身份层，Pod 用最小权限 SA，RBAC 严格限制 verbs/resources， 不用 default SA，不用 cluster-admin。②容器层，SecurityContext 强制 runAsNonRoot、runAsUser 非 0、drop ALL capabilities 后再 add 必需项、 readOnlyRootFilesystem、allowPrivilegeEscalation=false，并加 seccompProfile=default。 ③集群层，namespace 启用 Pod Security Standards restricted 级别强制校验， 配 NetworkPolicy 网络隔离、etcd 加密、审计日志、镜像扫描与仓库白名单。 三层一起才能挡住 RCE → 提权 → 横移 → 逃逸 的常见攻击链。

    本章小结

    • K8s API 请求经三道防线：Authentication 认证 → Authorization 授权（RBAC）→ Admission Control 准入。
    • 认证支持客户端证书、Bearer Token、ServiceAccount Token、OIDC，生产推荐 OIDC + SA 短期 Token。
    • RBAC 四个核心对象：Role/ClusterRole 定义权限，RoleBinding/ClusterRoleBinding 绑给 subject。
    • Role 是 namespace 级，ClusterRole 是集群级，常用 ClusterRole+RoleBinding 做模板+按需授权。
    • 用 kubectl auth can-i --as 验证权限，光看 YAML 不算数。
    • Pod 显式指定 serviceAccountName，禁用 default SA 跑业务，无 apiserver 需求的 Pod 关 automount。
    • SecurityContext 强制非 root + drop ALL + readOnlyRootFilesystem，是容器层最关键的安全字段。
    • Pod Security Standards（privileged/baseline/restricted）1.25+ 正式替代 PSP，生产默认 restricted。
