    第 21 章 AI+运维 约 35 分钟

    大模型部署与 AI+运维（AIOps）

    岗位要求有大模型部署实践、具备 AI+运维（智能告警、根因分析）经验。 本章讲怎么把大模型部署到本地服务器，再看 AI 怎么赋能运维—— 智能告警降噪、日志根因分析、故障自愈。这一章和前面的 AI Agent 教程呼应， 是「AI 能力」和「运维能力」的结合点。

    学习目标

    • 理解大模型部署的关键概念（量化、推理引擎、显存估算）
    • 能用 Ollama 或 vLLM 快速部署大模型服务
    • 理解 AI+运维的典型场景：智能告警、根因分析、故障自愈
    • 能设计一个简单的 AIOps 方案

    1. 大模型部署基础

    1.1 先搞清楚几个概念

    参数规模

    模型有 7B、13B、70B 等规格，B = Billion（十亿）。参数越多能力越强， 但需要的显存越大。粗略估算：FP16 精度下，1B 参数 ≈ 2GB 显存。 所以 7B 模型 FP16 部署约需 14GB 显存（还要算 KV Cache）。

    量化（Quantization）

    把模型权重从 FP16（16位浮点）降到 INT8/INT4（8/4位整数）， 显存占用减半甚至降到 1/4，精度损失可接受。 常用量化方法：GGUF（llama.cpp/Ollama 用）、GPTQ、AWQ。 7B 模型用 INT4 量化后只需约 4GB 显存，消费级显卡就能跑。

    推理引擎

    专门优化大模型推理速度的框架，比原生 PyTorch 快很多。 vLLM：高吞吐，适合服务化部署。 TGI：HuggingFace 出品。 llama.cpp：纯 CPU/边缘部署。 Ollama：最易用，一键部署。

    1.2 显存估算

    显存 = 权重 + KV Cache + 激活
    权重显存 = 参数数量 × 每参数字节数
  FP16: 7B × 2B = 14GB
  INT8: 7B × 1B = 7GB
  INT4: 7B × 0.5B = 3.5GB

KV Cache = 2 × num_layers × num_heads × head_dim × seq_len × 2(FP16)
  7B 模型 8k 上下文，并发 batch=4 时约占 5~10GB

结论：7B INT4 + 8k 上下文，至少准备 8~12GB 显存

    2. 用 Ollama 快速部署

    Ollama 是最简单的大模型部署工具，一条命令搞定，适合快速验证。

    # 安装（Linux）
curl -fsSL https://ollama.com/install.sh | sh

# 启动服务
systemctl start ollama

# 拉取并运行 7B 模型（自动下载约 4GB）
ollama run llama3

# 后台运行模型
ollama serve &
ollama pull qwen2:7b-instruct

# 调用 API
curl http://localhost:11434/api/chat -d '{
  "model": "qwen2:7b-instruct",
  "messages": [{"role": "user", "content": "你好"}]
}'

# 自定义模型（用 Modelfile 量化/配置）
# Modelfile:
#   FROM qwen2:7b-instruct
#   PARAMETER temperature 0.7
#   SYSTEM 你是一个运维助手，擅长分析日志和排查故障
ollama create ops-assistant -f Modelfile
    无显卡也能跑

    Ollama 支持纯 CPU 推理，只是速度慢。7B 模型在 CPU 上大约每秒 5~10 个 token， 适合对延迟不敏感的场景。有 NVIDIA 显卡会自动用 GPU 加速。

    3. 用 vLLM 部署高性能推理服务

    生产环境高并发场景，用 vLLM 部署，吞吐比原生 PyTorch 高几倍。

    # 安装
pip install vllm

# 启动 OpenAI 兼容的 API 服务
python -m vllm.entrypoints.openai.api_server \
  --model Qwen/Qwen2-7B-Instruct \
  --quantization awq \              # AWQ 量化
  --gpu-memory-utilization 0.85 \   # 用 85% 显存
  --max-model-len 8192 \            # 最大上下文
  --tensor-parallel-size 1          # 用几张卡（多卡设 2、4）

# 调用（兼容 OpenAI API 格式）
curl http://localhost:8000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "Qwen/Qwen2-7B-Instruct",
    "messages": [{"role": "user", "content": "分析这段日志..."}],
    "temperature": 0.3
  }'
    vLLM 的核心技术：PagedAttention

    vLLM 提出 PagedAttention，把 KV Cache 像操作系统分页内存一样管理， 解决了传统框架显存碎片和浪费问题，让高并发下显存利用率大幅提升。 面试被问「为什么 vLLM 快」，答 PagedAttention 就对了。

    3.1 容器化部署

    # docker-compose.yml
services:
  llm:
    image: vllm/vllm-openai:latest
    runtime: nvidia
    environment:
      - NVIDIA_VISIBLE_DEVICES=all
    command: >
      --model Qwen/Qwen2-7B-Instruct
      --quantization awq
      --gpu-memory-utilization 0.85
      --max-model-len 8192
    ports:
      - "8000:8000"
    volumes:
      - ./models:/root/.cache/huggingface
    deploy:
      resources:
        reservations:
          devices:
            - driver: nvidia
              count: all
              capabilities: [gpu]

    4. AI+运维（AIOps）实践

    大模型部署好之后，怎么用在运维上？核心思路是： 把运维数据（日志、指标、告警）喂给大模型，让它帮我们分析、决策、甚至自动修复。

    4.1 智能告警降噪

    传统告警系统一个故障会触发几十上百条告警，运维根本看不过来。 用大模型做告警聚合和根因摘要： 

    告警输入：
  - [CRITICAL] web-01 CPU 95%
  - [CRITICAL] web-02 CPU 92%
  - [WARNING]  db-01 响应慢
  - [CRITICAL] api 网关 5xx 错误率 30%
  - [WARNING]  redis 内存 85%

大模型输出：
  【根因分析】web 集群 CPU 飙高导致请求堆积，进而引发网关 5xx 和数据库响应慢。
  【可能原因】
    1. 流量突增（建议检查网关 QPS）
    2. 新版本发布引入性能问题（建议查最近发布记录）
    3. 某个慢查询/慢接口（建议查应用慢日志）
  【建议操作】
    1. 先扩容 web 副本缓解压力
    2. 抓取 web-01 的进程栈定位高 CPU 函数
    3. 如果是发布导致，立即回滚

    4.2 日志根因分析

    把异常日志片段发给大模型，让它解释错误并给排查建议：

    prompt = """
你是一个资深运维工程师。请分析下面的错误日志，给出：
1. 错误的含义
2. 可能的原因
3. 排查步骤
4. 解决方案

日志：
{}
""".format(error_log)

response = call_llm(prompt)
print(response)
    用 RAG 增强准确性

    通用大模型不一定懂你们公司的架构和历史故障。把内部运维文档、 历史故障报告、FAQ 做成知识库（RAG，参考第 9-10 章）， 大模型回答时先检索相关文档，再生成分析，准确性会高很多。

    4.3 故障自愈（智能体闭环）

    更进一步：让 AI Agent（参考前面 AI Agent 教程）不仅分析，还能执行修复操作。 这就是「感知 → 决策 → 执行」的闭环。

    自愈闭环流程
    监控告警 → 大模型分析根因 → 生成修复方案 → 人工审批/自动执行 → 验证恢复
   ↑                                                      │
   └──────────── 结果反馈，持续优化 ←──────────────────────┘
    # 伪代码：一个简单的自愈 Agent
def alert_handler(alert):
    # 1. 收集上下文：日志、指标、最近变更
    context = collect_context(alert)

    # 2. 大模型分析并给出修复方案
    plan = llm.analyze(alert, context)
    # plan = {
    #   "root_cause": "Pod 内存超限被 OOMKill",
    #   "action": "kubectl scale deploy web --replicas=5",
    #   "risk": "low"
    # }

    # 3. 低风险操作自动执行，高风险人工审批
    if plan["risk"] == "low":
        execute(plan["action"])
        # 4. 验证是否恢复
        if verify_recovered(alert):
            close_alert(alert)
        else:
            escalate_to_human(plan)
    else:
        notify_human_for_approval(plan)
    安全红线

    AI 自动执行操作必须有权限边界和审批机制。 只允许在预定义的操作集合里选择（如扩容、重启、回滚）， 禁止让大模型自由执行任意命令。高危操作（删库、改网络）必须人工审批。

    4.4 AIOps 落地建议

    • 第一步：告警降噪，投入小、见效快，先让大模型帮你整理告警。
    • 第二步：日志分析助手，作为查询工具，不自动操作，降低风险。
    • 第三步：辅助决策，给出修复建议但不自动执行，人工确认。
    • 第四步：有限自愈，只对低风险、可验证的操作自动化。
    • 全程可观测：AI 的每次决策和操作都要记录，可审计、可回滚。

    5. 运维工程师的 AI 能力清单

    面试官问「你怎么看 AI+运维」时，可以从这几个维度回答：

    • 会用 AI 工具：用 Copilot/Cursor 写脚本，用大模型分析日志。
    • 懂部署大模型：知道 Ollama/vLLM 怎么搭，显存怎么估算。
    • 能设计 AIOps 方案：告警降噪、根因分析、故障自愈的闭环。
    • 有安全意识：知道 AI 自动操作的边界，审批和审计不能少。
    • 结合本教程的 AI Agent：用 Agent 框架把运维工具编排起来（参考第 5、6、11、14 章）。

    本章小结

    • 大模型部署关键：参数规模 × 量化精度 = 显存需求，7B INT4 约需 8~12GB。
    • Ollama 适合快速验证，vLLM 适合生产高并发（PagedAttention 提吞吐）。
    • AI+运维四大场景：告警降噪、日志根因分析、辅助决策、故障自愈。
    • 用 RAG 把内部运维知识库接给大模型，提升分析准确性。
    • 自愈闭环要设权限边界和审批，高危操作必须人工确认。
