各库核心考点（按“必答”整理）

不求全，先把高频说清楚

2.1 Oracle：体系结构是地基 必背

必须能脱口而出的点

  • SGA：Shared Pool（SQL 解析、执行计划、数据字典）、Database Buffer Cache、Redo Log Buffer、Large Pool、Java Pool。
  • PGA：会话私有，排序、Hash Join、Bitmap 等；OLTP 常用 PGA_AGGREGATE_TARGET 自动管理。
  • 后台进程：DBWn 写数据块、LGWR 写 redo、CKPT 检查点、SMON 实例恢复、PMON 进程清理、ARCn 归档。
  • 逻辑结构：数据库 → 表空间 → 段 → 区 → 块；物理结构：数据文件、控制文件、redo、参数文件、密码文件、归档日志。
  • RAC：多实例共享一份存储，通过 Cache Fusion（GCS/GES）在节点间传数据块；依赖私网 interconnect、OCR 和 Voting Disk；前端用 SCAN/VIP + TAF 做连接漂移。
  • Data Guard：主库 LNS 传 redo，备库 RFS 接收、MRP 应用；三种保护模式的最大区别是主库是否等待备库确认。
高频追问：“RAC 是共享存储，那存储坏了怎么办？” 答：RAC 只解决实例级高可用，不解决存储单点；生产上要配 ASM 冗余、存储双活或 Data Guard 异地备库，形成“本地 RAC + 异地 DG”。

2.2 达梦 DM8：最像 Oracle 的国产库 高频

体系结构（四层）

  • 逻辑结构：数据库 → 表空间 → 段 → 簇 → 页；默认页大小 8KB、簇大小 16 页，初始化后页大小不可改。
  • 物理结构：数据文件 .DBF、控制文件 dm.ctl、联机日志 dm01.log、归档日志、参数文件 dm.ini、dmarch.ini、dmwatcher.ini。
  • 内存结构：内存池（MEMORY_POOL）、数据缓冲区（BUFFER）、排序区、Hash 区、日志缓冲区等。
  • 线程结构：监听线程、工作线程、IO 线程、日志 FLUSH 线程、日志归档线程、定时器线程、调度线程、TRACE 线程。

高可用三件套

  • Data Watch：主备集群，实时主备（同步，RPO=0）、异步备、级联备、远距离备；由 DMWatcher 守护、DM Monitor 监控。
  • DSC：共享存储多活集群，类似 Oracle RAC，节点间通过 MAL 网络通信。
  • MPP：Shared Nothing 分布式，按分布键水平拆分，适合分析型 / 大规模数据。

常用命令 / 视图

disql SYSDBA/SYSDBA@127.0.0.1:5236 · V$INSTANCE · V$SESSIONS · V$TABLESPACE · V$ARCHIVED_LOG · V$BACKUPSET · V$LOCK · V$TRX

与 Oracle 的差异点（面试常问）：DM 是多线程模型；默认端口 5236；备份用 dmrman/dexp；高可用是 Data Watch 而非 DG；没有 Oracle 的 SCN 机制，用 LSN；部分语法、函数、执行计划有差异，迁移必须做兼容性改造。

2.3 金仓 KingbaseES：PG 内核 + Oracle 兼容 高频

体系结构

  • 进程模型：postmaster 主进程 + 每个连接一个 backend 进程；辅助进程包括 checkpointer、background writer、walwriter、archiver、autovacuum launcher、stats collector。
  • 逻辑结构：数据库簇（cluster）→ 数据库 → 模式（schema）→ 表 / 索引。
  • 物理结构：数据目录 data/、base/、global/、WAL 目录、控制文件 pg_control。
  • Oracle 兼容：支持 Oracle 模式，兼容 PL/SQL、ROWNUM、DUAL、序列、同义词、包、DBLink 等，降低迁移改造量。

高可用

  • 主备流复制：同步 / 异步，一主多备；备库只读，可做报表和备份。
  • RWC 读写分离集群：主库写、备库读，通过读写分离代理或中间件路由。
  • KES Sharding：分布式水平拆分，适合海量数据。

工具与视图

ksql · sys_ctl · sys_basebackup · sys_dump/sys_restore · sys_rman · sys_stat_statements · pg_stat_replication · pg_stat_activity

必答差异：金仓底层是 PostgreSQL，所以它有 MVCC、VACUUM、WAL、单进程多连接；与 Oracle 最大的不同是没有 undo 表空间、依赖 autovacuum 回收死元组，长事务会导致表膨胀。

2.4 GaussDB：CN / DN / GTM / CM 分工 架构必背

组件职责

  • CN（Coordinator Node）：接收 SQL、解析优化、生成分布式计划、下发 DN 并行执行、汇总结果。
  • DN（Data Node）：存储数据分片，执行本地查询；主备副本之间同步日志。
  • GTM：全局事务管理器，生成全局事务 ID、快照、时间戳，保证跨 DN 事务一致性。
  • CM：集群管理，cm_agent 上报状态，cm_server 决策主备切换；基于多数派（Quorum）避免脑裂。

高频考点

  • 分布键怎么选：高基数、分布均匀、常用于 Join / 过滤的字段；避免热点和严重数据倾斜。
  • 高可用：DN 一主多备，同步复制 RPO=0；CM 检测故障后自动升备，RTO 秒级。
  • 备份：Roach 并行物理备份（全量/增量），gs_dump 逻辑备份，支持 PITR。
  • 调优：EXPLAIN PERFORMANCE 看分布式执行计划，关注 Broadcast / Redistribute / 数据倾斜。

2.5 PolarDB：计算存储分离 加分

  • 架构：计算节点（主 + 只读）与存储分离，底层共享分布式存储 PolarFS，多个计算节点共享同一份数据。
  • 一写多读：主节点写，只读节点通过物理复制读共享存储，延迟低；可扩展到多个只读节点。
  • 弹性：存储按量扩展，计算节点秒级扩容；备份使用存储快照，速度快、对业务影响小。
  • 高可用：多可用区部署，主节点故障自动切换；只读节点可承接读流量。
  • PolarDB-X：分布式版，CN 计算节点 + DN 存储节点 + GMS 全局元数据，水平拆分与分布式事务。
  • 运维：控制台 / OpenAPI / DAS；关注慢 SQL、连接数、CPU、存储水位、只读延迟。
面试话术：“PolarDB 的核心是把存储做成共享池，计算节点无状态化，所以扩容、备份、读扩展都快；代价是强依赖底层存储和网络，排障时要同时看计算层和存储层指标。”

3.2 切换预案必须包含的 8 项 高频

  1. 触发条件：什么情况切（主库宕机、网络分区、存储故障），谁有权决策。
  2. 角色与分工：指挥、执行、验证、业务确认、厂商支持，联系方式。
  3. 前置检查：备库延迟、日志连续性、备份可用性、应用连接配置。
  4. 切换步骤：停业务 → 确认无新写入 → 主备角色切换 → 启动 → 验证。
  5. 验证点：数据一致性、复制状态、应用连通性、关键交易冒烟。
  6. 回退条件与步骤：什么情况回退、回退窗口、数据反向同步。
  7. 业务影响：停机时长、影响范围、通知模板。
  8. 复盘与演练：演练频率、记录、问题闭环。

3.3 脑裂与延迟：两个必答追问

脑裂怎么防

  • 引入第三方仲裁：Oracle Voting Disk、达梦 DM Monitor / 仲裁节点、GaussDB 多数派、金仓 witness。
  • 网络分区时宁可停止写入，也不能双主写入；优先保证数据一致性。
  • 切换前确认旧主已隔离（ fencing / STONITH / 存储屏蔽），再升备。

主备延迟怎么查、怎么处理

  • 查：Oracle v$dataguard_stats；金仓 pg_stat_replication 的 replay_lag；达梦 v$dmwatcher / 归档日志差异；GaussDB pg_stat_replication。
  • 原因：大事务、批量导入、网络带宽不足、备库 IO 慢、主库写入突增、同步复制等待。
  • 处置：拆分大事务、限流、提升网络/IO、临时改异步（需评估 RPO）、扩容备库资源。

3.4 两地三中心怎么讲

“同城两个中心做同步复制 + 自动切换，保证 RPO=0、RTO 分钟级；异地第三个中心做异步复制或备份，防区域级灾难。生产上还要考虑链路带宽、复制延迟、切换顺序和回切方案。演练时按‘单实例故障 → 单机房故障 → 区域灾难’三级场景逐步验证。”

注意：不要一上来就说“上 RAC 就高可用了”。RAC 只解决实例层，存储、机房、逻辑误删都不防；完整体系是“本地高可用 + 同城容灾 + 异地备份 + 定期演练”。

性能调优：用方法论而不是运气

分层定位，拿证据说话

4.1 分层排查模型 答题框架

4.2 一条 SQL 变慢，标准排查 8 步 必考

  1. 确认现象：是所有 SQL 慢还是单条？从什么时候开始？有无变更/数据量突增？
  2. 拿到 SQL 和绑定变量：不要只看平均，找最差执行、最高 DB Time 的 SQL。
  3. 看执行计划：是否走错索引、全表扫描、笛卡尔积、排序溢出、并行度异常。
  4. 看统计信息：是否过期、是否采样不足、是否有大量数据变更后未收集。
  5. 看等待事件：DB CPU、db file sequential read、log file sync、enq: TX row lock、library cache 等。
  6. 看对象与锁：索引是否失效、表是否膨胀、是否有锁等待/阻塞、是否有长事务。
  7. 看资源：CPU、IO、内存、网络是否打满；是否被其他会话/备份任务抢占。
  8. 处置与验证：加/改索引、改写 SQL、收集统计信息、调参数、限流；对比调优前后耗时和逻辑读。

4.3 索引失效的 8 个典型场景

  • 在索引列上做函数/表达式：where trunc(create_time)=...
  • 隐式类型转换：字符串列传数字、数字列传字符串。
  • 前导模糊查询：like '%xx'。
  • 联合索引不满足最左前缀。
  • 使用 or 且部分条件无索引。
  • 使用 not in、!=、is null（视优化器和数据分布）。
  • 数据分布倾斜，优化器判断全表扫描更便宜。
  • 统计信息过期，优化器估算错误。
反问加分：“全表扫描一定差吗？” 不一定。小表、高比例返回、宽表顺序读时全扫可能更快；关键看逻辑读、返回行数占比和实际耗时，不能只看执行计划里的 TABLE ACCESS FULL。

一个可讲的调优案例（把数字换成你的）

背景：某核心查询从 0.5 秒劣化到 30 秒，业务超时。
定位：AWR 发现该 SQL 逻辑读暴涨；执行计划由索引范围扫描变为全表扫描；统计信息显示表数据量一周增长 40%，且索引列被加了函数。
处置：先加临时索引/改写 SQL 止损；再收集统计信息、将函数条件改为范围条件、调整联合索引顺序；最后加慢 SQL 告警和数据增长监控。
结果：耗时从 30 秒降到 0.3 秒，逻辑读下降 90%，同类问题纳入巡检。

备份恢复：运维的底线能力

5.1 备份策略怎么答 必背

先讲原则，再讲落地：

  • 3-2-1 原则：至少 3 份数据、2 种介质、1 份异地。
  • 全量 + 增量 + 归档：每周全备、每天增量、归档日志持续备份，支撑任意时间点恢复（PITR）。
  • 分层：本地快速恢复（最近 7 天）+ 异地长期保留（按合规要求 6 个月~数年）。
  • 验证：定期做恢复演练，不是只看备份任务成功；校验备份集完整性、可恢复性、恢复耗时。
  • 监控：备份失败告警、归档空间水位、备份窗口超时。
面试官最爱追问：“备份成功就代表能恢复吗？” 答：不代表。要定期做异机恢复演练，验证备份介质、归档连续性、恢复脚本和耗时；核心库至少每季度一次，重要变更前额外做一次。

5.4 备份恢复的 6 个实战细节

  • 归档必须开：没有归档就没有 PITR；归档空间要独立监控，满了会挂起数据库。
  • 备份窗口：避开业务高峰；物理备份对 IO 有压力，可限速/压缩。
  • 加密与权限：备份文件含敏感数据，需加密、最小权限、审计下载。
  • 恢复顺序：参数文件 → 控制文件 → 数据文件 → 归档/日志 → recover → open。
  • 恢复验证：检查数据文件头、归档连续性、SCN/LSN、告警日志。
  • 演练报告：记录 RTO 实测值、遇到的问题、改进项，形成闭环。

6.1 六阶段迁移方法论 加分项

6.2 兼容性十坑（能讲出 3 个就很加分）

  1. 空字符串：Oracle 中 '' 等于 NULL，PG 系/部分国产库不这么认为。
  2. 大小写：Oracle 默认大写对象名，PG 系默认小写，需统一引号策略。
  3. ROWNUM / LIMIT：分页写法不同，需改写。
  4. 序列：Oracle 序列语法与自增列机制不同。
  5. 存储过程/包：PL/SQL 到 PL/pgSQL 或达梦过程语言，需重写和回归。
  6. 数据类型：NUMBER、VARCHAR2、DATE、CLOB/BLOB、TIMESTAMP 映射差异。
  7. 隐式转换：字符串与数字比较行为不同，可能导致索引失效或报错。
  8. 外连接写法：Oracle (+) 需改为标准 JOIN。
  9. 执行计划：优化器不同，迁移后可能走错计划，需重新收集统计信息并调优。
  10. 字符集与时区：迁移前确认源库字符集，避免乱码和时间偏移。

6.3 割接 Runbook 与回退

割接前

  • 全量 + 增量已追平，延迟在秒级；应用连接串、驱动、账号权限已准备。
  • 完成至少一轮全链路演练，记录各步骤耗时。
  • 原库开启归档并保留，作为回退基础。

割接中

  • 停写 → 确认无新事务 → 追平最后增量 → 校验 → 切换 DNS/连接串 → 冒烟。
  • 每一步有人执行、有人复核、有人记录时间点。

回退条件

  • 数据校验不一致、关键业务报错、性能不达标且短时间内无法解决。
  • 回退要在窗口内完成，原库保持可写回或反向同步。
面试表达：“迁移不是‘导过去就行’，核心是兼容性改造 + 数据一致性校验 + 可回退。我一般会把割接拆成可验证的小步骤，每步都有回退点。”

7.3 数据库上 K8s 的 8 个坑 高频追问

  • 存储性能：网络存储 IOPS/时延不达标，数据库变慢；核心库优先本地 SSD / 高性能云盘。
  • Pod 漂移：节点故障后 Pod 重建，数据必须在 PVC 上；本地盘要用 local PV + 节点亲和。
  • 资源争抢：没有设置 request/limit，CPU 被其他 Pod 抢走，出现性能抖动。
  • 时钟同步：容器与宿主机时钟不一致会影响事务和日志，需 NTP/chrony。
  • 网络延迟：CNI 网络 + 存储网络叠加，主备复制延迟变大。
  • 优雅终止：terminationGracePeriodSeconds 太短，数据库来不及 checkpoint。
  • 调度集中：主备 Pod 被调度到同一节点，节点故障双挂；用反亲和分散。
  • 备份缺失：只备份 PV 不够，要用数据库原生备份到对象存储，并验证恢复。

弹性伸缩怎么答才专业

不要直接说 HPA 扩数据库副本。数据库是有状态服务，HPA 简单加副本会带来数据一致性和集群成员变更问题。正确做法：读写分离扩只读副本、垂直扩容（升 CPU/内存）、存储扩容、用 Operator 做受控扩缩容；业务侧配合连接池、限流和读写分离。无状态应用才适合 HPA。

A. 基础与架构

Q1Oracle 实例和数据库有什么区别？
  • 实例=内存（SGA）+ 后台进程，是运行时的、易失的；数据库=磁盘上的数据文件、控制文件、redo、归档等，是持久的。
  • 一个实例通常对应一个数据库（非 RAC）；RAC 是多个实例共享一个数据库。
  • 面试可补一句：关库后实例消失，数据库文件还在；启动是先 nomount（读参数、建实例）→ mount（读控制文件）→ open（打开数据文件）。
Q2SGA 由哪些部分组成？PGA 是干什么的？
  • SGA：Shared Pool（SQL/执行计划/数据字典）、Database Buffer Cache、Redo Log Buffer、Large Pool、Java Pool、Streams Pool。
  • PGA：会话私有内存，用于排序、Hash Join、Bitmap、游标等；OLTP 用 PGA_AGGREGATE_TARGET 自动管理。
  • 要点：SGA 共享、PGA 私有；调优时看 buffer cache 命中率、硬解析、PGA 溢出到临时表空间。
Q3Oracle 的逻辑结构和物理结构分别是什么？
  • 逻辑：数据库 → 表空间 → 段 → 区 → 数据块。
  • 物理：数据文件、控制文件、联机重做日志、归档日志、参数文件、密码文件、告警日志。
  • 关系：一个表空间由多个数据文件组成；一个段由一个或多个区组成；区由连续的数据块组成。
Q4达梦 DM8 的体系结构是什么？和 Oracle 最大的区别在哪？高频
  • 四层：逻辑结构（库→表空间→段→簇→页）、物理结构（DBF、dm.ctl、日志、归档、dm.ini）、内存结构（内存池、BUFFER、排序区、HASH 区）、线程结构（监听、工作、IO、日志 FLUSH、归档、定时器、调度、TRACE）。
  • 最大区别：DM 是单进程多线程，Oracle 是多进程；DM 默认端口 5236，Oracle 1521。
  • 高可用：DM 用 Data Watch 主备、DSC 共享存储、MPP，对应 Oracle 的 DG、RAC、分布式。
  • 备份：dmrman / dexp，对应 RMAN / expdp。
Q5达梦的页大小和簇大小是什么？初始化后能改吗？
  • 页是 DM 的最小 IO 单位，常用 8KB（可选 4/8/16/32KB）；簇（extent）由连续页组成，默认 16 页。
  • 页大小在初始化实例时确定，之后不能修改；簇大小也建议初始化时规划好。
  • 引申：迁移前要评估大字段、行长度，页太小可能导致行迁移/溢出。
Q6金仓 KingbaseES 为什么能兼容 Oracle？底层是什么？高频
  • 底层基于 PostgreSQL，属于多进程、MVCC、WAL 架构；通过 Oracle 兼容模式支持 PL/SQL、ROWNUM、DUAL、序列、同义词、包、DBLink 等。
  • 工具都是 sys_ 前缀：sys_ctl、sys_dump、sys_restore、sys_rman、sys_basebackup。
  • 与 Oracle 的关键差异：没有 undo 表空间，依赖 autovacuum 回收死元组；长事务会导致表膨胀，这是迁移后重点。
Q7GaussDB 的 CN、DN、GTM、CM 分别负责什么？高频
  • CN：协调节点，接收 SQL、解析优化、生成分布式计划、下发 DN、汇总结果。
  • DN：数据节点，存储分片数据、执行本地查询，主备副本同步。
  • GTM：全局事务管理器，生成全局事务 ID、快照、时间戳，保证跨节点事务一致性。
  • CM：集群管理，cm_agent 上报、cm_server 决策，基于多数派做故障检测和主备切换。
Q8PolarDB 计算存储分离有什么好处？
  • 计算节点无状态，存储共享（PolarFS），扩容、备份、读扩展都快。
  • 一写多读：只读节点共享同一份数据，物理复制延迟低，可承载报表/读流量。
  • 备份用存储快照，速度快、对业务影响小；支持 PITR。
  • 代价：强依赖底层存储和网络，排障要同时看计算层和存储层。
Q9分布式数据库的分布键/分片键怎么选？
  • 高基数、分布均匀，避免数据倾斜和热点。
  • 优先选业务查询和 Join 最常用的字段，减少跨节点数据重分布。
  • 避免频繁更新的字段；避免单值过多的字段（如状态、性别）。
  • 上线后持续监控 DN 数据量和 CPU 分布，发现倾斜及时调整。
Q10读写分离怎么做？读延迟怎么处理？
  • 方案：主库写、备库/只读节点读；通过代理（如读写分离中间件）、应用多数据源或驱动路由。
  • 延迟来源：主备复制延迟、备库负载高、大事务。
  • 处理：强一致读走主库；弱一致读走备库；监控复制延迟，超阈值自动摘除只读节点；拆分大事务。
  • 注意：读写分离不是高可用，主库挂了仍需切换方案。

B. 高可用与容灾

Q11Oracle RAC 的原理是什么？Cache Fusion 怎么工作？高频
  • 多个实例通过私网互联，共享同一份存储；每个实例有自己的 SGA，但数据文件共享。
  • Cache Fusion：一个实例需要另一个实例内存中的脏块时，通过 GCS/GES 在私网传输块镜像，避免直接写磁盘再读。
  • 依赖：OCR（集群配置）、Voting Disk（仲裁防脑裂）、私网 interconnect、SCAN/VIP。
  • 局限：只解决实例级高可用，不防存储故障，需要配 ASM 冗余、存储双活或 DG。
Q12RAC 脑裂是怎么产生的？OCR 和 Voting Disk 的作用？
  • 节点间私网/心跳中断，但节点都还活着，各自认为对方挂了，可能出现双写。
  • Voting Disk 用于仲裁，多数派节点存活才能组成集群；少数派被驱逐，避免双主。
  • OCR 保存集群资源、实例、服务、VIP 等配置，需要定期备份。
  • 处置：先确认心跳网络，再检查 Voting Disk 和集群日志，不要盲目重启所有节点。
Q13Data Guard 的三种保护模式有什么区别？高频
  • 最大保护（Maximum Protection）：主库提交前必须收到至少一个同步备库确认，RPO=0；备库全挂时主库会宕，可用性最低。
  • 最高可用（Maximum Availability）：正常情况下 RPO=0；备库不可用时自动降级为最大性能，主库继续运行。
  • 最大性能（Maximum Performance）：异步传输，主库性能最好，RPO>0。
  • 选型：核心交易用最高可用；报表/容灾可最大性能。
Q14switchover 和 failover 有什么区别？
  • Switchover：计划内切换，主备角色互换，不丢数据，可回切；用于演练、维护、升级。
  • Failover：故障时强制切换，可能丢数据，原主库需要重建；用于灾难恢复。
  • 答的时候补一句：切换前要确认日志追平、应用连接配置、切换后验证和回退方案。
Q15达梦 Data Watch 的原理是什么？实时主备和异步备的区别？高频
  • 主库把日志发送到备库，备库重演；DMWatcher 守护实例和复制状态，DM Monitor 做监控和仲裁。
  • 实时主备：同步复制，主库等待备库确认，RPO=0，但备库故障可能影响主库。
  • 异步备：主库不等待确认，性能好，RPO>0，适合远距离容灾。
  • 还有级联备（备库再带备库）和远距离备；切换要防脑裂，需仲裁/监视器。
Q16达梦 DSC 和 Oracle RAC 有什么区别？
  • 相同点：共享存储、多节点多活、节点间通过高速网络同步缓存/锁信息。
  • 不同点：DM DSC 基于 DM 自己的多线程架构和 MAL 网络；Oracle RAC 用 GCS/GES + Cache Fusion。
  • 两者都不防存储单点，生产要配存储冗余和异地容灾。
Q17金仓主备流复制同步和异步怎么选？同步备库挂了主库会怎样？
  • 同步：主库提交等待备库确认，RPO=0，但备库故障会影响主库写入，通常配一同步一异步。
  • 异步：主库不等待，性能好，RPO>0，适合跨机房。
  • 同步备库挂了：主库可能 hang 住等待确认；需及时摘除同步备或降级为异步，恢复后再加回。
  • 监控：pg_stat_replication 的 state、sync_state、replay_lag。
Q18两地三中心怎么设计？切换预案包含什么？
  • 同城双中心同步复制 + 自动切换，RPO=0、RTO 分钟级；异地第三中心异步复制或备份，防区域灾难。
  • 预案：触发条件、角色分工、前置检查、切换步骤、验证点、回退条件、业务通知、演练复盘。
  • 演练按“单实例 → 单机房 → 区域灾难”分级，记录实测 RTO。

C. 备份恢复

Q19冷备和热备的区别？归档模式有什么用？
  • 冷备：停库拷贝文件，一致性好但停机；热备：开库备份，依赖归档保证一致性。
  • 归档模式把联机日志持久化，支持 PITR、Data Guard、在线备份。
  • 生产核心库必须开归档；归档空间要独立监控，避免写满挂库。
Q20RMAN 的全备、增量、level 0/1 怎么理解？
  • 全备：备份所有数据块；level 0 是全备的基准，可作为增量起点。
  • level 1：差异增量（自上次 level 0/1 以来的变化）和累积增量（自上次 level 0 以来的变化）。
  • 配合块变更跟踪（Block Change Tracking）提升增量备份速度；归档日志单独备份。
  • 恢复：还原数据文件 → 应用归档 → recover → open。
Q21误删表怎么恢复？高频
  • Oracle：优先 FLASHBACK TABLE ... TO BEFORE DROP（回收站）；若已 purge，用备份 + 归档做表级时间点恢复。
  • 达梦：从逻辑备份导入单表，或用 dmrman 备份 + 归档做表空间/表级还原。
  • 金仓/GaussDB：PITR 恢复到临时库，再比对回写；不要直接在生产库上反复试。
  • 通用顺序：止损 → 保护现场 → 评估影响 → 选最快恢复路径 → 校验 → 复盘。
Q22怎么验证备份是有效的？
  • 检查备份任务状态、备份集大小、归档连续性。
  • 定期做异机恢复演练，记录恢复耗时（实测 RTO）和数据校验结果。
  • Oracle 可用 RESTORE VALIDATE、VALIDATE BACKUPSET；其他库做实际还原验证。
  • 核心库至少每季度一次，重大变更前额外做。
Q23RPO 和 RTO 怎么定？
  • 由业务决定，不是 DBA 拍脑袋：交易类 RPO=0、RTO 分钟级；报表类可放宽。
  • RPO 决定复制方式（同步/异步）和备份频率；RTO 决定切换方式（自动/手动）和恢复方案。
  • 成本和指标要平衡：RPO=0 + RTO 秒级通常意味着更高成本和更复杂的架构。
Q24归档日志满了怎么办？
  • 先确认是否已备份：已备份的归档可按保留策略清理；未备份的绝不能删。
  • 临时扩容归档空间或调整归档路径；必要时增加备份频率。
  • 根因：大事务、批量导入、备份失败、保留策略不合理；从源头治理并加水位告警。
  • 注意：Oracle 归档满可能导致数据库挂起，处置要快。

D. 性能调优与故障

Q25一条 SQL 突然变慢，你怎么排查？必考
  • 先确认影响面：单条还是整体？从何时开始？有无发布、数据量突增、统计信息变化。
  • 拿 SQL 和执行计划：是否走错索引、全表扫描、笛卡尔积、排序溢出、并行度异常。
  • 看等待事件和锁：DB CPU、db file sequential read、log file sync、行锁等待。
  • 看统计信息和对象：统计信息过期、索引失效、表膨胀。
  • 处置：加/改索引、改写 SQL、收集统计信息、调参数、限流；用前后耗时和逻辑读验证。
Q26执行计划怎么看？全表扫描一定差吗？
  • 看访问路径（索引扫描/全表扫描）、Join 方式（Nested Loop/Hash Join/Merge Join）、成本、基数估算、实际行数。
  • 重点看估算行数与实际行数差异，差异大通常是统计信息问题。
  • 全表扫描不一定差：小表、高比例返回、宽表顺序读时可能更优；关键看逻辑读和实际耗时。
  • 工具：Oracle dbms_xplan.display_cursor / SQL Monitor；金仓 explain (analyze,buffers)；GaussDB EXPLAIN PERFORMANCE。
Q27索引失效的常见场景有哪些？
  • 索引列上做函数/运算；隐式类型转换；前导模糊 like '%x'。
  • 联合索引不满足最左前缀；or 条件部分无索引；not in/!=。
  • 数据分布倾斜、统计信息过期，优化器主动放弃索引。
  • 应对：改写 SQL、建函数索引/组合索引、收集统计信息、检查隐式转换。
Q28统计信息和绑定变量对性能有什么影响？
  • 统计信息让优化器估算行数和成本；过期或采样不足会导致走错计划。
  • 绑定变量减少硬解析，但可能出现“绑定变量窥探”导致计划不适合所有值。
  • 应对：定期收集统计信息、对倾斜列用直方图、必要时用 SQL Profile/Baseline 固定计划。
Q29AWR 里你最关注哪些指标？
  • DB Time、DB CPU、等待事件 Top 5、SQL ordered by Elapsed/CPU/Gets/Reads。
  • 逻辑读、物理读、硬解析、执行次数、平均耗时。
  • 结合 ASH 看时间段内的活跃会话分布，定位是某条 SQL 还是整体负载。
Q30数据库 CPU 100% 怎么定位？高频
  • 先看是数据库进程还是其他进程：top -Hp <pid> 找高 CPU 线程。
  • 数据库内：查活跃会话、当前 SQL、执行计划、并行度、硬解析。
  • 常见原因：低效 SQL 全表扫描、缺索引、并行度过高、硬解析、排序/Hash 溢出、锁自旋。
  • 处置：抓 Top SQL → 调优/限流/杀会话 → 加索引/改 SQL → 复盘加慢 SQL 监控。
Q31锁等待和死锁怎么处理？
  • 查锁：Oracle v$lock/v$session；金仓/GaussDB pg_locks/pg_stat_activity；达梦 v$lock。
  • 找阻塞源：根据 blocking_session 找到根会话，确认业务是否可杀。
  • 死锁：数据库通常自动检测并回滚一方；人工介入时优先杀代价小的事务。
  • 根治：缩短事务、统一加锁顺序、减少大事务、加超时和重试。
Q32主备延迟越来越大，怎么排查？
  • 查延迟指标：Oracle v$dataguard_stats；金仓/GaussDB pg_stat_replication；达梦 v$dmwatcher/日志差异。
  • 看主库写入是否突增（大事务、批量导入）、网络带宽/延迟、备库 IO 和 CPU。
  • 处置：拆分大事务、限流、提升网络/存储、临时改异步（评估 RPO）、扩容备库。
  • 预防：延迟监控告警、批量任务错峰、定期演练。
Q33达梦/金仓/GaussDB 参数调优的重点分别是什么？
  • 达梦：MEMORY_POOL、BUFFER、SORT_BUF、HASH 区、工作线程数；关注 HASH 冲突和排序溢出。
  • 金仓：shared_buffers、work_mem、maintenance_work_mem、effective_cache_size、max_connections、autovacuum 相关。
  • GaussDB：shared_buffers、work_mem、max_process_memory、并发控制、WLM 资源池、分布键和统计信息。
  • 通用原则：先定位瓶颈，再调参数；每次只改一个，压测验证，记录基线。
Q34操作系统层怎么做适配调优？
  • 内存：关闭/降低 swap，调整 vm.swappiness，大页 HugePages。
  • IO：IO 调度器（SSD 用 noop/none）、预读、文件系统挂载参数、独立磁盘放日志。
  • 内核：共享内存 shmmax、信号量 semmni、文件句柄 nofile、进程数 nproc。
  • CPU/网络：NUMA 绑核、中断亲和、网络带宽和重传；用 top/vmstat/iostat/pidstat 对齐时间轴。

E. 云原生与自动化

Q35在 K8s 上跑数据库要注意什么？高频
  • 用 StatefulSet + Headless Service 保证稳定网络标识和有序启停。
  • 数据必须落 PVC；核心库用高性能存储，注意 RWO/RWX 和节点亲和。
  • 设置 request/limit、探针、优雅终止时间、反亲和分散主备。
  • 用 Operator 管理部署、备份、扩缩容和切换；备份要落到对象存储并验证恢复。
Q36StatefulSet 和 Deployment 有什么区别？
  • StatefulSet 提供稳定 Pod 名（db-0、db-1）、稳定网络标识、稳定存储、有序部署/扩缩容。
  • Deployment 的 Pod 是无状态的、可互换的，不适合数据库主备角色。
  • 数据库集群成员发现、主备角色、PVC 绑定都依赖 StatefulSet 的稳定性。
Q37PVC 挂载失败怎么排查？
  • kubectl describe pod 看 Events；kubectl get pvc 看是否 Pending。
  • 常见原因：StorageClass 不存在、容量不足、访问模式不匹配、节点亲和冲突、云盘可用区不一致。
  • 再看 CSI 插件日志、后端存储权限和网络。
  • 处置：修正 StorageClass/容量/亲和；不要直接删 PVC 以免数据丢失。
Q38数据库能不能用 HPA 做弹性伸缩？
  • 不建议直接 HPA 扩数据库副本：有状态服务涉及数据一致性、集群成员变更、主备角色。
  • 正确做法：扩只读副本、垂直扩容、存储扩容、Operator 受控扩缩容。
  • 业务侧配合连接池、限流、读写分离；无状态应用才适合 HPA。
Q39你写过什么自动化脚本？怎么设计的？
  • 举例：巡检（表空间、归档、会话、锁、主备延迟）、备份校验、日志清理、主备切换演练、数据迁移。
  • 设计：配置分离、幂等、超时重试、结构化日志、异常告警、退出码。
  • 落地：crontab / Jenkins / 运维平台定时调度；结果入库和可视化。
  • 价值：把重复巡检从小时级降到分钟级，减少人为遗漏。
Q40监控告警体系怎么设计？
  • 分层：基础资源（CPU/内存/IO/网络）、数据库（可用性、连接数、慢 SQL、锁、复制）、业务（交易量、失败率）。
  • 分级：预警/严重/致命，不同通知渠道和升级策略。
  • 收敛：去重、抑制、依赖收敛，避免告警风暴。
  • 闭环：每条告警有处置手册和责任人，定期复盘误报漏报。

F. 迁移与项目经验

Q41Oracle 迁移到达梦，具体怎么做？加分
  • 评估：对象、数据量、SQL 复杂度、存储过程/包、字符集、时区。
  • 改造：数据类型映射、语法兼容、函数替换、分页/ROWNUM、序列、大小写、空字符串。
  • 迁移：DTS 做结构和全量，DMHS 做增量追平；先迁测试库做全链路验证。
  • 验证：数据量/抽样/聚合校验、业务回归、性能压测、执行计划对比。
  • 割接：停写 → 追平 → 校验 → 切连接 → 冒烟；保留原库和回退方案。
Q42迁移过程中最大的坑是什么？
  • 兼容性：空字符串与 NULL、大小写、ROWNUM、存储过程、隐式转换。
  • 性能：迁移后执行计划变化，原本走索引的 SQL 变成全表扫描。
  • 数据一致性：增量追平后仍有少量差异，校验方案必须可量化。
  • 回退：原库保留、反向同步、回退窗口，否则出问题很被动。
Q43迁移后怎么保证数据一致？
  • 行数比对、主键/唯一键比对、金额/汇总类聚合校验、抽样明细比对。
  • 增量阶段持续比对，割接前做最终一致性校验并留报告。
  • 业务侧做功能回归和关键交易验证；异常数据有清单和处置方案。
Q44割接方案和回退方案怎么写？
  • 割接：时间窗口、步骤、责任人、每步耗时、验证点、业务通知、应急预案。
  • 回退：触发条件（校验不一致/关键报错/性能不达标）、回退步骤、数据反向同步、回退时限。
  • 提前演练至少一轮，记录实际耗时；割接当天按 Runbook 执行，双人复核。
Q45讲一次你印象最深的故障处理。必考
  • 用 STAR：背景（系统/规模/影响）→ 现象（告警/报错/指标）→ 定位（分层排查、证据）→ 处置（止损、根治）→ 结果（量化恢复时间）→ 复盘（预防措施）。
  • 建议选“主备延迟/CPU 打满/误删数据/迁移后性能下降”这类有技术含量的案例。
  • 一定要有量化结果和后续改进，体现闭环意识。
  • 不要编造；细节经不起追问反而扣分。

6 个情景排障题

先止损，再定位，后根治

场景 1：应用突然报“数据库连接不上”

  1. 确认范围：是所有应用还是单个应用？是所有节点还是单节点？
  2. 网络与监听：ping/telnet 端口、监听状态、防火墙、VIP/SCAN、DNS。
  3. 实例状态：进程是否在、告警日志、v$instance/pg_isready、是否处于 mount/恢复。
  4. 连接数：是否达到 max_connections / processes 上限，是否有连接泄漏。
  5. 处置：重启监听、清理空闲会话、扩容连接数、切备库；恢复后查根因并加连接池监控。

场景 2：数据库 CPU 持续 100%

  1. 止损：确认影响业务后，先限流/杀高消耗会话/暂停批量任务。
  2. 定位：top -Hp 找线程 → 数据库内查活跃会话和当前 SQL → 看执行计划和等待事件。
  3. 常见根因：缺索引全表扫描、并行度过高、硬解析、排序/Hash 溢出、锁自旋。
  4. 根治：SQL 调优、加索引、收集统计信息、调整并行度和内存参数。
  5. 预防：Top SQL 监控、慢 SQL 告警、发布前 SQL 审核。

场景 3：主备延迟持续增大

  1. 确认：延迟从何时开始、是否持续、影响哪些只读业务。
  2. 查主库：是否有大事务、批量导入、DDL、日志生成量突增。
  3. 查备库：CPU/IO 是否打满、回放进程是否正常、是否有长查询阻塞回放。
  4. 查网络：带宽、延迟、丢包、重传。
  5. 处置：拆分大事务、限流、临时改异步（评估 RPO）、扩容备库、摘除延迟节点。

场景 4：表空间/归档空间快满了

  1. 确认：哪个表空间、增长趋势、是否有临时段/大事务；归档是否已备份。
  2. 止损：扩容数据文件/加盘；已备份归档按策略清理；暂停非核心批量任务。
  3. 根因：数据增长、临时排序、归档保留策略、备份失败。
  4. 根治：容量规划、分区/归档历史数据、加监控水位告警。
  5. 注意：未备份的归档不能删；删数据前确认可恢复。

场景 5：误删了核心业务表

  1. 立即止损：停止相关写入，避免覆盖可恢复窗口；通知业务和负责人。
  2. 保护现场：记录操作时间、账号、SQL、影响范围。
  3. 快速恢复：Oracle 回收站/Flashback；其他库用备份 + 归档恢复到临时库。
  4. 校验回写：比对数据后回写生产，避免二次伤害。
  5. 复盘：权限最小化、生产禁 delete 无 where、审计、变更审批。

场景 6：迁移后应用报错或性能下降

  1. 先回退还是先修：看影响面和窗口，关键业务优先回退，非关键可快速修复。
  2. 报错：看应用日志和数据库错误码，常见是类型、空字符串、大小写、函数不兼容。
  3. 性能：对比迁移前后执行计划，检查统计信息、索引、参数、数据分布。
  4. 处置：改写 SQL、补索引、收集统计信息、调整参数；必要时回退。
  5. 复盘：兼容性评估清单、回归测试用例、割接前压测。

南方电网项目：特色与话术

体现你做过功课

11.1 项目背景关键词

  • 数字电网 / 数字南网：核心业务系统上云、数据集中、智能化运维。
  • 信创国产化：Oracle 存量逐步替代为达梦、金仓、GaussDB、PolarDB，多库并存。
  • 业务范围：覆盖广东、广西、云南、贵州、海南五省区，系统规模大、链路长。
  • 稳定性要求：营销、计量、调度等系统 7×24 运行，重大保供电期间零故障。
  • 安全合规：电力监控系统安全防护、等保 2.0、数据安全法、权限与审计。

11.2 电力行业“十六字方针” 加分

安全分区 · 网络专用 · 横向隔离 · 纵向认证

  • 安全分区：生产控制大区与管理信息大区隔离，数据库部署位置要合规。
  • 网络专用：电力调度数据网等专用网络，禁止随意跨区访问。
  • 横向隔离：不同安全区之间用隔离装置，不是普通防火墙。
  • 纵向认证：上下级系统之间的身份认证和加密。
怎么用：被问到“电力行业数据库运维有什么特殊要求”时，先答这十六个字，再补“所以变更要审批、访问要最小权限、数据要分级分类、操作要审计”。

11.3 三条可直接用的话术

为什么选南网“我一直做核心库运维和国产化迁移，南网正在做大规模信创替代和多库并存，这正好是我这几年积累的方向；而且电力行业对稳定性要求高，能把运维规范和高可用能力真正用起来。”
怎么保证稳定“我的做法是三件事：变更前有备份和回退、运行中有监控和巡检、故障后有预案和演练。核心库不做没验证过的变更，重要操作双人复核。”
怎么面对 7×24“我接受应急响应机制，也做过值班和夜间故障处理。我的习惯是把重复问题脚本化、把处置步骤预案化，这样夜间处理不依赖个人记忆，也能降低压力。”
提醒：不要过度吹捧，也不要背稿感太重。用“我做过什么 + 和岗位怎么匹配”来表达，真实最重要。

反问、收尾与面试禁忌

最后 5 分钟也能加分

12.1 三个高质量反问

  1. “目前团队的数据库规模和技术栈分布大概是怎样的？国产化替代进行到哪个阶段了？”
  2. “这个岗位入职后前三个月最重要的目标是什么？是保障存量稳定，还是推进迁移/自动化？”
  3. “团队的值班和应急响应机制是怎样的？自动化运维平台建设到什么程度？”

不要一上来问薪资、加班、转正；这些可以等 HR 面或 offer 阶段再谈。

12.2 面试禁忌

  • 不编造：没做过的迁移/故障，不要硬说做过；被追问细节会露馅。
  • 不抢功：团队成果说清楚“我负责哪部分”，比“都是我做的”更可信。
  • 不贬低：不要说国产库“难用/不行”，也不要说前公司/前同事坏话。
  • 不沉默：不会的问题说“这块我了解不深，我的思路是……”，展示推理过程。
  • 不空谈：少说“精通”，多讲场景、动作、结果和数字。

12.3 面试前 10 分钟速记

  • Oracle 端口 1521，DM 5236，金仓 54321。
  • DM 默认页 8KB、簇 16 页，初始化后页大小不可改。
  • Oracle 逻辑：表空间→段→区→块；内存：SGA+PGA。
  • RAC = 多实例共享存储 + Cache Fusion；不防存储单点。
  • DG 三模式：最大保护 / 最高可用 / 最大性能。
  • DM 高可用：Data Watch / DSC / MPP。
  • 金仓 = PG 内核 + Oracle 兼容；工具 sys_ 前缀。
  • GaussDB = CN / DN / GTM / CM；分布键决定数据落点。
  • PolarDB = 计算存储分离 + 共享存储 + 一写多读。
  • 备份 3-2-1；没恢复过的备份等于没有备份。
  • 排障公式：止损 → 分层 → 证据 → 处置 → 复盘。
  • 电力十六字：安全分区、网络专用、横向隔离、纵向认证。
